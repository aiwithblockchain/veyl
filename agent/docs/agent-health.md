# Agent 健康状态：运维平台的第一个观察点

> 日期：2026-11-27
> 状态：**草案**。建议一、二已实现（`3544ac9`）；建议三（双钥匙）方案已定，尚未实现。
> 相关：`agent/docs/traffic-metering.md`（读取逻辑）、`docs/design/admin-console.md`（运维平台全貌）

---

## 0. 一句话

运维平台要回答的第一个问题是：**这台机器的 agent 现在读得到网卡数据吗？** 本文件定义为了让这个问题可回答，agent 侧需要补什么。

---

## 1. 目标与边界

**要回答的**：

- agent 进程还活着吗？
- 它最近一次成功读到计数器是什么时候？
- 如果读不到，连续失败几次了、最后一次的错误是什么？

**不试图回答的**：

- 流量计得准不准（那是 `traffic-metering.md` 的范围）
- agent 进程彻底挂了之后的状态（进程死了就没人能回答，只能靠「查询失败」推断）

**一条贯穿全篇的原则**：运维与业务分开。运维读状态不应该复用客户端的凭据模型，也不应该让控制面代劳轮询。

---

## 2. 现有通信机制

agent 是一个 MCP 服务器，监听 `0.0.0.0:32100`，MCP 挂在 `/mcp`（Streamable HTTP，无状态、JSON 响应、不开 SSE）。

端口对公网开放，但真正拦人的是四道闸：

| 闸 | 内容 |
|---|---|
| TLS | 自签证书；信任锚（CA / 叶指纹）只能从控制面取 |
| Host 白名单 | Host 头必须是本机公网 IP 或配置的域名 |
| Bearer 令牌 | Ed25519，claims `{server_id, jti, exp}`；`server_id` 必须等于本机，`exp` 60 秒 |
| jti 一次性 | 只在执行 `tools/call` 时消费，落盘，重启后仍有效 |

令牌由控制面持私钥签发；签发入口按 `account_id` 过滤，别人的 server 拿不到票。

**现有的业务工具只有两个，都是写操作**：`rotate_credentials`（轮换 Shadowsocks 端口与密码）、`upgrade_singbox`（装控制面当前发布的 sing-box 版本并自检）。

**没有任何读取状态的工具。** 这是本文件要补的第一块。

## 3. 建议一：`get_status` 与两个新字段

### 3.1 工具

新增只读工具 `get_status`，返回 agent 当前的自检状态。

数据来源是 agent **内存里**的 `TrafficState`（第一次成功读取时从 `/var/lib/veyl-agent/traffic.json` 载入，之后每 `save_secs` 落盘一次）。不要读磁盘——那份最多滞后 5 分钟。

注意是**第一次成功读取**才载入，不是进程启动：首次 `tick` 之前这份状态还是空的，那就是 §3.4 里 `metering: null` 的窗口。

### 3.2 为什么现有字段不够

`TrafficState` 现在有 `counter_last`、`pending_bytes`、`last_ok_at`、`seq`。其中：

- `counter_last` 是最后一次读到的计数，**只有读成功才会变**；
- `last_ok_at` 记的是最后一次**上报成功**的时间（`traffic.rs:253`），不是最后一次读取。

所以「计数器在涨」是滞后指标，「上次上报成功」和「读网卡是否正常」也不是同一件事。要直接回答问题，需要两个新字段：

| 字段 | 含义 | 更新时机 | 落盘 |
|---|---|---|---|
| `last_read_at` | 最后一次**成功读到计数器**的时间 | `tick` 读取成功的分支 | 是 |
| `consecutive_read_failures` | 连续读取失败的次数 | 失败 +1，成功清零 | **否** |

`last_read_at` 落盘：重启后、第一次 tick 之前，它还能说明上次成功读取是什么时候。`consecutive_read_failures` 不落盘（`#[serde(skip)]`）：「连续」跨进程重启没有意义，旧值被读回来会让新进程声称观察到一个它没观察过的连续失败。

有了这两个，`counter_last` 在涨 + `last_read_at` 是几十秒内 + `consecutive_read_failures == 0`，才是「正在正常读取」。

两者都加 `#[serde(default)]`，旧状态文件照常能读。

### 3.3 返回内容（草案）

```json
{
  "version": "0.1.7",
  "uptime_secs": 3600,
  "now": 1795760400,
  "metering_attached": true,
  "metering": {
    "counter_last": 156708490,
    "pending_bytes": 156707288,
    "seq": 1795759055,
    "last_read_at": 1795760351,
    "last_ok_at": 1795759055,
    "consecutive_read_failures": 0,
    "observed": true
  },
  "cert_state": "current",
  "cert": {
    "not_after": 1955000000,
    "renewal_failures": 0,
    "last_renewal_error": null
  },
  "health": { "...": "见 §4" }
}
```

- `now` 是**节点自己的时钟**（unix 秒）。所有绝对时间都要和它一起读，否则节点时钟偏了会把判断整个翻转。
- `observed: false` 表示本次进程还没成功读过计数器，`metering` 里的数字是从状态文件恢复的**最后已知值**。它和「从没读过」不是一回事。
- `cert_state` 的四种取值见 §3.5；只有 `current` 时 `cert` 块才有内容。

### 3.4 `metering: null` 有两种含义，必须分开

`metering` 为 `null` 时，可能是两件完全不同的事：

| 情形 | 含义 | 是否生产状态 |
|---|---|---|
| `metering_attached: false` + `metering: null` | 计量模块根本没接上（开发用的 `serve` 命令） | 否 |
| `metering_attached: true` + `metering: null` | 接上了，从没读过，状态文件里也没有 | 是，短暂 |
| `metering_attached: true` + `metering.observed: false` | 本次进程还没读成功，数字是上次落盘的；`last_read_at` 能说明**多久以前**成功过 | 是，可能长期 |

第三种是这一版补的：重启后如果一直读不到计数器，以前 `metering` 会一直是 `null`，已经落盘的 `last_read_at` 也被一起藏起来——管理员看到「uptime 1 小时 + 空 + nft_read 失败 120 次」，会读成「刚启动还没读」，而不是「已经坏了很久」。

如果不分开，第一种情形会配上一个空的 `health: {}`，在仪表盘上就是一片绿——和 §4.1.1 要消灭的假绿灯是同一个东西。

`metering_attached` 由服务端在构造时确定，不依赖运行时状态。

`uptime_secs` 不能省，原因见 §4.3。

### 3.5 证书状态

`cert: null` 本身说明不了任何问题——它可能是还没换证的存量节点，也可能是证书文件已经坏了。必须看 `cert_state`：

| 取值 | 含义 | 要不要处理 |
|---|---|---|
| `current` | 统一根签发、验签通过、SAN 覆盖当前地址 | 否 |
| `legacy` | 自签证书，文件可用（存量节点尚未换证） | 是，随迁移处理 |
| `stale` | 不是自签，但不是当前根签发（meta 丢失或根已更换） | 是，必须重签 |
| `broken` | 证书或私钥缺失、损坏、不配对，节点可能已经服务不了 | 是，最高优先 |

`current` 时 `cert` 块才有内容；更准确地说，只要叶证书由**当前根**签发（即使 SAN 标记落后、状态显示 `stale`），`cert` 块就有值；meta 丢失时 `not_after` 为空。

| 字段 | 来源 | 落盘 |
|---|---|---|
| `not_after` | 签发成功时控制面返回、agent 存下来 | 是 |
| `renewal_failures` | 续期请求连续失败次数，成功清零 | 否 |
| `last_renewal_error` | 最近一次续期失败原文，截断 | 否 |

**运维平台判断「续期坏了」不靠这个块，靠 D1 里的到期日。** 控制面每次签发成功都会把 `servers.cert_not_after` 写成新的到期时间；续期正常时，这个值会在进入 30 天窗口后的几小时内跳到两年后。如果它停在原处不动，就是续期失败——这比等 agent 把失败事件送上来可靠，因为续期失败时网络往往正是不通的。

`get_status` 里的这个块是**诊断用**：能连上时才看得到，用来回答「失败了几次、最后一次报什么错」。`renewal_failures` 不落盘的理由同 §3.2 的 `consecutive_read_failures`。

## 4. 建议二：内存级错误表

### 4.1 结构

一张**固定 key** 的映射，进程内有效，不落盘：

```
key -> { count, last_at, last_error, last_ok_at }
```

`count` 是**连续**失败次数：成功一次就清零，并把 `last_ok_at` 更新到当前时间。只增不清会让恢复后的节点一直挂着红色，和假绿灯一样有害。

初始 key（后续可扩）：

| key | 记录什么 | 状态 |
|---|---|---|
| `nft_read` | 读计数器失败 | 已接线 |
| `report` | 上报控制面失败 | 已接线 |
| `singbox_apply` | 应用期望状态失败 | 仅声明 |
| `logging` | 日志轮转失败 | 仅声明 |

### 4.1.1 未接线的 key 不出现在返回里

`get_status` 的 `health` **只包含已接线的 key**。未接线的 key 不是返回一个 `count: 0` 的零值，而是**根本不出现**。

`count: 0` 在仪表盘上看起来是「没有失败」，实际上根本没人记录——那是假绿灯。**「没测量」和「测量了、没失败」是两个不同的答案**，不能长得一样。

这条和本仓其它地方的原则一致：把「没有答案」压成「一切正常」，是这一整轮改动反复在消灭的模式。

### 4.2 唯一的硬约束

**key 必须是编译期常量。** 不能来自外部输入、不能动态拼接，否则这张表会无界增长。以后把别的模块接进来，沿用这个约定即可。

每条错误只保留最近一条，截断到几百字节；不堆历史。

### 4.3 为什么必须配 `uptime`

这张表在进程重启后清空。管理员看到一片绿，可能只是「刚重启过」，而不是「一直健康」。所以 `get_status` 必须同时返回 `uptime_secs`，让读的人自己判断这片绿有多长的历史。

### 4.4 共享方式

表放在一个 `Arc` 里，计量模块和控制端点各持一份引用：计量侧写，`get_status` 侧读。不打日志、不落盘，微秒级。

## 5. 建议三：双钥匙与运维 worker

> **2026-11-27 实测更正，先读这一段。** Cloudflare Worker **连不到 agent**：`fetch` 连裸 IP 被 Cloudflare 自己的 1003 拦掉（请求没出网），`node:tls` 用 `{socket}` 报类型不兼容、用 `{host, port}` 报 `proxy request failed`。所以下面 5.3/5.5 里「运维 worker 直接调 `get_status`」**不成立**。
>
> 改为：由能固定证书的**原生客户端**（桌面 / 手机 App）直连 `IP:32100`，worker 只负责登录、读清单、签只读票。证书侧改用统一根证书，见 `certificates.md`。

目标：让运维平台直接调用 `get_status`，且它拿到的凭据不能执行写操作；运维与业务的信任链彻底分开。

### 5.1 两把钥匙，编译进 agent

| 公钥 | 私钥在哪 | 用途 |
|---|---|---|
| `signer_pubkey` | 控制面 | 业务：拥有者的桌面端调工具 |
| `ops_signer_pubkey` | 运维 worker | 运维：查询健康状态 |

两个私钥互不持有。agent 启动时同时信任两把公钥。

### 5.2 能力由钥匙决定，不由 claim 决定

**业务钥匙签的票 → 全部工具。运维钥匙签的票 → 只有只读工具。**

不用 `scope` 字段。理由是：**scope 是声明，钥匙是事实**。运维 worker 即使被攻破、被逼着签一张 `write` 票，agent 也会因为「这把钥匙只配读」而拒绝。

这个替代同时消掉了 scope 方案的三个麻烦：新增 claim、读票是否豁免 `jti` 的裁决、以及「新增写工具忘了标记」的风险——那把钥匙本来就调不到写工具。

### 5.3 验签与放行

先试业务钥匙，验不过再试运维钥匙。哪把钥匙验过，决定这次能调哪些工具。

`server_id` 校验两把钥匙都要做：票仍然绑定到**具体一台**机器，运维票也不能跨机器使用。

验签结果是一个能力枚举（全权 / 只读），由「哪把钥匙验过」产生，**不来自请求内容**。

实现时三条容易写漏的：

- **能力映射写成 allowlist，默认拒绝**，不要写成「只读工具」的名单。将来加一个「顺带清理点东西」的读工具，反向名单会让它自动继承副作用。
- **`jti` 是否消费也由同一个枚举决定**。业务票消费、运维票不消费——如果只按「是不是 `tools/call`」判断，运维票会被消费掉，第二个请求就 401。
- **两把公钥在编译期断言不相等**。配置成同一把，运维票就拿到了全权，而运行期不会有任何报错。

### 5.4 有效期与 jti

| 票类型 | 有效期 | jti |
|---|---|---|
| 业务（现有） | 60 秒 | 一次性，落盘 |
| 运维 | **1 小时** | 不消费——读操作重放无害 |

业务票保持现状不动。运维票定 1 小时：换票频率降到每节点每小时一次，泄露窗口仍然有限，而且这是个可调常量。

### 5.5 运维 worker 与手机 / 桌面 App

App 用 Cloudflare Access 认证到运维 worker，**App 全程不接触任何私钥**。worker 持运维私钥，按请求为某台机器签一张只读票。

换手机、丢手机都不影响密钥安全——这是把密钥留在服务端而不是客户端的意义。

### 5.6 运维 worker 直接共享控制面的数据库

运维 worker 绑定同一份 D1，读写都在里面，**不新建管理员接口**。

两条理由：

- 运维平台只有一个用户，入口由 Cloudflare Access 兜底，暴露面本来就只有一个；
- **只读的看板修不了垃圾数据**。控制面自己会留下需要人工收拾的行——比如建机在 agent 起好之前就开始累计流量份额的机器。这类数据只能改，看板修不了。

要拿的三个值（IP、`control_port`、证书指纹）都不是秘密：IP 与端口扫 DO 地址段就能发现；证书对任何发起连接的人都公开出示；指纹是那张公开证书的哈希，知道它只能**验证**对方，不能冒充。

**失败要分态**：指纹会变（公网 IP 变了、证书重签了）。worker 拿着旧指纹去连会 TLS 失败，看起来和「agent 挂了」一模一样。**「指纹不匹配」和「连不上」必须分成两种状态**，否则一次正常的证书轮换就会变成全站误报——那比没有监控更糟。

### 5.7 写操作的约束（当前不实现）

**现在只做 `get_status` 查询，不涉及任何写。** 以后加写功能时按下面八条来，否则「修数据」本身会制造新的垃圾：

1. **有代码路径的走代码路径。** 销毁、退款、激活这些控制面已经有实现，里面包含状态守卫、并发处理和审计。直接写库会绕过它们。
2. **所有直写必须是带状态守卫的条件 `UPDATE`。** `changes = 0` 就重读、重新展示，**绝不盲写**。理由是并发：计费 Cron 每 5 分钟和每 60 分钟各扫一遍同一批行，直接写库最大的风险就是和它同时改同一行。
3. **点名禁止直写 `wallet_ledger` / `payments` / `topups`。** 这三张表的每一行都对应一个外部事实（Stripe 那边真实发生过的收款），直写会破坏对账不变量。涉及钱的表一律走控制面的代码路径。
4. **环境与 schema 归属**：一个部署只绑一个环境的 D1；运维端**永不执行迁移、不建表**。表结构归控制面。
5. **没有代码路径的才直接写，而且做成命名操作。** 按钮背后是一段固定、可审阅的语句，不是界面上随手跑的 UPDATE。
6. **每类写落一条 `audit_log`**，标明来源是运维平台。不是为了防谁，是为了事后能还原当时做了什么。
7. **有外部副作用的操作必须同时处理外部系统。** 例子：修复一台卡在建机的机器，正确做法是「销毁 droplet + 标记行 + 释放它已占用的额度」，而不是把状态字段改成 `destroyed`。只改状态会得到一台「库里说没了、DO 那边还在按秒计费」的机器——这正是我们自己踩过的坑。
8. **写之前展示改前值和影响范围。** 也就是 dry-run 那一屏。

### 5.8 代价与边界

- **运维公钥编译进二进制**，轮换它等于发一个新 agent 版本。这与业务钥匙相同——业务钥匙虽然有 enroll 时下发的通道，要退役旧钥匙同样得等节点换过一遍，所以不是新增负担。
- **存量节点不支持**：只有带运维公钥的新版本 agent 才会接受运维票。这是上线节奏问题，不是设计缺口：运维平台上线时覆盖的本来就是新版本节点。
- **运维私钥泄露的影响上界**：能给任何机器签只读票、读状态；不能签写票。这个上界由钥匙本身保证，不依赖任何运行时检查。
- **运维 worker 持有生产库的写权限**（§5.6）。它自己的代码质量因此等于控制面数据的安全边界——加写功能时尤其要记住 §5.7 那五条。

## 6. 这套设计不覆盖什么

- **agent 进程挂了**：`get_status` 调不到，只能靠「查询失败」判断。本文件不解决。
- **内存表重启清空**：见 §4.3，靠 `uptime` 让读的人区分。
- **计量的准确性**：不在本文件范围。
