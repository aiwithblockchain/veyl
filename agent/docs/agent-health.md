# Agent 健康状态：运维平台的第一个观察点

> 日期：2026-11-27
> 状态：**草案**。建议一、二进入实现；建议三（凭据）方案已定，尚未实现。
> 相关：`agent/docs/traffic-metering.md`（读取逻辑）、`docs/design/admin-console.md`（运维平台全貌）

---

## 0. 一句话

运维平台要回答的第一个问题是：**这台机器的 agent 现在读得到网卡数据吗？** 本文件定义为了让这个问题可回答，agent 侧需要补什么。

---

## 1. 目标与边界

**要回答的**：

- agent 进程还活着吗？
- 它最近一次成功读到计数器是什么时候？
- 如果读不到，连续失败几次了、最后一次的错误是什么？

**不试图回答的**：

- 流量计得准不准（那是 `traffic-metering.md` 的范围）
- agent 进程彻底挂了之后的状态（进程死了就没人能回答，只能靠「查询失败」推断）

**一条贯穿全篇的原则**：运维与业务分开。运维读状态不应该复用客户端的凭据模型，也不应该让控制面代劳轮询。

---

## 2. 现有通信机制

agent 是一个 MCP 服务器，监听 `0.0.0.0:32100`，MCP 挂在 `/mcp`（Streamable HTTP，无状态、JSON 响应、不开 SSE）。

端口对公网开放，但真正拦人的是四道闸：

| 闸 | 内容 |
|---|---|
| TLS | 自签证书；信任锚（CA / 叶指纹）只能从控制面取 |
| Host 白名单 | Host 头必须是本机公网 IP 或配置的域名 |
| Bearer 令牌 | Ed25519，claims `{server_id, jti, exp}`；`server_id` 必须等于本机，`exp` 60 秒 |
| jti 一次性 | 只在执行 `tools/call` 时消费，落盘，重启后仍有效 |

令牌由控制面持私钥签发；签发入口按 `account_id` 过滤，别人的 server 拿不到票。

**现有的业务工具只有两个，都是写操作**：`rotate_credentials`（轮换 Shadowsocks 端口与密码）、`upgrade_singbox`（装控制面当前发布的 sing-box 版本并自检）。

**没有任何读取状态的工具。** 这是本文件要补的第一块。

## 3. 建议一：`get_status` 与两个新字段

### 3.1 工具

新增只读工具 `get_status`，返回 agent 当前的自检状态。

数据来源是 agent **内存里**的 `TrafficState`（启动时从 `/var/lib/veyl-agent/traffic.json` 读入，每 `save_secs` 落盘一次）。不要读磁盘——那份最多滞后 5 分钟。

### 3.2 为什么现有字段不够

`TrafficState` 现在有 `counter_last`、`pending_bytes`、`last_ok_at`、`seq`。其中：

- `counter_last` 是最后一次读到的计数，**只有读成功才会变**；
- `last_ok_at` 记的是最后一次**上报成功**的时间（`traffic.rs:223`），不是最后一次读取。

所以「计数器在涨」是滞后指标，「上次上报成功」和「读网卡是否正常」也不是同一件事。要直接回答问题，需要两个新字段：

| 字段 | 含义 | 更新时机 | 落盘 |
|---|---|---|---|
| `last_read_at` | 最后一次**成功读到计数器**的时间 | `tick` 读取成功的分支 | 是 |
| `consecutive_read_failures` | 连续读取失败的次数 | 失败 +1，成功清零 | **否** |

`last_read_at` 落盘：重启后、第一次 tick 之前，它还能说明上次成功读取是什么时候。`consecutive_read_failures` 不落盘（`#[serde(skip)]`）：「连续」跨进程重启没有意义，旧值被读回来会让新进程声称观察到一个它没观察过的连续失败。

有了这两个，`counter_last` 在涨 + `last_read_at` 是几十秒内 + `consecutive_read_failures == 0`，才是「正在正常读取」。

两者都加 `#[serde(default)]`，旧状态文件照常能读。

### 3.3 返回内容（草案）

```json
{
  "version": "0.1.6",
  "uptime_secs": 3600,
  "metering": {
    "counter_last": 156708490,
    "pending_bytes": 156707288,
    "seq": 1795759055,
    "last_read_at": 1795760351,
    "consecutive_read_failures": 0
  },
  "health": { "...": "见 §4" }
}
```

`uptime_secs` 不能省，原因见 §4.3。

## 4. 建议二：内存级错误表

### 4.1 结构

一张**固定 key** 的映射，进程内有效，不落盘：

```
key -> { count, last_at, last_error }
```

初始 key（后续可扩）：

| key | 记录什么 | 状态 |
|---|---|---|
| `nft_read` | 读计数器失败 | 已接线 |
| `report` | 上报控制面失败 | 已接线 |
| `singbox_apply` | 应用期望状态失败 | 仅声明 |
| `logging` | 日志轮转失败 | 仅声明 |

### 4.1.1 未接线的 key 不出现在返回里

`get_status` 的 `health` **只包含已接线的 key**。未接线的 key 不是返回一个 `count: 0` 的零值，而是**根本不出现**。

`count: 0` 在仪表盘上看起来是「没有失败」，实际上根本没人记录——那是假绿灯。**「没测量」和「测量了、没失败」是两个不同的答案**，不能长得一样。

这条和本仓其它地方的原则一致：把「没有答案」压成「一切正常」，是这一整轮改动反复在消灭的模式。

### 4.2 唯一的硬约束

**key 必须是编译期常量。** 不能来自外部输入、不能动态拼接，否则这张表会无界增长。以后把别的模块接进来，沿用这个约定即可。

每条错误只保留最近一条，截断到几百字节；不堆历史。

### 4.3 为什么必须配 `uptime`

这张表在进程重启后清空。管理员看到一片绿，可能只是「刚重启过」，而不是「一直健康」。所以 `get_status` 必须同时返回 `uptime_secs`，让读的人自己判断这片绿有多长的历史。

### 4.4 共享方式

表放在一个 `Arc` 里，计量模块和控制端点各持一份引用：计量侧写，`get_status` 侧读。不打日志、不落盘，微秒级。

## 5. 建议三：只读凭据

目标：让运维平台（而不是控制面）直接调用 `get_status`，且它拿到的凭据不能执行写操作。

### 5.1 令牌加 `scope`

claims 从 `{server_id, jti, exp}` 变成 `{server_id, jti, exp, scope}`，取值 `read` / `write`。

**缺省按 `write` 解释**：旧票、旧代码的行为完全不变，不需要一次性切换。

### 5.2 只读在哪强制

关键不在字段，而在**分类不能是一张游离的表**。工具的声明和它是否只读必须在同一处，`list_tools` 与 `call_tool` 共用这一份。

配一条表驱动的测试：遍历工具清单，对每个工具断言「读票能否调用」与它的声明一致。以后新增写工具而忘了标记，测试直接红，而不是悄悄开一个口子。

### 5.3 复用与 jti

只读票**不消费 jti**，因此在有效期内可反复调用。安全性来自「读操作重放无害」——重复查询返回的就是当前状态。

代价是泄露的读票在有效期内可反复使用，所以有效期必须短：

| 票类型 | 有效期 | jti |
|---|---|---|
| 写（现有） | 60 秒 | 一次性，落盘 |
| 读（运维） | **15 分钟** | 不消费 |

写票保持现状不动。选择 15 分钟而不是 1 小时，是因为换票成本可以忽略（每节点每 15 分钟一次），而泄露窗口缩短四倍。运维 App 可以在临近过期时主动续。

### 5.4 签发：控制面（已定 2026-11-27）

只读票仍由控制面签发，运维平台**不持有签名密钥**。

理由不是省事，是信任锚的数量：agent 在 enroll 时只拿到控制面那一把公钥。让运维侧自持密钥就要让每台 agent 信任第二把钥匙，而这把钥匙的轮换要推到所有存量节点——agent 目前没有自升级通道，等于每次轮换都绑上一次重建节点。

「运维与业务分开」分开的是**权限与用途**（读/写、运维工具/客户工具），不是签发者。签发权集中在一处反而是优势。

运维平台不是每次查询都申请：**每 15 分钟换一张票**，一张票管这一段的所有 `get_status` 调用。

### 5.5 控制面怎么认「管理员」

建议用 admin worker 与控制面之间的**共享密钥**（Cloudflare Secret 绑定）。边界只有一跳，而 admin worker 已经做过 Cloudflare Access 校验；在控制面里再验一遍 Access JWT 属于重复建设，还会把 Access 的 team domain / AUD 引进控制面配置。

密钥轮换通过更新 secret 完成，不涉及 agent，也不需要重建节点。

### 5.6 运维平台还缺的另一半

`get_status` 只回答「这台机器怎么样」，回答不了「我们有多少台机器、分别归谁、什么状态」。那部分在控制面的 D1 里，而现有接口全部按 `account_id` 过滤。

所以运维平台还需要控制面的**管理员接口**。它与 agent 凭据是两件独立的事，目前都不存在。


---

## 6. 这套设计不覆盖什么

- **agent 进程挂了**：`get_status` 调不到，只能靠「查询失败」判断。本文件不解决。
- **内存表重启清空**：见 §4.3，靠 `uptime` 让读的人区分。
- **计量的准确性**：不在本文件范围。
