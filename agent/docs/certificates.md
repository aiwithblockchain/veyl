# 证书体系：根证书、叶证书与浏览器信任

> 日期：2026-11-27
> 状态：**草案**。尚未实现。
> 相关：`agent/src/cert.rs`（当前实现）、`agent/docs/agent-health.md`（运维平台）

---

## 0. 一句话

控制面持一张**根证书**，每台 agent 拿它签自己的**叶证书**。浏览器只装一次根证书，之后访问任何节点都不再弹证书警告。

---

## 1. 为什么改

现在每台 agent 启动时自己在本地生成一张自签 CA 和一张叶证书（`cert.rs`）。好处是零依赖，坏处是**每台都不一样**：

- 桌面 App 能连，是因为控制面把这一台的 CA 发给它；
- 浏览器要连，就得给每一台点一次「继续前往」。

运维平台如果做成网页，每加一台机器就要人手点一次。换成统一根证书后，这个动作只发生一次。

---

## 2. 三张证书的关系

```
根证书（控制面持有私钥）
   │  签发
   ├── 节点 A 的叶证书（私钥只在节点 A）
   ├── 节点 B 的叶证书（私钥只在节点 B）
   └── …
```

| 东西 | 私钥在哪 | 谁信任它 |
|---|---|---|
| 根证书 | 控制面的 Cloudflare secret | 浏览器（手动安装一次）、桌面 App、手机 App |
| 叶证书 | 各自的节点，**永不外传** | 任何信任根证书的一方 |

**叶证书的私钥永远不离开节点。** 控制面只签公钥，不代生成密钥。

---

## 3. 签发流程

1. agent 首次启动，本地生成一对密钥，把公钥做成 CSR。
2. agent 在 enroll 时把 CSR 一并发给控制面。
3. 控制面用根私钥签出叶证书，返回给 agent。
4. agent 把叶证书存到本地 `certs` 目录，和私钥放在一起。
5. 之后重启直接复用，**不再找控制面**。

叶证书的 SAN 包含节点的公网 IP——和现在一样。

---

## 4. 浏览器怎么装

在**专用浏览器或专用 profile** 里安装根证书。

理由不是怕它泄露（根私钥在 Cloudflare secret 里，和支付密钥同一级别），而是：装进浏览器意味着这台浏览器对**所有网站**都信任这张根。用独立 profile 的好处是万一出事，影响面只有这一个 profile，日常浏览不受牵连。

---

## 5. 有效期与轮换

- **根证书有效期定长**（十年以上），并把到期日记下来。到期不处理，所有节点会一起失效。
- 根轮换 = 用新根重签所有叶证书 + 浏览器重装一次。这是一个人工动作，不能自动化到没人知道。

---

## 6. 对现有客户端的影响

**不需要改。**

控制面的 `/v1/servers/{id}/agent-token` 现在返回每台的 `ca_pem` 和 `cert_fingerprint`。改造后：

- `ca_pem` 对所有节点都是同一张根证书；
- `cert_fingerprint` 仍然是每台的叶证书指纹。

客户端一直是「拿控制面给的信任锚去验对方」，换掉锚的来源它不需要知道。桌面端、手机端、以后的原生运维 App 都是这一套。

---

## 7. 关于「重签需要控制面」

现在的 agent 在叶证书的 SAN 缺公网 IP 时会本地重签，不需要控制面。改造后重签只能由根证书签，所以需要控制面可达。

这**不构成实际问题**：

- 公网 IP 按设计不变——变了，客户端配置里的地址也就失效了，节点事实上已经不可用；
- 唯一会触发重签的场景是「启动时元数据服务没答复、IP 稍后才探测到」。那时 enroll 已经成功，控制面必然可达；
- 叶证书是持久化的，正常重启走本地存档，不会触发重签。
