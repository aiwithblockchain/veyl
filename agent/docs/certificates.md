# 证书体系：根证书、叶证书与浏览器信任

> 日期：2026-11-27
> 状态：**草案，未实现**。技术前提已在本地 workerd 验证通过（§8），实现拆分见 §9。
> 相关：`agent/src/cert.rs`（当前实现）、`agent/docs/agent-health.md`（运维平台）

---

## 0. 一句话

控制面持一张**根证书**，每台 agent 拿它签自己的**叶证书**。浏览器只装一次根证书，之后访问任何节点都不再弹证书警告。

---

## 1. 为什么改

现在每台 agent 启动时自己在本地生成一张自签 CA 和一张叶证书（`cert.rs`）。好处是零依赖，坏处是**每台都不一样**：

- 桌面 App 能连，是因为控制面把这一台的 CA 发给它；
- 浏览器要连，就得给每一台点一次「继续前往」。

运维平台如果做成网页，每加一台机器就要人手点一次。换成统一根证书后，这个动作只发生一次。

---

## 2. 三张证书的关系

```
根证书（控制面持有私钥）
   │  签发
   ├── 节点 A 的叶证书（私钥只在节点 A）
   ├── 节点 B 的叶证书（私钥只在节点 B）
   └── …
```

| 东西 | 私钥在哪 | 谁信任它 |
|---|---|---|
| 根证书 | 控制面的 Cloudflare secret | 浏览器（手动安装一次）、桌面 App、手机 App |
| 叶证书 | 各自的节点，**永不外传** | 任何信任根证书的一方 |

**叶证书的私钥永远不离开节点。** 控制面只签公钥，不代生成密钥。

---

## 3. 签发流程

1. agent 首次启动，本地生成一对密钥，把公钥做成 CSR。
2. agent 在 enroll 时把 CSR 一并发给控制面。
3. 控制面用根私钥签出叶证书，返回给 agent。
4. agent 把叶证书存到本地 `certs` 目录，和私钥放在一起。
5. 之后重启直接复用，**不再找控制面**。

叶证书的 SAN 包含节点的公网 IP——但**不来自 CSR**，见下一节。

### 3.1 SAN 由控制面构造，不采信 CSR

这是整套设计里最要紧的一条约束。

叶证书的 SAN 由控制面用 `servers.ip`（加上 `localhost` / `127.0.0.1`）**自己拼出来**；CSR 里带的 `subjectAltNames` 一律忽略，带了白名单之外的条目就拒签并写审计。

理由：根证书装在浏览器里，对**所有站点**生效。如果签发权跟着 CSR 走，任何一台节点——或者只是偷到一台节点密钥的人——都能申请 `SAN=accounts.google.com`，用这张被信任的根签出来。那台浏览器访问任何 HTTPS 站点都可能被中间人。

今天不出事，是因为每台节点的 CA 是私有的、客户端只信那一台；换成共享根之后，**签发权就等于全站中间人**。这一条不能靠「节点是可信任的」来辩护——节点的私钥就在那台机器上，而那台机器只跑我们自己的代码，也挡不住有人拿到它。

同时约束：只接受 ECDSA P-256；CSR 里的密钥用法扩展不采信，用法由控制面固定。

---

## 4. 浏览器怎么装

在**专用浏览器或专用 profile** 里安装根证书。

理由不是怕它泄露（根私钥在 Cloudflare secret 里，和支付密钥同一级别），而是：装进浏览器意味着这台浏览器对**所有网站**都信任这张根。用独立 profile 的好处是万一出事，影响面只有这一个 profile，日常浏览不受牵连。

### 4.1 enroll 之后的签发通道

enroll 是一次性的——那条 token 只有 20 分钟、用一次就消费掉，只覆盖第一次装机。但后面还有三种情况需要签发：

- 叶证书到期续期（§5）
- 换根之后重签
- agent 丢了状态、或者私钥/证书文件损坏

所以需要一个 enroll 之后的入口：

```
POST /v1/agent/cert
Authorization: Bearer <server_token>    ← 就是上报流量用的那把，长期有效
body: CSR
→ 叶证书
```

**没有这个通道，§9 B 里「去掉本地重签」就等于去掉了一个能自愈的能力却不给替代**——叶证书一坏，节点就永久起不来。

---

## 5. 有效期与轮换

- **根证书有效期定长**（十年以上），并把到期日记下来。到期不处理，所有节点会一起失效。
- 根轮换 = 用新根重签所有叶证书 + 浏览器重装一次。这是一个人工动作，不能自动化到没人知道。
- **叶证书有效期一年**，剩余不足 30 天自动续期（走 §4.1 的通道）。现状 `cert.rs` 没有设置 `not_after`，rcgen 的默认是几千年——等于永不过期，泄露的叶证书在换根之前一直有效。这一点必须改。

### 5.1 不做吊销（明确取舍）

全篇没有 CRL / OCSP，这是有意的，不是遗漏：

- 叶证书只有在那张根被信任的范围内才有用，而根只装在我们自己的设备上；
- 真正的止损手段是「销毁节点 + 回收 IP」和「换根 + 重装浏览器」，都更重，但都有效；
- 做吊销要在 agent 和所有客户端都加检查逻辑，收益与成本不匹配。

以后如果节点数量上来、或者有多人持有根证书，这个取舍要重新看。

---

## 6. 对现有客户端的影响

**不需要改。**

控制面的 `/v1/servers/{id}/agent-token` 现在返回每台的 `ca_pem` 和 `cert_fingerprint`。改造后：

- `ca_pem` 对所有节点都是同一张根证书；
- `cert_fingerprint` 仍然是每台的叶证书指纹。

客户端一直是「拿控制面给的信任锚去验对方」，换掉锚的来源它不需要知道。桌面端、手机端、以后的原生运维 App 都是这一套。

---

## 7. 重签需要控制面，后果是什么

`cert.rs:118` 的 `leaf_usable` 判据是：**叶证书和私钥都在，且 SAN 标记文件的内容等于当前 host 列表**。所以触发重签的不止一种情形：

- 叶证书或私钥文件丢失、损坏；
- SAN 标记文件丢失或损坏；
- 配置里的 host 列表变化（不只是公网 IP，任何 host 变动）；
- 启动时元数据服务没答复、IP 稍后才探测到。

也就是说，**重签确实可能发生在控制面不可达的时候**（比如一次离线窗口里的配置改动）。

改造后这种情形只能失败并重试，不能本地兜底。后果是可控的：agent 起不了 TLS → 客户端连不上 → 节点事实上不可用；控制面一恢复就自动恢复。

**不做本地兜底重签**：那需要把根私钥放到每一台节点上，为了一个可用性问题把最大的密钥散布到全网，得不偿失。

## 8. 验证记录（2026-11-27）

### 8.1 环境与方法

| 项 | 值 |
|---|---|
| 运行时 | 本地 `wrangler dev`（workerd），**与生产同一运行时**，全程没有部署 |
| 库 | `@peculiar/x509` 3.1.0 + `reflect-metadata` |
| 密钥 | ECDSA P-256（WebCrypto 原生支持；agent 侧 rcgen 同样支持） |
| CSR | rcgen 0.14 真实生成，`CN=veyl-node-agent`，SAN 含 IPv4 `139.59.99.76` |

### 8.2 结果：四件事全部成立

worker 收到 CSR 后解析、用一张临时 CA 签发、把结果读回来：

```
csrSubject        = CN=veyl-node-agent
csrExtensionCount = 1                                  ← 扩展请求（SAN）解析成功
leafSubject       = CN=veyl-node-agent                 ← 主体来自 CSR
leafIssuer        = CN=veyl-test-root                  ← 由 CA 签，不是自签
leafSan           = [{"type":"ip","value":"139.59.99.76"}]  ← IP SAN 完整传递
```

结论：

1. **Workers 能签 X.509**：WebCrypto 提供 P-256 签名，`@peculiar/x509` 负责 DER 编码。
2. **能读懂 rcgen 的 CSR**：Rust 生成的 DER 在 Worker 侧解析无误。
3. **CA 签发可用**：不是自签，`issuer` 与 `subject` 正确分离。
4. **扩展能穿过签发**：CSR 里的 SAN 能被解析并写进叶证书——这证明「从 CSR 取扩展」这条路技术上通。**但生产实现不这么做**：SAN 由控制面自己构造，CSR 的 SAN 一律忽略，理由见 §3.1。

另外单独验过：`@peculiar/x509` 在 workerd 里能正常 `createSelfSigned`（早期只有这个测试时就返回过合法的 448 字节 PEM）。

### 8.3 尚未验证

- **浏览器实际安装根证书后的行为**：要等真的装一次、真的打开一台节点才知道。
- **证书轮换**：换根、重签全部叶证书的流程没有跑过。
- **agent 侧的持久化与重启复用**：属于实现，尚未动工。

## 9. 实现拆分

### A. 控制面（签发方）

- 根证书与私钥放 Cloudflare secret（PEM）。**私钥不进仓库、不进日志。**
- **SAN 由控制面构造**：`servers.ip` + `localhost` + `127.0.0.1`。CSR 的 `subjectAltNames` 一律忽略；带了白名单之外的条目就拒签并写审计（§3.1）。
- 密钥类型只收 ECDSA P-256；密钥用法扩展由控制面固定，不采信 CSR。
- 叶证书有效期一年。
- enroll 时接收 CSR 签出叶证书；另开 `POST /v1/agent/cert`（server token 鉴权）供 enroll 之后续期与重签（§4.1）。
- 继续往 `servers` 写 `cert_fingerprint`（叶证书）与 `ca_pem`（根证书）。

> 注意：`@peculiar/x509` 的依赖应该加在**控制面**，不是 admin worker。验证阶段加在 admin 只是因为两边同一个运行时，方便跑。

### B. agent（被签方）

- `cert.rs`：不再生成 CA。有可用的叶证书就用本地存档；否则生成密钥 + CSR。
- **「可用」的判据要改**：现在是「叶证书和私钥在，且 SAN 标记文件等于当前 host 列表」（`cert.rs:118`）。改造后还要加一条「叶证书的 issuer 等于当前根」——否则存量节点永远不会重签，见 D。
- enroll 请求带 CSR；enroll 之后走 `POST /v1/agent/cert` 续期。
- `identity.rs`：去掉本地重签路径（见 §7）。
- 剩余有效期不足 30 天时自动续期。

### C. 现有客户端

**不改。** 见 §6。

一个会被掩盖的现象要写在这里：控制面把 `ca_pem` 换成共享根之后，老节点仍是自签证书，App 的 CA 校验会失败并**回落到指纹固定**——客户端照常可用，所以这个问题只有浏览器能看见，写日志时别让它静默。

### D. 存量节点迁移

已上线节点的叶证书是自签的，换了根之后 `leaf_usable` 不会触发重签——它们会一直停在自签状态。所以：

- B 里那条「issuer 等于当前根」的判据是迁移的触发器；
- 重签走 `POST /v1/agent/cert`，用节点已有的 server token；
- 迁移窗口内 `ca_pem` 按每台返回：老节点返自签 CA、新节点返根。不需要一次性切换，也不需要停机。

### E. 运维端

浏览器装根证书、或者原生 App 直连，两种都行——但**发起连接的一方必须是能固定证书的客户端**。Cloudflare Worker 连不到 agent（实测：`fetch` 被 1003 拦、`node:tls` 两条路都失败），这一点见 `agent-health.md` §5 顶部。
