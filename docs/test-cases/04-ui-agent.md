## 3. 事件契约

事件名写错、或者改了常量却没改消费方，**运行时不会报错**——事件只是被静默丢弃，表现为「AI 在回复但界面不动」。所以这一类必须有编译期或 CI 期的机械检查，不能靠人眼。

| ID | 层 | 追溯 | 前置 | 步骤 | 预期 | 优先级 |
|---|---|---|---|---|---|---|
| **TC-CHAT-010** | U | `docs/contracts/events.md` §1、4.3 设计 | 仓库可构建 | 1) 跑 `node tests/contracts/check-contracts.mjs`；2) 跑前端单测 | 三项全部通过：①`AGENT_EVENTS` 的取值集合与契约事件总表**完全相等**（不多不少）；②`AGENT_EVENTS` 的每个取值都被 `src/state/chatStore.ts` 的 switch 处理；③`RuntimeStatus` / `RuntimeSnapshot` 的快照字段不含 `clash_addr` | P0 |
| **TC-CHAT-011** | U | 同上 | 人为把 `AGENT_EVENTS.messageChunk` 改成 `message-chunk-2`（不改 chatStore） | 1) 跑检查 | 检查**必须失败**并指出「chatStore 未处理事件 messageChunk = "message-chunk-2"」。如果它仍然通过，说明这条防线是假的 | P0 |
| **TC-CHAT-012** | E | 2.1 关联键 | 用户点「停止」后立刻发新消息，旧请求的 `ai-request-end` 迟到 | 1) 观察新会话 | 迟到事件按 `request_id` 被过滤，不污染新会话（不追加文本、不改状态）；状态行不被旧请求的 `ai-status` 覆盖 | P1 |

> **实现说明**：`tests/contracts/check-contracts.mjs` 已可用，它直接读契约文档、`src/agent/protocol.ts`、`src/state/chatStore.ts` 与 `src-tauri/src/runtime/manager.rs`，不依赖构建产物，因此可以在 CI 第一步跑。当前它会报出两处真实偏差（见测试计划 §13），这是预期的——偏差要由实现方修，不是把检查放宽。
>
> 前端的 `switch (event.name)` 目前用的是字符串字面量。即便以后改成 `case AGENT_EVENTS.messageChunk:`，本检查同样成立（脚本两种写法都识别）。不过**推荐改为引用常量**：这样改名时 TypeScript 会直接编译失败，比等 CI 更早。

### 4.1 `DeepseekSaveKey`：存下去，但可能验证不过

契约 §4.15 的铁律是「**Key 先存下来，验证失败也返回 `ok: true`**」，靠 `verified` + `failure_reason` 表达真实结果。理由是反过来会诱导 Agent 反复重试、多次写钥匙串。

| ID | 层 | 追溯 | 前置 | 步骤 | 预期 | 优先级 |
|---|---|---|---|---|---|---|
| **TC-SET-008** | I + E | FR-8.1、contracts/tools §4.15 | mock LLM 对含 `invalid` 的 Key 返回 401 | 1) 调 `DeepseekSaveKey({"key":"sk-test-invalid"})`；2) 查返回值、钥匙串、界面文案 | `ok=true`；`data.saved=true`；`data.verified=false`；`data.failure_reason="invalid_key"`；Key **已写入钥匙串**；**UI 与 Agent 都必须提示「已保存，但该 Key 无效」**，只显示「已保存」算失败；不得自动重试保存 | P0 |
| **TC-SET-009** | I | 同上 | mock LLM 不可达 | 1) 保存 | `ok=true`、`verified=false`、`failure_reason="network"`；提示区分「网络问题」与「Key 无效」，不引导用户去换 Key | P1 |
| **TC-SET-010** | I | 同上 | mock 返回余额不足（402） | 1) 保存 | `failure_reason="insufficient_balance"`；提示去充值，而不是让用户重新申请 Key | P1 |
| **TC-SET-011** | I | 同上、9.3 | 上述任一场景之后 | 1) 查 `data` / `content` / 事件 payload / 日志 | Key 明文出现 **0 次**；`failure_reason` 是枚举值，**不得**把上游错误响应原文透传给模型或 UI | P0 |

> **字段名对齐提醒**：PM 指令里写的是「`validation=invalid`」，契约 `tools.md` §4.15 的实际字段是 `verified: boolean` + `failure_reason: "invalid_key" | "insufficient_balance" | "network" | null`。用例按契约写。若产品确实想要 `validation` 这个字段名，要先改契约再改用例，不要两边各写一套。
