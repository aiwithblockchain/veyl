# 免费机场接入评估

> 日期：2026-11-04
> 性质：调研与判断，不含实现。**未收集、未下载任何真实节点凭据。**
> 问题：客户端要不要接入网上公开的免费机场/免费节点？

---

## 0. 结论先行

**分两种「接入」，结论不同：**

| 形态 | 结论 |
|---|---|
| **用户自己贴订阅链接**（现有 URL 导入） | **保留**。这是用户主动输入、我们自己生成配置，产品不生产也不分发节点 |
| **产品内置一批免费节点** | **不做** |
| **产品推荐/整理免费机场列表** | **不做** |
| **做「免费节点市场」由第三方提交** | **不做** |

**决定性的是两条，不是可持续性：**

1. **法律与凭据来源**：公开免费节点的上游大量是「别人的试用、泄露的订阅、扫描到的公开代理」。产品内置或推荐，等于我们成为一个公开分发入口——分发的是我们并不拥有的凭据。这与「安全、高端」的定位直接冲突，且把一个中立的用户工具变成「我们替你提供线路」。
2. **安全与信任**：出口运营方能看到域名、时间、流量与真实 IP；免费节点的商业动机通常就是收集这些、引流或投放。我们无法替用户审计一个每天换运营方的出口。

可持续性（节点几小时到几天就死）是**产品风险**，会让首次体验直接失败；但它不是唯一原因——即使节点很稳定，前两条仍然成立。

## 1. 事实层面

### 1.1 流通格式与我们的覆盖

| 格式 | 常见程度 | 我们现有能力（`config-execution.md` §6） |
|---|---|---|
| Base64 编码的 `ss://` / `vmess://` / `vless://` / `trojan://` 混合列表 | 很常见 | **只解析 `ss://`**；其它协议明确报不支持 |
| Clash / Mihomo YAML（`proxies:` + `proxy-groups:` + `rules:`） | 很常见，是很多聚合站的主格式 | **不支持**（本期只做 base64 多节点列表） |
| sing-box JSON | 常见于较新聚合站 | **不支持** |
| 纯文本 URI 列表（未编码，一行一个） | 常见 | 当前要求整段 base64，纯文本是否接受需要确认 |
| 账号密码 / 登录换取订阅 | 商业机场常见 | 本期不做 |

结论：**「技术上已经支持」只对「base64 编码的 Shadowsocks 子集」成立**。免费节点生态里占比很高的 VMess/VLESS/Trojan/Hysteria 和 Clash YAML，我们都接不了。要把覆盖率做上去，是另一个批次的解析工作，不是「已经有了」。

### 1.2 生命周期（公开社区观察，非严格统计）

| 来源类型 | 典型存活 | 说明 |
|---|---|---|
| 聚合站自动抓取、每日更新 | **几小时到 2 天** | 上游一关、IP 被标记、令牌过期就整批失效 |
| 人工转发/整理的订阅 | **1–7 天** | 上游停服即失效 |
| 机场自建引流节点 | 相对长，但限速、随时撤 | 目的是把用户导向付费 |
| 机场官方试用 | 取决于运营方 | 三类里最可追溯，但通常有流量/时限 |

补充观察：

- 「能连通」的测活通常只做端口探测，不测带宽；晚高峰大量节点不可用。
- 有实测对 107 条公开节点做严格 TLS 校验，只有约 27–31 条稳定通过（社区文章，非学术统计）。
- 订阅链接经常带一次性令牌或短期有效期，复制给别人就失效。

**对首启的含义**：我们的产品定位是「用来解决网络问题的工具」。第一次打开、默认线路大面积失效，用户不会区分「免费节点本来就不稳」和「这个产品不行」，直接卸载的概率很高。

### 1.3 来源

公开讨论里常见五类：

1. 机场试用/赠送（推广成本，可追溯）
2. 公益机场（自建或捐赠，通常邀请制、限速）
3. **别人分享或泄露的订阅**（来源不明，可能违反原服务条款）
4. 云平台免费额度自建（个人小规模）
5. **爬取/聚合的公开代理**（含端口扫描、蜜罐）

第 3、5 类是「免费节点池」的主要供给。把它们做成产品能力，等于我们替用户承担了「这些凭据从哪来」的问题。

## 2. 风险层面

### 2.1 安全

| 风险 | 说明 |
|---|---|
| 流量元数据 | 出口方能看到访问的域名（HTTPS 的 SNI 多为明文）、时间、上下行流量、真实 IP。HTTPS 内容看不到，但「你在访问什么」已经足够 |
| 中间人 | 真正能解密 HTTPS 的路径是让用户安装不明根证书/描述文件，或使用被改过的客户端。我们不应引导用户做这两件事 |
| 内容篡改 | HTTP 明文页面可被插入广告或替换内容 |
| 恶意订阅配置 | Clash YAML 是一份完整配置，可改 DNS、把不该走代理的流量也送进隧道、关闭证书校验 |
| 出口被当成「反向代理池」 | 部分「永久免费」客户端会把用户设备当出口；纯订阅模式风险较低，但说明这个生态的动机不纯 |

**我们现有设计的一个优势**：URL 导入只取五个字段（name/server/port/method/password），配置由我们自己生成，不消费对方的 YAML/DNS/证书设置。这挡掉了「订阅即完整配置」那一类攻击。**但它挡不住出口方看元数据，也挡不住出口方对 HTTP 流量的篡改。**

### 2.2 法律

- 中国监管框架下，提供/销售「翻墙」工具或服务存在明确的行政与刑事风险；实务讨论常引用「向 5 人以上提供」或「违法所得 5000 元以上」作为立案参考（检察院科普口径，非统一标准）。公开分发的商业产品，暴露面远大于个人自用。
- 共享、转售他人账号/订阅通常违反原服务商条款；如果凭据来自受管制服务商，分发入口的性质更敏感。
- **用户自己贴订阅**与**我们内置/推荐**在法律定性上不是一回事：前者是中立工具接受用户输入；后者是我们主动提供线路来源。
- 具体定性依司法辖区与事实而定，本评估不构成法律意见；对外发布前应由法务复核。

### 2.3 可持续

- 免费节点的高失效率与「首启即用」直接冲突。
- 免费节点的带宽被大量用户分摊，晚高峰体验差；用户会把账算在产品头上。
- 节点池越大，维护测活、解析、失效重试的成本越高；而这些节点不受我们控制，SLA 为零。
- 免费转付费的漏斗不是靠「节点多」成立的，而是靠「第一次体验可靠」。用不稳定的免费节点做漏斗，反而会毁掉漏斗。

### 2.4 和「种子不随包」的逻辑是否冲突

`config-execution.md` §9 的理由是：**安装包公开下载，打包进去的凭据会被提取滥用。** 同样的逻辑用在这里，结论是：

- **内置免费节点 = 把别人（或我们）的凭据放进公开安装包** → 一样会被提取、被白嫖、加速失效；而且这次受害者还包括第三方运营方，我们还要承担「分发他人凭据」的额外风险。
- **推荐列表**不把凭据放进包，但把「我们去哪找免费节点」产品化了，等于我们为这些节点的来源和安全背书；这与 §9 里「测试节点凭据不随包、由我们持续保障 URL」是两种完全不同的责任关系。
- **用户自己贴订阅**不违反这条逻辑：凭据是用户自己带进来的，我们不存储、不分发、不背书。

**所以：不冲突，但结论是「只保留用户主动导入」，不是「因此可以内置」。**

## 3. 如果要做，什么形态最合理

### 3.1 推荐：维持现状 + 明确边界

- 保留 URL 导入与手动编辑；它是用户主动行为。
- 不内置、不推荐、不整理免费机场列表。
- 导入结果**只解析、不自动连接**（现有约定），并复述五个字段让用户确认。
- 文案上不出现「免费」「推荐」「可用节点」这类背书词；只说「你自己的订阅」。
- 可选（非本期）：导入时一次性提示「节点由你提供，出口方可看到你的访问域名」，不阻断。

### 3.2 如果要接「免费转付费」的漏斗，走合作方，不走抓取

- 与可签约、可审计的服务商合作，作为**供应商渠道**接入（`provider-integration.md` 的方向）。
- 有合同、有 SLA、有安全责任划分，节点凭据由对方按协议提供，而不是从公开池里抓。
- 这与「免费机场」是两件事：前者是商业合作，后者是分发来路不明的凭据。

### 3.3 明确不做

| 形态 | 为什么不做 |
|---|---|
| 内置一批免费节点 | 凭据被提取、来源与法律风险、首启不可靠 |
| 推荐/整理机场列表 | 为来源背书；名单会迅速过期；无法审计 |
| 第三方提交的「节点市场」 | 需要审核、举报、下架、责任承担；本质是内容平台，不是我们当前的产品 |
| 自动抓取公开节点池 | 直接分发他人凭据；安全与法律风险最高 |

### 3.4 与现有种子机制的关系

- `veyl_seed.json` 是**我们自己的运维资源**，只放我们负责的节点；更新、测活、失效兜底都由我们承担。
- 用户订阅是**用户自己的资源**，与种子并列，不合并、不写进种子、不参与种子刷新。
- 如果将来接合作方，它是**第三个来源**，有自己的信任级别与生命周期；仍然不与种子混层。
