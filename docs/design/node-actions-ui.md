# 节点三个动作的界面设计（同步 / 智能修复 / 问 AI）

> 2026-11-22 · 草案，待 AI 可选线评审
> 范围：同一账号多设备场景下，节点「测不通」时用户能做的三件事在界面上的入口、顺序与状态。
> 上游：`connection-repair-actions.md`（连接页两个动作）、`node-rotation-and-sync.md`（轮换与同步）

## 1. 三个动作的分工

| 动作 | 本质 | 代价 | 什么时候该出现 |
|---|---|---|---|
| **更新配置** | 从控制面取回这台节点的最新端口与密码 | 无中断，可自动 | 任何「配置可能过期」的时刻；失败路径**先自动执行一次** |
| **智能修复** | 让节点 agent 换端口与密码 | 会断线，端口变化影响其它设备 | 同步后仍测不通 |
| **问 AI** | 把现象交给助手诊断 | 需要 AI 已配置 | 用户不确定原因时 |

**顺序是硬的：更新配置 → 智能修复 → 问 AI。** 多设备下反过来的代价是两台机器互相重置（A 换端口 → B 不通 → B 也换 → A 又不通）。

## 2. 入口矩阵（唯一住处）

| 界面 | 更新配置 | 智能修复 | 问 AI |
|---|---|---|---|
| 连接页 · 节点行（自有且测不通） | 不显示按钮，**失败后自动执行一次** | 行内动作 | 行内动作 |
| 智能修复确认弹窗 | 正文里的一条文字链「先更新配置」 | 主按钮 | 无 |
| 我的服务器 · 服务器详情 | 不显示 | 按钮（已有） | 无 |
| 设置 › 连接 · 节点配置同步 | 「立即同步」+ 周期选择 + 本会话最近同步时间 | 不显示 | 无 |
| 服务器列表 · 表头 | 同步图标（与设置行同一动作的快捷入口） | 不显示 | 不显示 |

规则：**同一个动作不在同一屏出现两次**；连接页任何时刻最多两个动作，不出现第三个。列表行为什么不显示「N 分钟前同步」：同步是全账号的，同一个时间戳挂在每一行是噪音；时间只住在设置行。

> 「配置已变更，请重试」+「重新连接并测试」不是第四个动作：它只在「同步发现变化且隧道在跑」这个状态下**替换**整行动作；重连测试通过就恢复，仍不通才换回「智能修复 · 问 AI」。所以同一时刻仍然只有两个可点目标。

## 3. 连接页 · 失败行

四种状态，行内右侧同一位置替换：

| 状态 | 行内显示 | 时长 / 触发 |
|---|---|---|
| 失败，自动同步中 | `测不通　正在更新配置…` | 同步返回即结束；上限 **22 秒**（单次请求 10 秒 + 全局锁排队最长 10 秒 + 余量），超过按「未完成」处理、直接进修复态 |
| 同步发现变化，且隧道正在运行 | `测不通　配置已变更，请重试` + `重新连接并测试` | 等用户点击；不自动重连 |
| 同步无变化，或隧道没在运行 | 自动重测一次 | 返回即结束 |
| 恢复 | 行内 `已恢复`，延迟回填 | 3 秒 |
| 仍不通 | `测不通　智能修复 · 问 AI` | 持续到状态改变 |

- **一次失败只同步一次。** 用户点了「重新连接并测试」仍不通，直接进修复态，**不再触发第二次同步**——问题已经不在配置上，再同步只是循环。标志在探测恢复通过后清除，下一次新的失败重新从同步开始。
- **配置变了不能只重测**：探测走的是正在运行的 sing-box，它的内存里还是旧端口；同步只改了本地数据库。所以节点在跑时必须由用户点「重新连接并测试」，然后才测；直接测一定失败，会把人误导到「智能修复」。
- **重连必须是 stop → start 两步**，不能只发 `runtime_start`：`RuntimeManager` 对同一个 plan 直接返回 `already_running`，凭据变化不在 plan 里，单发 start 不会重启，仍用旧端口。两步等价于用户手动断开再连接；期间行内显示「正在重新连接…」。
- **同步成功就重测一次，不比较端口**：值相同也可能只是密码变了（手工改密码的场景），比端口会漏掉；多一次测速换来逻辑简单与覆盖完整。
  - 重测通过且端口变了 → `已恢复` + 一句「配置已更新，连接已恢复」。
  - 重测通过但端口没变 → 只显示 `已恢复`，不声称配置更新过。
- 自动同步**不发 toast、不弹窗、不切节点**；恢复提示只在行内与卡片底部，不加全局提示。
- 控制面不可达或超过 22 秒：不提示「更新失败」（调用可能仍在后台落库），直接进入「仍不通」第三态，让修复入口可见；但**必须写一条日志**（区分「无变化」与「请求失败」），否则线上无法判断。

### 3.1 周期同步发现变更（用户不在这一屏时）

用户在别的页面时配置变了，隧道仍在用旧端口跑，回来看到的是「已连接」——这时**不能只在节点行提示**，会被错过。

- 触发：`node_synced` 的 `node-list-changed` 带 `changed_node_ids`，其中包含**当前连接的节点**，且隧道处于已连接状态。
- 位置：**hero 状态区**。主按钮仍然唯一，文案切为「重新连接」；按钮上方一行说明「配置已变更，请重新连接」。
- 点击：stop → start → 重测。通过后回到正常的已连接态；仍不通则按失败路径处理，**不再二次同步**。
- 若变化的不是当前连接节点：不打扰，只在数据层更新，节点行保持原样。

## 4. 智能修复确认弹窗

380 宽 alertdialog，沿用 QuitDialog 骨架。

```
智能修复这台节点？

节点会重启一次，端口和密码都会变。
正在用它的设备会短暂断开，其它设备需要更新配置后才能继续用。

这台节点在别的设备上用过？先更新配置

                    [ 取消 ]  [ 智能修复 ]
```

- 主按钮 `确认修复` 用 `.btn--danger-ghost`（入口叫「智能修复」，弹窗里问「智能修复这台节点？」，按钮用动词短语回答）；`取消` 为描边次按钮；默认焦点在取消，Esc / 点背景取消。
- 「先更新配置」是正文最后一段里的**文字链**，不占按钮位：点击即同步这台；**若隧道正在运行且运行的就是这台，先 stop → start 再测**（否则测的是旧配置）；重测通过就不再进入修复。连接页与详情页共用同一个处理函数。
- 不给第三个实心按钮，避免一屏三个动作抢焦点。

## 5. 我的服务器 · 服务器详情

保持已有的「智能修复」按钮不变，只把确认弹窗换成上面这个（含「先更新配置」文字链）。

不加「更新配置」按钮：详情页的职责是管理这台机器，同步的是本机配置副本，入口在设置里。

## 6. 设置 › 连接 · 节点配置同步

一行设置，左侧标题、中间周期、右侧动作：

```
节点配置同步        每 30 分钟 · 2 分钟前同步        [立即同步]
                    （5 / 15 / 30 / 60 / 手动）
```

- 位置固定在**设置 › 连接**，与同步线既有实现一致；周期就地修改即保存（与其它设置行一致）。
- 「立即同步」执行一次全量同步；有变化时给一条轻 toast 说明改了几台，无变化不提示。
- **最近同步时间只存在于本会话内存**：重启后显示「尚未同步」，不新增后端字段。
- 这一行是周期与状态的主住处；服务器列表表头的同步图标是**同一动作的快捷入口**（紧凑/抽屉布局下设置不易到达）。两处共用同一个执行入口，不各写一套。

## 7. 状态与文案的住处

| 事实 | 唯一住处 |
|---|---|
| 这台节点正在自动更新配置 | 连接页该行行内 |
| 配置已变更、需要重连 | 连接页该行行内（替换动作行，不与修复入口同时出现） |
| 配置已更新并恢复 | 连接页该行（3 秒）+ 延迟回填 |
| 正在修复 | 连接页该行「正在修复…」/ 详情页按钮态 |
| 修复成功与新端口 | 详情页就地；连接页卡片底部一行 |
| 修复失败原因 | 出现入口的那一屏的卡片底部 |
| 最近同步时间 | 设置 › 连接 的该行（本会话内存态，重启后为「尚未同步」） |
| 全量同步结果 | 设置行的 toast；列表表头的图标只反映进行中/失败 |

## 8. 边界

- 节点不是自有（种子 / 手动导入）时，三个动作都不出现。
- **免费节点（种子）测不通不给任何动作**（2026-11-22 定）：裸的「测不通」文字即可。免费节点本来就不保证可用，界面上已提示过；用户没有恢复手段，问了 AI 也只能得到「换个节点」。手动导入节点仍保留「问 AI」——那是用户自己订阅的，AI 还能帮上忙。
- `untested`、测速中、已到期、悬挂删除：不触发同步、不出现修复。
- 同一时刻只允许一个修复在进行；修复中所有行的两个动作禁用，其它行仍可切换节点。
- 同步与修复并发由 Host 侧的串行锁保证，界面不做第二把锁；界面只负责禁用同一台的两个动作。
- **已知边界**：只改了密码、端口没变（手工改配置）而隧道正在运行时，界面只能比较端口，判断不出「配置变了」，会走自动重测 → 修复入口。此时点修复弹窗里的「先更新配置」即可恢复——该动作会先 stop → start 再测，不需要真的换端口。
- **建机的时间边界**（2026-11-22 定）：正常建机 2–3 分钟。**15 分钟**时界面把进度改判为「安装超时，可以销毁重建」，并把「销毁」提为显眼动作，但不自动销毁；**20 分钟**时控制面兜底销毁未 `active` 的机器（现 `enrollment_expires_at` 为 45 分钟，需收紧）。
- **建机期间不出现任何会触达节点的动作**：`智能修复`、`更新配置` 都不出现（包括禁用态）——此时 agent 是否可用未知。唯一可点的节点相关动作是「销毁」；改名这类纯本地操作照常保留，它不依赖 agent。
