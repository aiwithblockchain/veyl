# 测试节点手动刷新

> 日期：2026-11-06
> 状态：设计定稿，未实现
> 上游：`docs/contracts/commands.md` §8.1–8.2、`docs/design/node-list.md`
> 涉及：`src/components/Settings.tsx`（高级）、`src-tauri/src/seed.rs`、
> `src-tauri/src/tools/net.rs`（`CatalogRefresh`）
>
> **这份文档解决什么**：后端早就有 `default_profile_refresh(force)`，AI 也有 `CatalogRefresh`，
> 但设置页没有手动入口。用户只能等 6 小时的后台刷新，或者去问 AI。

---

## 1. 现状

| 项 | 现状 |
|---|---|
| 后台刷新 | 无缓存 → 启动后立即；有缓存 → 启动 5 分钟后；之后每 6 小时 |
| 强制刷新 | `default_profile_refresh(true)` 跳过 6 小时间隔，仍带 ETag；同一时刻只允许一个请求（`REFRESH_LOCK`） |
| AI | `CatalogRefresh { force? }`、`DefaultProfileStatus`；无需新增工具 |
| 设置页 | 网络 →「默认配置源」只展示版本、节点数、更新时间，没有按钮 |
| 状态接口 | `default_profile_status` 只读不联网：`version` / `node_count` / `applied_at` / `checked_at` |

缺的只是入口与结果反馈，命令本身不用新造。

---

## 2. 入口位置

**放在「设置 → 高级」，紧挨运行库升级下方，并列，不新增 `settings-subhead`。**

理由：两行结构相同（标题 + 版本信息 + 一个按钮），并列本身已经表达「都是资源更新」；
再加一个 subhead 会把现有的运行库、后台组件两行拆成两组，收益为零。

```
运行库         运行库 1.15.0 · 内置 1.14.4        [ 检查更新 ]
测试节点       v3 · 12 个节点 · 3 小时前检查       [ 检查更新 ]
后台组件       正在运行 · 与安装包一致              [ 重启 ]
默认配置源地址  https://…                          [ 问 AI ]
```

**把「网络 → 默认配置源」整行搬到这里并改名「测试节点」，网络页不再保留同名行。**
状态（版本、节点数、上次检查时间）只允许有一个住处；两处都显示，早晚会出现一处忘了更新。
「问 AI」按钮跟着行一起搬。高级里原有的「默认配置源地址」一行顺手改名为「测试节点地址」，
避免同一页出现两个「默认配置源」。

显示内容：

| 字段 | 来源 | 空值 |
|---|---|---|
| 版本 | `version`（仅展示，可能是 null） | 省略，不显示 `vnull` |
| 节点数 | `node_count` | `0` 时显示「还没有节点」 |
| 上次检查 | `checked_at` 的相对时间 | 无缓存时显示「从未检查」 |

示例：`v3 · 12 个节点 · 3 小时前检查`。

行下不写「这是种子/默认节点」——对外只有「测试节点」一个叫法（机制名不出现）。

## 3. 交互与五态

按钮 `检查更新`（ghost），只有这一个动作；**不需要二次确认**：

- 这是只读拉取 + 应用一份资源，不改系统设置、不改当前连接；
- 唯一副作用是节点集可能变化，而「当前节点消失」已单独处理（§5）；
- 加确认只会让用户多点一次，且没说清确认的是什么。

| 状态 | 按钮 | 行内说明 |
|---|---|---|
| **检查中** | `检查中…`，disabled | `正在检查测试节点…` |
| **已是最新** | `检查更新` | `已经是最新（刚刚检查）` |
| **已更新** | `检查更新` | `已更新 3 个节点（共 12 个）`；已连接时追加「下次连接生效」 |
| **离线，保留旧缓存** | `检查更新` | `现在连不上，继续用上次的节点（2 小时前）`，`--warn-text` |
| **内容异常** | `检查更新` | `新内容有问题，已保留原来的节点` + `复制诊断信息` |

- 五态互斥，同时只显示一条。
- 请求在飞时按钮 disabled（后端本来就有单飞锁，前端禁用只是避免用户以为没点上）。
- 离线/异常后按钮不锁死：网络恢复后用户要能直接再点。
- 无缓存且拉取失败（`Offline { cached: false }`）→ 命令返回 `UPSTREAM_ERROR`，按钮恢复，
  行内显示 `拿不到测试节点，请检查网络`，不显示「已是最新」。

## 4. 结果怎么反馈

**行内反馈，不用 toast。**

- 设置页已有行内反馈的用法（诊断信息、导入结果），toast 会变成第二个住处，而且会消失。
- 结果就显示在用户点击的那一行下面，位置和动作在同一处。
- 结果在下次操作或离开页面后清掉；`上次检查` 时间保留在行里。

**「下次连接生效」只在已连接时出现。** 依据 `seed.rs` 的行为：刷新会立即换缓存与节点层，
但正在跑的进程不会热替换配置；断开状态下刷新就是立即生效，多说一句会让人以为还有一步操作。

**当前节点消失**（§5）时的文案单独占一行，不与五态混在一起。

---

## 5. 新版本里当前节点消失

### 5.1 后端行为

`sync_seed_nodes` 会删掉新版本里不存在的种子节点。目标行为：

1. 删除前记录哪些配置的 `current_node_id` 指向被删节点；
2. 删除后，把这些配置的 `current_node_id` 设为**剩下的第一个节点**（没有剩余则为 `null`）；
3. 发 `config-changed`（`reason = "seed_refreshed"`），节点集变化已由 `node-list-changed` 表达。

**为什么不是留 null**：契约 `commands.md:1125` 现在写「置 null，下次连接落到第一个可用节点」。
但节点卡与节点面板都靠 `current_node_id` 画「当前」徽标；置 null 会出现「卡片显示东京 01、
却没有当前标记」的状态，用户无法确认下次会连哪个。设为第一个节点，界面与下次连接一致。

空种子（一个合法节点都没有）已被 `parse_seed` 拒绝，按「内容异常」处理、保留旧缓存，
所以不会出现「一次刷新把所有节点删光」。

### 5.2 文案

| 情况 | 文案 |
|---|---|
| 当前节点仍在 | 不显示 |
| 当前节点消失，有替代 | `原来的「香港 01」已下架，已切换到「东京 02」`；已连接时加「下次连接生效」 |
| 当前节点消失，没有替代 | `原来的「香港 01」已下架，这套配置现在没有节点` |

连接中的会话不受影响：当前连接保持到用户主动断开（与 `commands.md` §8.2 一致）。

## 6. 刷新频率评估

现状是「无缓存立即、有缓存 5 分钟后、之后 6 小时」。用户反馈试用节点「经常变化」。

**建议：把启动后的第一次等待从 5 分钟缩到 30 秒，其余不变（仍每 6 小时）。**

理由：

- 5 分钟是给启动让路，但刷新本来就是后台任务，不阻塞 UI；请求带 ETag，未变化时是 304，
  成本接近一个空响应。真正会被 5 分钟挡住的，是「打开应用用几分钟就关」的短会话——
  这类用户恰恰最需要新节点。
- 不到 30 秒就检查，会和首启引导、首次连接抢网络与日志；30 秒足够让启动稳定。
- 不把 6 小时缩短到 1 小时：试用节点是「几天一变」的量级，不是分钟级；缩短只会让所有客户端
  的请求数乘 6，换来的新鲜度用户感知不到。真有需要，用户手边就有按钮。
- 手动刷新就是「我现在就要」的出口，比调短定时更可控。

如果上线后发现节点确实按小时变，再把间隔降到 2 小时；不要一步到 15 分钟。

## 7. 与 AI 同一口径

同一个命令（`default_profile_refresh(true)`）、同一份结果字段、同一套句子：

| 结果 | 设置页 | AI |
|---|---|---|
| 未变化 | `已经是最新（刚刚检查）` | 「已经是最新」 |
| 有变化 | `已更新 N 个节点（共 M 个）` | 「已更新 N 个节点」 |
| 离线有缓存 | `现在连不上，继续用上次的节点（…）` | 「现在连不上，继续用上次的节点」 |
| 内容异常 | `新内容有问题，已保留原来的节点` | 「新内容有问题，已保留原来的节点」 |
| 无缓存且失败 | `拿不到测试节点，请检查网络` | 「拿不到测试节点，请检查网络」 |

- 不允许出现「测试节点已更新」与「更新了 3 个节点」两种说法；以本表为准。
- 由 AI 触发时，结果写在对话里；设置页只更新状态（版本、节点数、上次检查），
  **不再重复弹一条行内结果**。由设置页触发时反之。同一事实只在一个地方播报。

## 8. 需要补的字段（命令不变）

`default_profile_refresh` 现在返回的是 `DefaultProfileResult` + `source` + `changed`，
但 `source`/`changed` 没有写进契约，且无法区分「离线」与「内容异常」。建议增补：

```ts
type DefaultProfileResult = {
  // ...现有字段
  source: "network" | "cache";          // cache = 本次没拿到远端，用本地
  changed: boolean;                     // 本次是否真的换了内容
  reason: "offline" | "invalid_content" | null;  // 新增：五态里 4/5 的区分
  added: number | null;                 // 新增：新增节点数（拿不到时 null）
  removed: number | null;               // 新增：移除节点数（拿不到时 null）
};
```

- `added` / `removed` 来自 `sync_seed_nodes` 的变更集（删除时判方向）；拿不到就返回 `null`，
  文案退回「已更新，共 M 个节点」。
- 离线且有缓存仍返回 `Ok`（现状），不改成错误：用缓存是正常场景，不是失败。
- 无缓存且失败才返回 `UPSTREAM_ERROR`。
