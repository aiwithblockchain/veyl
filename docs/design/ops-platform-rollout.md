# 运维平台与根证书：分阶段与分工

> 日期：2026-11-27
> 状态：**排期草案，待拍板**
> 相关：`agent/docs/certificates.md`（证书设计）、`agent/docs/agent-health.md`（双钥匙与 get_status）、`admin-console.md`（旧版看板草案，部分已被本文件取代）

## 0. 结论

方案可行。两条轨道互相独立，可以并行；唯一必须先完成的是一件契约，不是代码。

| 轨道 | 内容 | 回答什么问题 |
|---|---|---|
| **A · 证书** | 控制面签叶证书，统一根 | 浏览器访问节点不再逐台点确认 |
| **B · 运维平台** | 双钥匙 + worker + App 直连 agent | agent 现在读得到网卡吗 |

---

## 1. 先纠正一个排期上的误解：根证书不阻塞运维平台

运维端是**原生 App**，它从控制面拿到 `cert_fingerprint`，按指纹固定验证 agent——和现在的桌面端完全一样。所以：

- 运维平台第一版**不需要**根证书；
- 根证书只在「用浏览器直接访问节点」时才需要。

这不是要砍掉证书轨道，而是说明它可以独立排期：早做晚做都不影响运维平台上不上线。两条轨道唯一的交集是都改 agent，所以它们的 agent 改动由同一个会话顺序完成。

|---|---|---|---|---|---|

### 2.1 日历排布

| 时间 | 并行在做 |
|---|---|
| 第 1 天上午 | P0、P1 |
| 第 1 天下午 – 第 3 天 | P2（控制面）∥ P3（agent 双钥匙） |
| 第 3 天 – 第 4.5 天 | P4（worker）∥ P6（agent 证书） |
| 第 4.5 天 – 第 5 天 | P5（验证器）+ 第一次 agent 发版 |
| 第 5 天 – 第 7.5 天 | P7（App）∥ P8 的迁移观察 |
| 第 8 天 | P8 收尾、P9 |

关键路径约 **8 个工作日**；每条交付都要过交叉评审，实际按 10 天排更稳。

### 2.2 发版顺序是硬约束

**控制面必须先于 agent 上线。** 新版 agent 只认 `enroll(csr)` 与 `POST /v1/agent/cert`；反过来先发 agent，撞上没有签发端点的控制面，换证请求是 404、被当成不可重试，冷节点永远不监听，最后由 enrollment TTL 收机器。

同一条约束的另一面：**控制面不能回退到没有 `/v1/agent/cert` 的版本**。已经升级的节点一旦丢了证书就再也换不回来，只能重建。

## 3. 分工与文件边界

一条硬规则：**同一时间一个文件只有一个写者。** 下面按文件划开，会话之间不重叠。

### 会话 A · 控制面签发（P2）

- 新建 `cloudflare/control-plane/src/certs.ts`：读根证书、验 CSR、构造 SAN、签叶证书
- 改 `cloudflare/control-plane/src/servers.ts`：`agentEnroll` 收 CSR；新增 `agentCert`；激活前签叶证书
- 改 `cloudflare/control-plane/src/index.ts`：路由 `POST /v1/agent/cert`
- 改 `cloudflare/control-plane/src/env.d.ts`：`ROOT_CA_KEY_PEM`、`ROOT_CA_CERT_PEM`
- **不需要迁移**：`cert_fingerprint`、`ca_pem` 两列已经存在

### 会话 B · agent（P3 然后 P6，顺序做）

两批都由同一个会话做，原因是都要改 `agent/src/agent.rs`，两个人同时改必冲突。

- 第 1 批（P3）：`auth.rs`、`server.rs`、`agent.rs`
- 第 2 批（P6）：`cert.rs`、`identity.rs`、`control.rs`、`agent.rs`

### 会话 C · 运维 worker（P4、P5）

- 改 `cloudflare/admin/src/index.ts`，必要时拆成 `auth.ts` / `tickets.ts` / `servers.ts`
- 改 `cloudflare/admin/wrangler.jsonc`：新增 `OPS_SIGNING_JWK`、`TOKEN_SIGNING_JWK`、`ADMIN_EMAILS`
- 新建命令行验证器（`scripts/ops/status.*`）：拿票 → 连 `IP:32100/mcp` → `get_status`

登录不用新写一套：App 走产品现有的邮箱验证码登录，拿到的 access token 直接带给 worker；worker 用同一个 `TOKEN_SIGNING_JWK` 自验，再查 `accounts` 表拿邮箱、比对白名单。**不自建第三套登录、不复制验证码逻辑。**

### 会话 D · 运维 App（P7）

- 新建 `client/ops/`（桌面优先，手机端等链路验证完再做）
- 复用 `client/pc` 的 Tauri 壳、登录组件、证书固定逻辑
- 只读：列表、详情、`get_status`

### 会话 E · 评审

Felix 在 P1 契约定稿、以及每一批代码交付后各评一次。按现有规矩：子会话不 commit，我按显式路径提交。

## 4. 三处不能并行

1. **契约没定，四路不许开工。** 否则 enroll 请求体、错误码、票型各写各的，合并时全是返工。
2. **`agent.rs` 只由会话 B 改**，两批顺序执行。
3. **agent 只发一次版。** 双钥匙和 CSR 一起进同一个版本，避免线上同时存在两个半成品版本；P5 的真机验证排在这次发版之后。

## 5. 每阶段的验收

| 阶段 | 验收（可复现的动作） |
|---|---|
| P2 | 真 CSR 签出叶证书，`issuer` 是根、SAN 来自 `servers.ip`；带 `SAN=accounts.google.com` 的 CSR 被拒并写审计 |
| P3 | 业务票能调写工具；运维票只能调 `get_status`；运维票不消费 `jti`；两把公钥配成同一把时编译失败 |
| P4 | 白名单邮箱能拿到 `{ip, port, ticket}`；非白名单邮箱 403；审计有一条签票记录 |
| P5 | 对真节点返回 `metering.consecutive_read_failures == 0` 且 `last_read_at` 是几十秒内 |
| P6 | 冷启动节点 enroll 后叶证书 issuer 是根；断网重启仍能起 TLS；剩余不足 30 天触发续期；issuer 不等于根时重签 |
| P7 | 列表显示全部机器；详情显示 health 与 uptime；「现在查」有真实返回，不可达时显示「不可达」而不是「离线」 |
| P8 | 新节点全部根签发；存量节点在 24 小时内自动重签，没重签的在看板上能看出原因 |

## 6. 风险与回退

| 风险 | 上界 | 回退 |
|---|---|---|
| 根私钥泄露 | 可签任意站点证书（浏览器信任根） | 换根 + 浏览器重装；SAN 白名单把签发面收窄到节点 IP |
| 签发端点被刷 | 只能签自己那台的 IP | server token 鉴权 + 审计 |
| 运维票泄露 | 1 小时内读任意一台状态 | 只读、不消费 jti、到期自失效 |
| 运维 worker 被攻破 | 能签只读票 | 拿不到写权限——能力由钥匙决定，不由 claim 决定 |
| agent 重签时控制面不可达 | 节点暂时起不了 TLS | 不做本地兜底；控制面恢复即恢复 |
| 控制面回退到没有 `/v1/agent/cert` 的版本 | 已升级节点换不了证，冷节点永不监听 | **只能前进不能回退**；回退前先确认没有节点在跑新 agent |
| App 遇到证书重签 | 指纹变化导致 TLS 失败 | 每次从控制面取最新指纹，下一轮自愈 |

## 7. P1 契约要拍板的六条

1. enroll 是否带 CSR；格式定 DER + base64（rcgen 原生输出，Worker 侧不用再转 PEM）。
2. `POST /v1/agent/cert` 的请求体、响应体、错误码，以及续期与重签是否共用这一个端点。
3. 叶证书有效期 2 年、剩余 30 天续期；续期失败每 6 小时重试，不阻塞主循环。
4. agent 是否继续上报 `ca_pem`。**建议不再上报**——根证书归控制面所有，agent 手里没有，控制面直接写 `ca_pem` 即可，少一条可能写错的路径。
5. 运维票的 claims 与行为：有效期 1 小时、`server_id` 必须匹配、不消费 `jti`。
6. 运维 worker 的三个端点（机器清单、签票、健康查询）的路径与返回结构。

---

## 8. 还没定的两件事

- **App 形态**：建议第一版只做桌面端，手机端等 P5 链路验证完再排。手机端多出来的工作是分发（TestFlight / 侧载）和固定证书在 iOS 上的可行路径。
- **运维票的审计落在哪**：worker 自己写一行 `audit_log` 最简单，但会和控制面的审计混在一起。第一版按简单来，字段里带 `source=ops`。

## 9. 证书可见性（运维平台功能）

### 9.1 要回答的问题

- 这台机器的叶证书到哪天？
- 它续期成功了吗？没成功的话，最后一次报什么错？

### 9.2 列表新增一列

| 列 | 内容 |
|---|---|
| 证书到期 | 绝对日期 + 剩余天数，例如 `2028-11-27 · 730 天` |

着色三档：

| 剩余 | 含义 |
|---|---|
| > 30 天 | 正常 |
| ≤ 30 天 | **需要看**——正常节点进入窗口后几小时内就会续上，停在这里说明续期没成功 |
| ≤ 7 天或已过期 | **需要处理**——到期后客户端直接连不上 |

### 9.3 详情

「现在查」调 `get_status`，把 `cert` 块原样显示：

- `not_after`：证书到期日；
- `renewal_failures > 0`：连续续期失败次数，标红；
- `last_renewal_error`：最后一次失败的原文。

`cert: null` 表示这台还在用自签证书（存量节点），显式写「未接入统一根」，不要显示成正常。

### 9.4 数据来源

- **历史/半实时**：D1 `servers.cert_not_after`（unix 秒）。控制面每次签发成功时写入，迁移编号从 `0020` 起。
- **实时**：`get_status` 的 `cert` 块，能连上才有。

**告警依据是「到期日不再前进」，不是「收到失败事件」。** 续期失败时网络往往正是不通的，失败事件送不上来；而到期日停在原处是控制面自己能看见的事实。
