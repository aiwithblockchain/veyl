## 1. 端到端管线

```
模型输出
   │  "以下是……\n```layout\n{...}\n```\n还有什么要调整？"
   ▼
① 流式状态机（Host，逐 delta）        吃掉围栏与 JSON，只发正文
   ▼
② 消息结束（Host，整段复核）          同一个纯函数跑一遍，兜住状态机的 bug
   ▼
③ 校验（Host）                        5 块白名单 + props schema + 安全字符
   ▼                        合法
④ 写库 store::layout::set ─────────── revision + 1
   ▼
⑤ 发 layout-updated ────────────────── UI 按 revision 丢迟到事件
   ▼
⑥ 中间区渲染                           渲染不了的块跳过；一块都渲染不出→本地兜底
```

①②③④⑤ 全在 Host 的 `claurst_session` 里，**前端只做 ⑥**。这样换任何前端都不会再漏。

## 2. 传输格式

### 2.1 为什么仍然要求围栏（哪怕 Host 也认裸的）

围栏不是唯一能识别的方式（§2.4 说明怎么认裸的），但它是**唯一能表达意图**的方式：
`layout` 说明「这是给机器看的」，`json` 说明「这是给人看的代码」，裸 JSON 什么都不说。

围栏给了三件事：

1. **边界明确**——起止是两个独立标记，流式时不用等整段就能判定「这里开始了」。
2. **意图明确**——同样形状的 JSON，加 `layout` 就是布局，加 `json` 就是给人看的代码。
3. **可以计数**——「一条消息最多一份」在传输层可校验，而不是靠模型自觉。

裸 JSON 只能靠形状识别（§2.4），天生比围栏粗：行首一个 `{"version": 1, ...}` 就会被当成布局，
哪怕模型本来只想给用户看一段示例。所以提示词仍然要求围栏——**让模型说清意图，
Host 的兜底才有机会用不上**。

### 2.2 格式定义

````
```layout
{ "version": 1, "blocks": [ { "type": "empty_hint" } ] }
```
````

- 语言标记必须是 `layout`（小写；比较时忽略大小写与首尾空白）。
- 围栏必须在**行首**（允许 ≤3 个空格缩进），行尾不能有其他内容。
- 一条助手消息**最多一份**；多份时只认最后一份（§7）。
- 围栏之外**不应该**出现任何 JSON，提示词里要这么要求；但模型不会总是守规矩，
  所以 Host 另有一条按形状识别的安全网（§2.4）。提示词负责让输出可预期，安全网负责用户永远看不到 JSON。

### 2.3 提示词怎么改

`first-run.md:36-39` 那一段整段替换为（可直接粘贴）：

````
- 布局只在变化时输出，用 `layout` 围栏包起来，**一条回复最多一份**：
  ```layout
  { "version": 1, "blocks": [ { "type": "empty_hint" } ] }
  ```
- 围栏之外不要再出现任何 JSON。布局没变就不要输出围栏。
- **不要直接在正文里写 JSON**，一句都不要——包括「布局长这样」这种举例。
- 块里只写 `type` 和 `props`；`props` 里只有 `reachability` 的 `targets` 由你填。
````

**这条提示词的实际收益：把裸发的概率压低，压不到零。** 真机证据说明模型会无视格式要求
（它甚至在提示词明确给了 ```json 围栏的情况下按自己的习惯发）。所以：

- 提示词负责让**正常情况**可预期，不承担兜底职责；
- §2.4 的安全网负责**用户永远看不到 JSON**，它不依赖模型配合；
- 两者的分界就是 §7.4 的两个计数——计数只用来判断提示词有没有用，不用来决定要不要拦。

给「不要裸发」补一句是廉价的，但**不要因为加了它就把 §2.4 删掉**。

提示词之外，`mod.rs:41-49` 的 `BLOCK_CATALOG` 也要改两处（见 §4.1）：标题的「六种块」变「五种」，
表里删掉 `issue_card`，并在表后加一句「故障卡由系统叠加，你不能写」。

### 2.4 候选的三种来源与「形状」判定

**真机证据**：模型会把布局以**裸 JSON** 直接写在正文中间，前后各空一行：

```
已经连上了，用的是你现有的配置「首次配置」……出口已经通了。

{ "version": 1, "blocks": [ { "type": "proxy_card" } ] }

需要换线路的话告诉我。
```

所以「模型会守规矩用围栏」这个前提是错的。规则改为**按形状识别，不按围栏识别**。

#### 2.4.1 三种候选

| 来源 | 何时成为候选 |
|---|---|
| `layout` 围栏 | 行首三个反引号，语言标记是 `layout` |
| `json` / 无标记围栏 | 行首三个反引号，语言标记是 `json` 或空 |
| **裸 JSON** | **行首**（允许前导空白）第一个非空白字符是 `{` |

裸候选到与它配对的 `}` 为止——按 JSON 的字符串与转义规则配对，**不是简单数括号**
（`{"a":"}"}` 必须一次就配平）。

**只认行首。** 嵌在句子中间的 `{`（`把 {"version":1} 发给我`）不算候选，原样输出——
否则用户自己在讨论 JSON 时，我们会吃掉他的正文。这是本条规则唯一的保守之处，也是它的价值。

#### 2.4.2 分类：显式声明不看形状，其余按形状兜底

**布局形状** = 一个 JSON 对象，同时有 `version` 键与 `blocks` 键。

| 候选来源 | 怎么分类 | 结果 |
|---|---|---|
| **`layout` 围栏** | **不看形状**，一律当布局 | **永远不显示**。解析失败 → 记 `bad_json`；解析成功但校验不过 → 记原因码；合法 → 写库。未闭合也整段丢弃 |
| `json` / 无标记围栏 / 行首裸 JSON | 有布局形状 | **永远不显示**，再走 §4 校验：合法 → 写库；非法 → 丢弃 + 记原因码 |
| `json` / 无标记围栏 / 行首裸 JSON | 没有布局形状 | 当作普通内容，原样输出 |

两条规则合起来一句话：

> **标了 `layout` 的东西永远不进正文；没标的，长得像布局也不进正文。**

**为什么对 `layout` 更严。** `layout` 是模型的显式声明——它已经说了「这是给机器看的布局」，
Host 就不该再用形状去二次猜测。否则模型写坏一个逗号，用户会看到一个标着 `layout` 的代码块里
全是半截 JSON：既不完整，也没有任何用处。声明了就要负责到底。

而 `json` / 无标记 / 裸 JSON 没有声明意图，只能靠形状兜底：形状像就吞，不像就当普通内容——
用户自己贴的配置片段、AI 举的 JSON 例子都落在这一类里。

形状判定**不校验类型**：`"blocks": "oops"` 这种明显想写布局却写错的，也要吞掉。
宽一点是故意的——漏出去才是事故，多吞一段 JSON 只是把一个已经不该显示的片段藏掉了。

这条同时取代了原来「`json` 围栏非法就原样显示」的规则。旧规则留着这个隐患：
模型写错一个块名，用户就会看到整段 JSON。

#### 2.4.3 什么时候决定

`layout` 围栏在**打开的那一刻**就决定（看语言标记，不看内容）；`json` / 无标记围栏与裸 JSON
要等到闭合才分类。无论哪一种，正文里都不会先出现再消失——**没有闪烁**（§3.4 的测试覆盖）。

## 3. 流式过滤

### 3.1 为什么在 Host，而不是前端渲染层

- 前端有三个消费者（流式消息、`final_text`、历史消息），每个都要实现一遍，漏一个就漏。
- 历史是从数据库读的，前端过滤改不了已经写进去的东西；必须在**写库之前**过滤。
- 将来的其他前端（移动端、Web）不该各写一遍这个状态机。

### 3.2 状态机

逐字符消费，五个状态：

| 状态 | 收到什么 | 做什么 |
|---|---|---|
| `Prose` | 普通字符 | 发出去 |
| `Prose`（行首） | 行首可能是三个反引号或 `{` | **持有**到能判定为止 |
| `Fence` | 围栏已经打开 | 按候选类型累积或直通 |
| `Bare` | 行首 `{` 开始的裸对象 | 累积到配对的 `}` 或上限 |
| `End` | 流结束 | 冲刷持有区、判定未闭合的候选 |

判定细则：

- **只有行首才判定候选。** 行内的反引号与 `{` 原样输出，不进入任何候选状态——
  这一条同时挡住「模型在正文里提到围栏语法」与「用户自己在讨论 JSON」两种误判。
- 行首先跳前导空白，再看第一个非空白字符：反引号 → 围栏判定；`{` → 裸候选；其他 → 放行。
  **空白与候选同进同出**：吞掉候选时它前面的空白一起吞掉，放行时一起放行，否则会留一个空行。
- 行首持有区：最多持有 3 个反引号等待第 4 个字符。第 4 个字符不是反引号、或来了换行 →
  不是围栏，把持有的字符发出去。**持有上限 3 个字符，不影响打字观感**
  （普通 token 没有行首反引号，立即发出）。
- 围栏语言标记在**同一行**判定：整行 trim 后 `== "layout"` → 布局候选；
  `== "json"` 或空 → 兼容候选；其他 → 普通代码块，直通。
- 候选围栏体内**一个字符都不发**，累积到闭合。
- 候选围栏体超过 **64 KiB** → 放弃候选，改为普通代码块（防止模型吐一个巨大 JSON 把内存吃住），
  已累积的部分补发出去。
- 闭合行 = 整行 trim 后是 3 个及以上反引号、且后面没有内容。
- 裸候选按 JSON 规则配对括号（识别字符串与转义），**不是简单计数**；超过 **8 KiB** 未闭合 →
  放弃候选，原样放行并记 `layout.bare_too_large`。8 KiB 的依据：合法布局最多 8 块、每块 props 只有一个
  短列表，正常不到 1 KiB。

### 3.3 四种情况

**(a) 半截围栏**（如消息只写出两个反引号就结束）

留在持有区，流结束时冲刷出去。两个反引号不构成围栏，**按正文显示**。
这是对的：模型没说完，用户看到的就是他打的字。

**(b) 未闭合的布局围栏**（开了 `layout` 围栏，没有闭合就结束）

流结束时把累积体当作**候选**处理：

- 校验通过 → 当作布局，吞掉（模型常常忘记收尾）。
- 校验不通过 → **整块丢弃**，不显示半截 JSON，记日志 `layout.unclosed_invalid`。

即：**未闭合的 JSON 永远不会出现在正文里**，无论它合不合法。

**(c) JSON 在正文中间**

````
好的，我把代理卡放到第一位。            ← 正常发
```layout
{ ... }                                  ← 吞掉，不发
```
还需要我调整顺序吗？                     ← 正常发
````

围栏两侧的正文照常流入，中间只是「没有新字符」。用户看到的是消息在布局处停顿一下，
不会看到回退或删除——**没有闪烁**。

**(d) 裸 JSON**（行首 `{` 开始，没有围栏）

真机上的主要形态（§2.4）。处理与围栏一致：

- 行首 `{` → 进入 `Bare`，**一个字符都不发**，直到配对闭合。
- 闭合后按形状判定：是布局形状 → 吞掉（合法写库，非法丢弃并记原因码）；不是 → 连同它前面的空白整段放行。
- 流结束时仍未闭合 → 同 (b)：能解析就用，不能解析就整段丢弃（`layout.bare_unclosed`），**不补发半截**。
- 超过 8 KiB 仍未闭合 → 放弃候选，原样放行。

**代价**：以 `{` 开头的段落要等到闭合才显示，用户在这一小段时间内看到的是「消息停了一下」。
正常布局不到 1 KiB，在本地网络里延迟在毫秒级；真遇上巨型 JSON，8 KiB 上限兜底。
这个代价换的是「用户永远看不到 JSON」，值得——这正是本次要修的问题。

### 3.4 两个实现，必须同源

实现两份，但只有一份规则：

| 用途 | 函数 | 形状 |
|---|---|---|
| 流式 | `filter.push(delta) -> String` | 有状态，逐 delta |
| 正文 / 历史 / 未闭合复核 | `strip(text) -> (String, Option<Layout>)` | 纯函数，整段 |

**性质测试（唯一的正确性断言）**：把同一段文本按**每一个字节位置**切成任意两段或多段喂给
`filter.push`，拼接结果必须等于 `strip` 的正文部分，且提取出的布局相等。
这一条同时证明了「流式不会漏字」「流式不会多字」「两条路径不会分叉」。

正文过滤（`final_text`）与历史过滤（`persist_committed_message`）都用 `strip`，
所以历史里不会再出现布局 JSON。

### 3.5 三个出口

| 出口 | 改法 |
|---|---|
| `mod.rs:295` `message_chunk(text)` | 发 `filter.push(text)` 的返回值（可能为空串 → **空串不要发事件**） |
| `mod.rs:419` `final_text` | 发 `strip(raw).0` |
| `mod.rs:606` `persist_committed_message` | 写 `strip(text).0` |

`filter` 每个请求一个，放在 consumer 里，和 `final_text` 同生命周期。

## 4. 校验

校验在 Host，写库之前，**一次性、原子**。

### 4.1 块白名单：AI 能写 5 块

`center-panel.md` §2.5 列了 6 块，但 `issue_card` 是**叠加渲染**、不进布局
（`data-model.md` §3.4、`events.md` §4.12）。所以：

| 块 | AI 可写 | 说明 |
|---|---|---|
| `empty_hint` | ✅ | |
| `proxy_card` | ✅ | |
| `source_choice` | ✅ | |
| `reachability` | ✅ | 唯一带 props 的块 |
| `update_hint` | ✅ | |
| `issue_card` | ❌ | 系统叠加。写进布局会导致故障卡渲染两次，出现即整份非法 |

`BLOCK_CATALOG` 与提示词里的「六种块」同步改成五种，并注明故障卡不可写。

### 4.2 每块 props schema

顶层只允许两个键：`version`、`blocks`。块只允许两个键：`type`、`props`。
**多一个键就是非法**（不允许模型塞 `style`、`id`、`hidden`）。

| 块 | props | 规则 |
|---|---|---|
| `empty_hint` | 无 | 必须缺省或 `{}` |
| `proxy_card` | 无 | 同上 |
| `source_choice` | 无 | 同上 |
| `update_hint` | 无 | 同上 |
| `reachability` | `{ "targets": string[] }` | 1–6 项；每项 trim 后 1–24 字符；去重；见 §4.3 字符规则 |

其他约束：

- `version` 必须是数字 `1`（不是字符串 `"1"`）。
- `blocks` 必须是数组，长度 0–8。**`[]` 合法**（§6.2）。
- 同一块类型**最多出现一次**（重复 → 整份非法）。块的外观固定，同型重复没有意义，
  却会让渲染顺序有歧义。
- 未知块类型 → 整份非法。**不做「过滤掉未知块」**（§4.4）。

### 4.2.1 与当前配置的兼容（语义校验）

结构合法不等于有意义。写入时还要用**那一刻的配置**过一遍：

| 块 | 要求 | 不满足 |
|---|---|---|
| `proxy_card` | `connect_mode = "system_proxy"` | 整份丢弃 |
| `source_choice` | `nodes` 为空 | 整份丢弃 |
| 其余三块 | 无 | — |

只有两条，因为每多一条语义规则，就多一个「把好布局扔掉」的理由。这两条属于**明确不可能成立**：
TUN 模式下没有本机代理端口，`proxy_card` 只能渲染出一张地址为空的卡，等于告诉用户一个假的事实；
已经有节点时再让用户「用测试节点还是用自己的」，是在要求他重做已经做完的事。

**这条只在写入时生效。** 配置后来变了（用户从本机代理切到 TUN），已落库的布局不做回溯校验——
渲染时按 §6.3 跳过不适用的块，**不整份丢弃**。否则用户只是换了个接管方式，中间区就整体消失，
而他并没有让 AI 改任何东西。

### 4.3 「数值必须来自工具结果」怎么保证

不是"校验模型写的端口对不对"，而是**布局里根本没有数值**：

| 事实 | 住处 | 谁能改 |
|---|---|---|
| 端口、地址 | `runtime.mixed_port` / `config.listen_port`，渲染时读 | 运行时 |
| 版本号 | `default_profile_status` / `core_upgrade_status`，渲染时读 | 后端 |
| 问题文案 | 问题管理模块，渲染时读 | 后端 |
| 节点、延迟 | 节点卡，不在布局里 | 后端 |

`proxy_card`、`update_hint`、`issue_card` 的 props **都是空的**，就是因为它们的内容全部来自
运行时事实。模型只决定「放哪些块、按什么顺序」，**不决定任何一个数字**。

唯一由模型填的是 `reachability.targets`——它是**服务名**，不是数值，也不是地址。
字符规则：

- 拒绝：任何控制字符、换行、`<` `>` `&` `"` `'`、`://`、以 `javascript:` / `data:` 开头。
- 拒绝：看起来像地址的（含 `/` 或 `:`）。
- 理由：`targets` 是唯一原样进到界面的模型字符串，必须限制成「一个短名字」。

### 4.4 非法布局：整份丢弃

PM 的裁决，这里把它写成规则：

- **整份丢弃**，不写库、不发事件、保留旧布局、记 `warn` 日志（含原因码，不含整份内容）。
- **不逐块过滤**。逐块过滤会让中间区呈现一个「模型没打算要的构成」——
  比如把 `issue_card` 滤掉，用户就少了自救入口，而这种缺失没有任何提示。
- **非法 ≠ 显示。** 标了 `layout` 的、以及形状像布局的候选，都只进校验、不出现在正文里（§2.4.2）。
  校验决定的是「写不写库」，不是「给不给用户看」。

三处契约的说法已经在 2026-11-06 对齐成整份丢弃（`events.md` §4.13、`data-model.md` §3.4、
`center-panel.md` §2.5 与 §3），§11.2 有清单。

原因码（日志用，不出现在界面）：`bad_json`、`bad_version`、`unknown_block`、`duplicate_block`、
`bad_props`、`too_many_blocks`、`unsafe_string`、`block_not_applicable`（§4.2.1）。

### 4.5 「首次就非法」时中间区长什么样

没有旧布局可保留，`layout` 仍是 `null` → **走本地兜底**（`middleArea.ts`）。

用户看到的就是他现在看到的那套：未连接一句话、失败卡、代理卡。**没有错误提示，没有重试按钮。**
编排失败是产品内部的事，不该变成用户的任务。

第二次成功时正常写入；用户不会感觉到第一次失败过。

## 5. 持久化与事件

### 5.1 写入时机：一次请求，结束时写一次

不在围栏闭合时写。理由：

- 一条请求里模型可能先写一份布局、调工具、再写一份修正版。围栏闭合时就写会产生
  revision +1、+2 两次写入，中间那一版还会被推给 UI。
- 流可能被取消。写到一半的布局不应该落库。
- 一次请求一次写入，revision 的语义才干净：**一个用户回合 = 至多一次布局变更**。

规则：

| 请求结果 | 是否写 |
|---|---|
| `success` / 输出达到长度上限 | 写（若提取得出合法布局） |
| `cancelled` | **不写**。用户按了停止，半成品的编排不该生效 |
| `error` / panic / 预算超限 | **不写** |

写入顺序：先 `request_end`，再 `layout-updated`。让对话先收尾，中间区再变，
否则用户会看到中间区在文字还没说完时就换了。

### 5.2 归属配置与 revision

- **归属配置按「开始时优先、中途被激活则跟随结束」判定**（`configs::active(conn)` 各取一次）：

  | 情况 | 归属 |
  |---|---|
  | 开始时已有活动配置，中途没有配置被激活 | 开始时的那个 |
  | 开始时没有活动配置（首启），或请求中有配置被激活（AI 新建并激活） | 请求结束时的活动配置 |
  | 请求结束时仍没有活动配置 | **不写库、不发事件** |

- **为什么不能只用开始时的快照**：首启时 kickoff 发生在配置还不存在的时刻，
  按「开始时」判定会让这一轮布局整段跳过，`source_choice` 永远不出现；
  反过来，已有配置时 AI 新建并激活一套，只按开始时的快照就会把布局写进刚被替换掉的旧配置。
  所以判定看的是「请求结束时谁是活动的」，开始时只是它的默认值。
- `store::layout::set` 已经返回新 revision（`layout.rs:28`），直接用它。
- **内容相同不写**：与库里现有布局做结构比较（键序无关），相同则既不写也不发事件。
  避免「模型每轮都复述一遍布局」把 revision 推高、让 UI 无谓重渲染。

### 5.3 事件载荷

沿用 `events.md` §4.13，不新增字段：

```ts
type LayoutUpdatedPayload = {
  contract_version: string;
  config_id: string;    // 按 §5.2 判定的归属配置
  revision: number;     // store::layout::set 的返回值
  layout: Layout;
  emitted_at: string;
};
```

### 5.4 UI 消费与迟到丢弃

现在没有消费者（`chatStore.ts:547` 明确丢弃，交给"各自的视图"，但那个视图不存在）。
**消费者是 `useVpnSession`**（`src/config/useVpnSession.ts`），它已经持有 `activeConfig`：

```
layout-updated:
  config_id !== 当前激活配置      → 丢弃
  revision <= activeConfig.layout_revision → 丢弃
  否则                           → activeConfig.layout = layout;
                                    activeConfig.layout_revision = revision
```

- **不重新拉 `config_detail`**：事件已经带全内容，多一次 IPC 只换来一次闪烁。
- 切换配置时 `config_detail` 带回 `layout` 与 `layout_revision`，状态随之重置；
  上一个配置的迟到事件被 `config_id` 挡住。
- **`ConfigDetail` 必须补 `layout_revision`**（现在只有 `layout`，`services.rs:2232` 没带 revision）：
  否则同配置内「事件后到」无法判断，用户会看到中间区闪回上一版。

### 5.5 与 `config-changed` 的关系

`layout-updated` **不触发** `config-changed`：布局不是配置数据，不影响连接、不影响导出。
反过来 `config-changed` 会触发 `config_detail` 重拉，`layout` 与 revision 一起回来，无需额外处理。

## 6. 与本地兜底的关系

### 6.1 三态

| `config.layout` | 中间区 |
|---|---|
| `null` | **本地兜底**（`middleArea.ts`，规则见 `middle-area-local-rules.md`） |
| 有行且 `blocks: []` | **空白**。AI 明确选择了「什么都不放」，不显示"暂无内容"，不回落 |
| 有行且 `blocks` 非空 | 按布局渲染 |

这三条已经在 `data-model.md` §3.4 与 `middle-area-local-rules.md:24-25` 写死，本设计不改。

### 6.2 `[]` 与 `null` 必须分开

- `null` = 不知道怎么排，让系统猜。**可以随时被本地规则接住**。
- `[]` = 我就要空的。**本地规则不许覆盖**，否则用户的空白被"好心"填满。

模型写 `blocks: []` 是一个合法且有用的表达（比如用户说「中间别放东西」）。

### 6.3 渲染器不认识、或当前配置用不上的块

出现版本错位（Host 的词汇表比 UI 新）或配置变了（写入后用户换了接管方式）时会碰上：

- 渲染器不认识的块 → **跳过**，不发「未知块」提示。
- 当前配置下不适用的块（如已切到 TUN 之后的 `proxy_card`）→ 同样**跳过**（§4.2.1）。
- **一块都渲染不出来，且 `blocks` 非空** → 退回本地兜底（等价于 `null`）。
- `blocks: []` 不受此规则影响（§6.2）。

跳过只发生在渲染时，不改库、不发事件、不消耗 revision——否则切换一次接管方式，
用户的布局就被系统"修正"了一次，他并没有让 AI 改任何东西。

这条同时解决了眼下的过渡：**5 个块的渲染器都还没实现**，管线先上，
中间区按旧规则继续工作，不会变空也不会报错；渲染器落地后自然接管。

### 6.4 故障卡永远是叠加层

`issue_card` 不进布局、不受 revision 影响、不因为 AI 改了布局而消失。
本地能插、AI 挂了也能插——这是「网断了也能自救」的保证（`center-panel.md` §2.5）。

## 7. 多份、跨消息、中断

### 7.1 一条消息两份

**最后一份合法布局生效**，前面所有布局围栏都被吞掉（无论合法与否）。

- 合法 + 合法 → 用后者。模型在自我修正，后一份是它的最终意思。
- 合法 + 非法 → 用前者（后者被丢弃，不覆盖）。这时日志里同时有 `layout.ok` 与原因码。
- 非法 + 非法 → 不写（可能保留旧布局）。
- 两条都进不了正文——**除了最后生效的那份，其余全部吞掉**。

### 7.2 跨消息

一条消息 = 一个 assistant turn。跨 turn 的两份（turn 1 一份、turn 3 一份，中间夹着工具调用）
按**请求**计：整个请求只写一次，取最后一份合法的。理由同 §5.1。

新请求（用户又发了一条）是新一轮：重新取一次，正常情况下模型**不该**输出布局
（提示词要求「只在变化时输出」）；输出了就按新布局处理，内容相同则不写（§5.2）。

### 7.3 流中断

| 情况 | 行为 |
|---|---|
| 用户取消 | 不写（§5.1）。已吞掉的 JSON 不会补发 |
| 网络错误 / panic | 不写。已发出去的正文保持已发出的样子 |
| 应用退出 | 不写。没有"恢复上次未完成的布局"这回事 |

### 7.4 裸 JSON 的统计

原来说「正文里的裸 JSON 只计数、不处理」，真机上模型就这么干（§2.4），所以已经改成按形状识别。
计数保留，但**只用于判断提示词有没有收住，不再决定行为**：

| 指标 | 含义 | 怎么用 |
|---|---|---|
| `layout.bare_ok` | 裸 JSON 被识别成合法布局 | 说明提示词那句没被遵守。持续 >1% → 提示词那句没用，安全网必须长期保留 |
| `layout.bare_invalid` | 形状是、内容非法 | 同上；同时说明校验在挡事 |

**不能因为计数变低就删掉安全网**——删掉的那天模型又开始裸发，用户又开始看到 JSON。
提示词降低概率，安全网兜住剩下的。

## 8. 安全边界

| 面 | 规则 |
|---|---|
| 结构 | 顶层只 `version` + `blocks`；块只 `type` + `props`；多键即非法。**没有可以放 HTML、样式、脚本、URL 的字段** |
| 字符串 | 只有 `reachability.targets` 一个自由文本字段；拒绝 `<> & " '`、控制字符、`://`、`javascript:`、`data:`、含 `/` 或 `:` 的串 |
| 长度 | 单个 target ≤24 字符；`targets` ≤6 项；`blocks` ≤8；围栏体 ≤64 KiB；**裸候选 ≤8 KiB** |
| 数值 | 布局不携带端口、地址、版本、节点、延迟（§4.3）——模型写不进来 |
| 渲染 | 渲染器只接受**类型化的 props**，不把 `props` 展开到 DOM 属性上；禁止 `dangerouslySetInnerHTML` |
| 注入 | 布局只能来自模型输出。用户正文里的"布局"是纯文本，不经过解析器 |
| 日志 | 记原因码与块类型，**不记整份布局内容**（可能含用户说过的服务名） |

## 10. 不做的事

- 不做**正文级**的 JSON 恢复（比如从一段话中间挖出 JSON）。判定只认**行首**（§2.4.1）——
  行内的 `{` 一律放行。裸 JSON 在行首时会被拦，这一点已经覆盖真机形态。
- 不逐块过滤非法块（§4.4）。
- 不让 AI 写 `issue_card`（§4.1）。
- 不在围栏闭合时写库（§5.1）。
- 不为布局新增 AI 工具：布局是每一轮的输出，不是一次调用。
- 不做布局的撤销 / 版本历史（revision 只用于丢弃迟到事件，不对外暴露旧版本）。
- 不做"重新生成布局"按钮：说一句「重新排一下」就行。

## 12. 验收口径

管线算「通」，要同时满足：

1. 一轮对话里模型照抄提示词示例，用户正文里**看不到任何 JSON**。
2. 模型吐一个坏块，中间区**不闪、不报错、不变**。
