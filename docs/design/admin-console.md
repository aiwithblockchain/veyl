# admin.dessage.xyz：agent 管理后台（草案）

> 日期：2026-11-26
> 状态：**草案，待逐条讨论**。只写结构与边界，不下最终结论。
> 相关：`agent-metering-failures.md`（失败类型清单）、`provider-gone.md`（DO 404 检测）

---

## 0. 一句话

一个只有管理员能进的看板 + 三个关键动作，专门回答一个问题：**这台机器上的 agent 和 sing-box，现在到底是什么状态。**

---

## 1. 为什么需要它

节点侧的自我保护只能覆盖「agent 还活着」的情况：

| 情况 | 本地能自救吗 |
|---|---|
| nft 废了、上报失败，agent 在跑 | 能——agent 自己按阈值停 sing-box |
| agent 挂了，sing-box 还在跑 | **不能**——没有任何进程能把 sing-box 停下来 |
| 机器在 DO 后台被删 | **不能**——本地已经没有进程了 |

控制面这边只能看到「上报沉默」，而沉默有三种完全不同的原因（nft 废了 / 网络断了 / agent 挂了），光看 D1 分不清。今天唯一的兜底是 DO 404 探测，最长 24 小时。

所以需要一个能**主动问**的地方：不是等 agent 上报，而是由管理员点一下、现在就去问。

### 1.1 要覆盖的故障类型（清单见 `agent-metering-failures.md`）

那个文档把节点计量会失败的地方逐条列了出来：本机读计量、本机存进度、上报到控制面（控制面九种返回）。这里只关心一件事——**今天控制面看得见几条**：

| 故障 | 现在控制面看得见吗 | 看板应该显示 | 能远程处理吗 |
|---|---|---|---|
| 本机读计量失败（nft 读不到） | **看不见**（`tick` 在读失败时直接 return，连心跳都不发） | 「上报沉默」+ 新增的读失败计数 | 不能，只能靠 agent 自停 |
| 本机存进度失败 | **看不见** | 上报里的最后保存时间 | 不能 |
| `200` 正常 | 看得见 | 正常 | — |
| `409 server_destroyed` | 看得见（`destroyed_at`） | `destroyed` | 不需要 |
| `401 unknown_token` / `missing_token` | **看不见** | 上报沉默；需要人工查凭据状态 | 可重新下发凭据 |
| `503 unavailable` | 看得见（是控制面自己的状态） | 全站提示，不是单台故障 | — |
| 其它 `5xx` | 只有日志 | 上报沉默 | — |
| 传输层失败（DNS/超时/TLS） | **看不见** | 上报沉默 | 不能 |
| 解码失败 | **看不见** | 上报沉默 | — |
| `400 invalid_body` | 只有日志 | 上报沉默 | — |

结论很直接：**十种里有六种，控制面今天完全看不见**，表现出来都是同一句话——"这台不上报了"。看板要做的第一件事，就是把这六种从"同一句沉默"里拆开，方法是让 agent 把本地健康状态捎带上来（见 §7.1）。

---

## 2. 第一版的范围

只做三件事：

1. 列出全部机器与 agent 的关键状态，一眼看出谁不正常；
2. 单台详情，能看出它属于哪一类故障；
3. 三个动作：**停止服务 / 恢复服务 / 强制标记失联**。

**非目标**：计费调整、日志检索、批量操作、多角色权限、历史曲线。这些都等真的需要再说。

---

## 3. 数据来源：三层，时效完全不同

| 层 | 来源 | 有什么 | 时效 |
|---|---|---|---|
| **历史** | D1 `servers` | state、last_seen_at、paid_until、provider_gone_at、node_port、region、机型 | 随上报更新 |
| **半实时** | agent 上报（新增健康字段） | 连续读失败次数、最后一次错误、sing-box 是否 active、agent 版本与运行时长 | ≤30 分钟（连续失败时每 30 秒） |
| **实时** | 管理员点「现在查」 | 直接调 agent 拿当下状态 | 点一下才查 |

界面必须把这三层**分开显示**，不能混成一个"状态"字。同一个「离线」，可能是五分钟前的上报说离线，也可能是根本没查过。

---

## 4. 认证与部署

- 独立 Worker，路由 `admin.dessage.xyz`，与 `edge` 平级（`cloudflare/admin/`）。
- HTTP Basic；用户名与密码来自环境变量（`ADMIN_USER` / `ADMIN_PASS`，用 `wrangler secret put` 写入），不落库、不写代码。
- 只走 HTTPS；不做注册、不做找回、不做"记住我"。
- 所有写动作（停服 / 恢复 / 标记失联）写 `audit_log`：谁、什么时候、对哪台、结果。
- 可选第二道：再套 Cloudflare Access，把 Basic 当兜底手段，而不是唯一手段。

## 5. 页面

### 5.1 列表（一屏看完所有机器）

一行一台，**正常 / 需要看 / 需要处理** 三档着色：

| 列 | 说明 |
|---|---|
| 名称 · server_id | |
| 地区 · 机型 | |
| 控制面状态 | `active` / `destroyed` / `provider_gone` |
| agent 最后上报 | 相对时间；>35 分钟标黄，>2 小时标红 |
| 计量 | `ok` / `读失败 N 次` / `从未成功` |
| sing-box | `active` / `inactive` / `unknown` |
| 端口 | `node_port`（对外服务端口）、`32100`（agent 控制端口） |
| 账 | `paid_until` |

### 5.2 详情

四块，从上到下：

1. **身份**：server_id、provider_id、IP、地区、机型、创建时间；
2. **账**：paid_until、billing_state、本月已用 / 已释放、是否有未结的超支；
3. **健康**：agent 版本与运行时长、最后一次成功上报、连续读失败次数与最后错误、sing-box 是否 active、agent 控制端口是否可达；
4. **动作**：停止服务 / 恢复服务 / 强制标记失联（都要二次确认，并显示将产生什么后果）。

### 5.3 「现在查」的返回

点一次，直接问 agent，拿回来的东西至少要有：`singbox_active`、`metering_state`（ok / broken）、`last_read_error`、`uptime`、`singbox_version`。查不到就是不可达，要明确写"不可达"而不是"离线"。

## 6. 命令怎么下发

两条路，第一版选一条：

| 路线 | 做法 | 生效速度 | 前提 |
|---|---|---|---|
| **A. 直连 agent** | 控制面已持有签名私钥，可现签一张一次性票，直接调 `https://<ip>:32100/mcp` | 立即 | agent 活着且端口可达 |
| **B. 写 D1 捎带** | 管理员写一条指令，agent 下次上报时在响应里带回 | ≤30 分钟 | agent 能上报 |

**两条都要求 agent 活着。** agent 死了就只剩「标记失联 + 去 DO 控制台手动停」，这一点要点破，别让管理员以为点了就能停。

建议第一版走 A（立即生效、不新增轮询），B 留作 A 不可达时的兜底。

---

## 7. agent 侧要配合的三件事

1. **上报带健康字段**：连续读失败次数、最后一次错误码、`singbox_active`、运行时长。不新增请求，搭在现有 `/v1/agent/traffic` 上。
2. **本地 dead-man switch**：连续计量失败达到阈值就 `systemctl stop sing-box`。按讨论定的口径——**30 分钟窗口内失败次数达到阈值即停**（每 30 秒读一次，30 分钟 = 60 次）。计数要落盘，agent 重启后继续累计，否则崩溃一次就清零。
3. **新增两个工具**：`stop_service` / `start_service`，供路线 A 调用。

## 8. 对账（DO 发票）

我们只信自己的 nft 计数，这套账**没有任何外部校验**。DO 侧能提供的只有月末发票：

- 周期内 `billing insights` 的夜间账单项只有按时计费的资源费，**不含带宽**；
- 带宽超额是整个周期用量减整池，只能在周期末算出来，因此只出现在发票的 `overages` 里。

所以对账是**月度**动作，做不到实时。

### 8.1 每月做什么

1. 发票出来后，人工把 DO 的 CSV 传进后台（DO 没有可用的发票明细 API）。
2. 后台导出我们这边的月末汇总：按账号列「机器·天 / 已释放 / 已用 / 应扣超支」，再加团队合计。
3. 比对团队口径的带宽超额与发票 `overages.amount`，算差额与系数 `k = 发票 ÷ 我们的数`。
4. 结果只做两件事：判断偏差是否在容忍范围内；校准下个月的保守系数与告警阈值。**不改用户记录，不改已扣的钱。**

### 8.2 口径（沿用 `traffic-billing.md` §9 与 §11.8）

- 只对**整月用量确实超过机型月额度**的账号比对，未超额的不参与。
- 被即时扣费、但月末整月净额为零的部分不计入偏差——这是口径差异，不是错误。
- 容忍度：差额在 **5%** 以内。
- DO 发票是整个团队一个数，我们的数据按 Veyl 账号分，所以对账只能在**团队合计**这一层做，不能逐账号对。

### 8.3 页面上要有

- 本月发票金额、我们的估算金额、差额、系数 `k`；
- 至少最近 3 个月的历史，看趋势；
- 偏差超过 5% 时醒目提示。

### 8.4 它回答的问题

「我们算出来的超支，和 DO 实际收的钱，差多少」——这个差额长期偏高，说明我们的计量在系统性少收；长期偏低，说明我们在多收用户。两种都需要人来判断，不自动改任何数。

## 9. 分阶段

| 阶段 | 内容 | 依赖 |
|---|---|---|
| **P0** | 只读看板：列表 + 详情，数据来自 D1 与上报字段 | agent 上报加字段、迁移加列 |
| **P1** | 三个动作，走路线 A | agent 加两个工具 |
| **P2** | 月度对账：上传 DO 发票、月末汇总、差额与系数 | 发票 CSV 格式确认 |
| **P3** | 沉默告警：超过 N 分钟没有上报就通知管理员 | 通知渠道待定 |

## 10. 待逐条讨论

- **Q1** 认证用 HTTP Basic 够不够？要不要一开始就套 Cloudflare Access？
- **Q2** 命令走 A、走 B，还是两条都做？
- **Q3** 健康字段放 `servers` 增列，还是单开一张 `agent_health` 表？后者不污染主表，但要多一次关联。
- **Q4** 「计量废了」要不要**自动**停服，还是只报警、由管理员点？自动停的风险是误判就断服务。
- **Q5** agent 控制端口 32100 现在绑 `0.0.0.0`，对所有公网开放；要不要限制来源，或改成只在有票时才接受连接？
- **Q6** 停服之后怎么防止它被别的机制拉起来（systemd `Restart=`、agent 自己的巡检）？
- **Q7** 「强制标记失联」和现在的 `provider_gone_at` 是同一个字段，还是另开一个"人工判定"的来源区分？
- **Q8** 对账用的发票 CSV：字段与格式先按第一张真实发票写死解析，还是要能容忍列变化？谁来上传、多久上传一次？
