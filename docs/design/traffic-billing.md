## 0. 一句话

机器照旧按天扣费；流量改成 **额度按天释放 + 超出按 GB 从余额扣**。额度由节点上的 agent 用 nft 计数器实时统计并上报，不依赖 DO 的 T+1 账单，也不依赖 sing-box 的内部计数。

---

## 1. 要解决的问题

现状：目录里卖 `transfer_gib`（500 / 1000 / 2000），但契约 2.32.0 明确「不新增已用字段」——**没有任何计量，也没有任何执行**。用户可以在几分钟内烧掉整月额度，超额成本全部由平台承担。

一个真实量级：500 GB 机型跑 25 分钟用掉 100 GB。

| 项 | 金额 |
|---|---|
| 机器费（25 分钟） | $0.0025 |
| 我们拿到 DO 的免费额度（按秒累计） | 0.31 GiB |
| DO 向我们收的流量费 | (100 − 0.31) × $0.01 ≈ **$1.00** |

亏损起点在第 5 秒左右：用户一旦超过这台机器到那一刻为止攒出来的额度，之后每一 GB 都是平台倒贴。

## 2. DO 侧的计费口径（已核实）

| # | 结论 | 依据（文档原文要点） |
|---|---|---|
| 1 | 只计**公网接口出站**；入站免费；VPC 私网流量不计 | "Inbound transfer to Droplets is free… Any data transfer sent by a Droplet using a public network interface counts against the transfer pool" |
| 2 | 额度与用量在**团队账户级池化**，不跨月结转 | "pooled cumulatively across all Droplets at the team level" |
| 3 | 额度**按存在秒数**累计：每秒 `机型额度 / 2,419,200` | "For every second a bundled-plan Droplet exists, it accrues 1/2,419,200 of its total transfer allowance" |
| 4 | 单台每计费周期最多累计 28 天（672 小时） | "up to a maximum of 2,419,200 seconds (28 days) per monthly billing cycle" |
| 5 | 超额 **$0.01/GiB**，不分区、不分机型 | 文档原文 |
| 6 | 销毁后**停止累计**，已用流量**不清零** | 累计按"存在"计算；用量记在团队池上 |
| 7 | 计费周期 = 账户 billing cycle（开户周年日），不是自然月 | "per monthly billing cycle" |
| 8 | 机型额度：`s-1vcpu-512mb-10gb` 500 GiB、`s-1vcpu-1gb` 1,000 GiB、`s-1vcpu-2gb` 2,000 GiB | DO 定价页；目录里 `transfer_gib` 由 `size.transfer × 1000` 得到 |
| 9 | **没有**按机器查累计量的 API；Billing 页用量 T+1，明细 CSV 需手动申请 | OpenAPI 里只有 `/v2/monitoring/metrics/droplet/bandwidth`（Mbps 速率） |

**一条容易搞错的口径**：节点是中继，用户上传的数据也是「进节点、再发出去」，所以**用户上下行每一 GB 都会以一次出站的形式被 DO 计费**。「500 GB 出站」实际等于用户上下行合计 500 GB，不是只有下载。

## 4. 额度模型

### 4.0 周期：与 DO 完全对齐

- 周期 = **自然月（UTC）**。已由官方文档确认（2026-11-26）：*"DigitalOcean billing cycles are monthly. Your balance accrues over the course of the calendar month…"*，且 *"We automatically invoice and charge … on the first day of each month for the previous month's usage"*（<https://docs.digitalocean.com/platform/billing/>）。
- 清零点：**每月 1 日 00:00 UTC**，额度与用量同时归零。
- 边界校验用 `/v2/customers/my/invoices/{invoice_uuid}` 的 `invoice_items[].start_time` / `end_time`（带时分秒）；`billing_history` 没有周期字段，`invoice_summary.billing_period` 只有 `YYYY-MM`，粒度都不够，只能校验。
- **时区：UTC**（DO 支持确认，2026-11-26）。清零点 = 每月 1 日 00:00 UTC；上线后用第一张真实发票的 CSV 时间戳复核一次即可。
- 因此 `cycle_id` 直接由 UTC 年月推导（`YYYY-MM`），**不需要调用 DO 接口**；发票只在月末对账时用。
- **不用我们自己的 30 天，也不做固定 28 天窗口**：长度和 DO 不一致时，一年会多清零几次，每次多给一份「第 1 天额度」（500 GB 机型约 $0.18），是净亏。28 天只是**单台机器在一个 DO 周期内最多累计的额度封顶**，不是我们的周期。
- 额度与用量都在同一边界归零，两者必须同源，否则超额判断会错位。
- 降级：拿不到 DO 边界时退化为固定 28 天滚动窗口（长度与 DO 封顶一致，不会多给），并在日志里标记为降级运行。

### 4.1 公式

```
日额度       = 机型月额度 / 28            // 500/1000/2000 → 17.86 / 35.71 / 71.43 GiB
已释放额度   = min(机型月额度, 日额度 × (本周期存活天数 + 1))
可用额度     = 已释放额度 − 本周期已用
```

- `+1` 是建机预付的那一天，解决「新建节点流量为 0、用户当天不能上网」。
- 天数按整天向下取整，跨天时才增加；不需要秒级精度（秒级只影响我们和 DO 的几分钱差额）。
- 存活天数只算**本计费周期内**；上周期的不带入。

### 4.2 示例

| 场景 | 已释放额度 | 已用 | 超出 |
|---|---|---|---|
| 新机 5 分钟 | 17.86 GB | 0.5 GB | 0 |
| 新机 25 分钟跑 100 GB | 17.86 GB | 100 GB | 82.14 GB → 扣 $1.64 |
| 跑满 10 天 | 196.4 GB | 180 GB | 0 |
| 跑满 28 天及以上 | 500 GB（封顶） | 520 GB | 20 GB → 扣 $0.40 |

### 4.3 销毁、换机型

- 销毁：停止释放新额度；**已释放的部分留在本周期账号池里**，可抵同账号其它机器的用量，已用同样留在账号账上。周期开始前就已销毁的机器不计。
  - 与 DO 团队级「按存在秒累计」一致：DO 在机器存在期间攒出的额度留在团队池里，不会因为销毁而作废。按「未用额度作废」实现会反向多收用户，不做。
- 换机型重建：新机器按新机型的日额度从建机当天重新释放；旧机器的已释放额度保留在账号总和里。
- 账号层面的判断永远是：`Σ 各机器已用 > Σ 各机器已释放` 才有超额，与机器换过几次无关。

### 4.4 周期切换时发生什么

每月 1 日 00:00 UTC：

1. 旧周期的 `server_traffic` 行封存，历史保留；
2. 新周期已用流量从 0 开始；
3. 已释放额度回到「第 1 天」（500 GB 机型 17.86 GB），之后每天继续累加。

**清的只是计量，不是服务。** 机器只要还在付费周期内就继续运行，端口、密码、已导入的配置都不变，VPN 不断线。用户唯一能感知的变化是「可用额度从上月剩下的变成新周期的第 1 天」。

如果用户在零点附近跑大流量，超过新周期已释放额度的部分按 $0.02/GiB 扣——这与 DO 的行为一致（那一刻它的池子也刚归零）。零点前后几分钟的流量可能落到相邻周期，按秒计，对整月的账没有影响。

## 5. 计费流程

### 5.1 扣费时机

每次 agent 上报后，控制面按增量结算：

```
over_bytes      = max(0, 本周期已用 − 已释放额度)
应付_cents      = floor(over_bytes / GiB × 2)        // $0.02/GiB = 2 分/GiB
本次应扣        = max(0, 应付_cents − 已扣_cents)
```

- 只对**增量**扣，`已扣_cents` 落库，重复上报不会重复扣。
- 扣费与额度判断都在控制面做；agent 只上报字节数，不参与钱的计算。
- **扣的是「此刻累计」**：`已用` 与 `已释放` 都取当刻值，额度随机器存活逐日长出来。所以一次突发会被即时扣费；如果这台机器之后继续存活、额度追上用量，DO 月末的净算可能是 0，我们**不退回**已扣的部分（v1 不做负增量退款，见 §10 第 5 项）。方向是我方多收，不会少收，所以不会被用户套利。

### 5.2 余额不足

- 余额 `> 0` 但小于本次应扣：扣到 0，然后走现有停机路径，停机原因记为流量超支未付（新 `details.reason`：`traffic_overage`）。
- 余额本就为 0：直接停机。
- 不产生负余额，不做账期后补扣。

### 5.3 用户看到的扣费

- 详情页流量行 + 余额变化同步出现，不单独弹窗。
- 充值时余额增加，超出部分继续按 GB 扣，直到用户不再超支。

### 5.4 余额预警与销毁

**预测**（控制面算，不下发给节点）

```
日消耗   = 日价 + max(0, 近 7 天流量超支扣费的日均)
剩余天数 = 余额 ÷ 日消耗           // 余额 ≤ 0 时记 0
```

- 超支日均取最近 7 天 `charged_cents` 的平均值；没有历史就按 0。
- 结果作为 `MyServerWallet.remaining_days` 给界面用，不落库。

**三次提醒**

- 阈值：剩余 ≤ 7 天、≤ 3 天、≤ 1 天，每档提醒一次。
- 计数按**账号**记（余额是账号级的，多台机器同时停机），落库 `billing_warnings(account_id, level, warned_at)`；同一档位只弹一次，多台设备不会重复。
- App 打开后首次拿到钱包数据时弹框：还能用 X 天、预计哪天停机、列出受影响的机器；用户关掉即记一次。
- 充值成功后清空该账号的提醒记录，下次再降到阈值会重新提醒一轮。
- 已知限制：只能 App 内弹，用户不开 App 收不到——没有推送通道。

**销毁**

- 第三次提醒（剩余 ≤ 1 天）之后仍未充值 → 销毁；余额扣不动时同样立刻销毁。两者都无宽限。
- 销毁后界面显示「已销毁」，列表行可删除。
- 这是余额驱动的销毁，与节点健康无关：不做在线检测、不因失联销毁。

## 6. 计量：agent + nft

### 6.1 为什么不用另外两条路

- **DO API**：只有 Mbps 速率和 T+1 账单，拿不到实时累计；而且速率积分本身有误差。
- **sing-box 统计**：确实有（`experimental.v2ray_api.stats`，clash_api 的 `/traffic` 与 `/connections`），但**只在内存里，不落盘**。2026-11-26 用随包 1.14.4 实测：过 3 MB 流量后 `downloadTotal = 3,009,744`，重启进程后归 0；`cache_file` 也没有统计相关开关。节点上的 sing-box 会因轮换、升级、崩溃重启，比整机重启频繁，账本不能建立在它上面。

### 6.2 数据源：nft 出站计数

- 启动时用默认路由解析公网网卡（`ip route show default` 的 `dev`），不写死 `eth0`。
- 自建一张表，不动系统防火墙规则：

```
table inet veyl_meter {
  chain out {
    type filter hook output priority 0; policy accept;
    oifname "<if>" counter
  }
}
```

- 只数出站，与 DO 的计费口径一致；计数只增不减。
- 读法：`nft -j list table inet veyl_meter`，取 `counter.bytes`。
- 表被清掉就重建；重建后计数从 0 起，由「负增量」分支衔接。

### 6.3 读取、落盘与上报

本地状态（**原子写**：临时文件 + rename）：

```
{ counter_last, pending_bytes, last_saved_at, last_ok_at, seq, pending_attempt? }
```

每 30 秒读一次计数器，**落盘每 5 分钟一次**，上报按事件触发：

```
cur     = nft_bytes()
delta   = if cur < counter_last { cur } else { cur - counter_last }   // 负增量=计数器归零
pending += delta; counter_last = cur
if now - last_saved_at >= 5 分钟: save()
if pending_attempt 还在:                       // 上一批没收到 2xx
    原样重发 pending_attempt 里的 (seq, bytes)，不重算
elif pending >= 256 MB || now - last_ok_at >= 30 分钟:
    pending_attempt = { seq, delta_bytes: pending }; save()   // 先冻结并落盘
    POST /v1/agent/traffic
    2xx → pending -= pending_attempt.bytes; seq += 1; last_ok_at = now; pending_attempt = None; save()
```

- **先冻结再发**：请求发出前把这一批的 `(seq, bytes)` 落盘，失败时只重发这一批的原值。否则响应丢失后的重试会带上期间新增的字节，而控制面按 `seq` 去重会把新增的那部分永久丢掉（少算）。

- **agent 不知道计费周期**，报文里不带周期；归属由控制面按收到时间决定（§6.5）。
- 上报失败不清 `pending`，下个窗口重发；控制面按 `(server_id, seq)` 去重，只接受递增序列。
- 请求量：空闲机器每天最多 48 次；重负载每 256 MB 一次。
- 重启损失 ≤ 5 分钟（落盘间隔）的流量，不是 30 分钟的上报窗口。

### 6.4 状态缺失的规则（方向性）

**状态文件缺失或读不出来时，绝不能把当前计数器值当成增量**——那会把本周期已上报的流量再算一遍，等于向用户多收钱。

正确做法：停止累计、报一条 `metering_state_lost`，以当前计数器值作为新基准重新开始。最坏结果是少算一段，方向是对的。

### 6.5 周期归属（在控制面）

- **agent 不关心周期**：`seq` 单调递增、永不清零，`pending` 跨周期继续累计。
- 控制面按**收到上报时的 UTC 日期**把 delta 归到当月（`cycle_id = YYYY-MM`）；不需要 agent 传周期，也不需要它拉 desired-state。
- 零点前后几分钟的流量可能落到相邻周期，按秒计，对池化计算无影响。
- 这条修掉一个冲突：原设计让 agent 从 desired-state 拿 `cycle_id`，但定时轮询已删除，运行中的节点永远拿不到新周期。

### 6.6 三条不变量

1. **不重复计量**：负增量、状态缺失、seq 重复，一律走保守分支；宁可少算，不可多算。
2. **不阻塞服务**：计数或上报出任何错，只记日志，不影响 sing-box、凭据与控制通道。
3. **可对账**：上报带 `seq`，控制面只接受递增；回退一律丢弃并记一条异常。

### 6.7 不做在线检测

流量上报会刷新 `servers.last_seen_at`，但控制面**不据此做任何动作**：不判定在线、不触发重启、不自动销毁。计费按天，与节点当时是否可用无关——可用性由用户自己判断和处理。

（`desired-state` 只为「启动装机」和「用户点检查升级」存在：启动时拉一次，之后只在用户点按钮时拉，没有任何周期性调用。轮询已于 2026-11-26 删除，见 `singbox-upgrade-task.md`。）

### 6.8 已知误差

| 误差源 | 方向 | 处理 |
|---|---|---|
| 系统更新、agent 自身请求 | 我们数得**偏高** | 接受；与 DO 账单同口径，宁高不低 |
| 落盘间隔内重启 | 可能**漏 5 分钟以内** | 可接受，约 $0.003 |
| 用户侧重传、ACK | 双方一致 | 不处理 |
| 突发后被后续额度追上 | 我们**多收**（月末净额可能为 0） | 接受，v1 不退款；口径见 §5.1、待办 §10 第 5 项 |

### 6.10 测试与验收

单测五条：正常累加、计数器归零、状态文件缺失、上报失败重试、seq 重复。

真机三条：

1. **无周期请求**：节点上线后观察 agent 与控制面日志，除启动与用户触发外不应出现按分钟的 `desired-state` 调用（验证轮询确已删除）。
2. **计量准确**：让节点下载一个已知大小的文件（1 GB），比对 nft 读数与最终上报值，误差 ≤ 1%。
3. **上报自愈**：断开控制面一段时间再恢复，`pending` 应补发且不被重复记账。

### 6.11 任务顺序与依赖

1. 文档修正：周期归属改由控制面按接收时间判定（§6.5，已完成）。
2. 控制面 + agent 计量：§6.9 前五行。
3. 控制面配套：30 天账单归集接口、余额预警（预测 / 三次提醒 / 第三次后销毁）、`billing_warnings`。
4. agent 验证（本批验收）：`cargo test` → 发新版 agent → 重建 dev 节点 → 跑 §6.10 三条真机验收。
5. App：账单弹层、总可用带宽、账户入口重构、预警弹框。

**部署注意**：agent 改动必须发新版二进制（`AGENT_VERSION` / SHA / URL）并**重建节点**才生效——`upgrade_singbox` 只换 sing-box，不换 agent 自身；轮询删除后也没有自升级通道。

## 7. 数据与契约

### 7.1 控制面表

`server_traffic`（按机器 × 周期存历史，销毁后保留作审计）：

| 列 | 说明 |
|---|---|
| `server_id` | 服务器 id |
| `cycle_id` | `YYYY-MM`（UTC 自然月，**控制面按收到上报的时间判定**） |
| `bytes` | 本周期已用出站字节 |
| `released_bytes` | 本周期已释放额度快照（按天释放，封顶 28 天） |
| `charged_cents` | 本周期已扣的超支金额 |
| `last_seq` | 已接受的最大上报序号（去重用，按 server 记、跨周期不清零） |
| `updated_at` | 最后上报时间 |

主键 `(server_id, cycle_id)`。`servers` 表不加上报字段。

### 7.2 agent 接口（冻结，2026-11-26）

```
POST /v1/agent/traffic
Authorization: Bearer <server_token>

{ "seq": 1234, "delta_bytes": 268435456 }

200 { "ok": true }
400 { "ok": false, "reason": "invalid_body" }
401 unknown token
409 { "ok": false, "reason": "server_destroyed" }   // 终态，agent 停止上报
```

- `seq` 每个 server 单调递增、永不清零；`seq <= last_seq` 视为重复，回 200 但不记账。
- 归属周期 = 控制面收到请求时的 UTC 年月，agent 不传周期。
- 接受 delta 后：`bytes += delta`，并按 §5.1 在同一事务里算并扣超支。

## 8. 用户可见状态

服务器详情事实区「流量」一行（`servers-list-detail.md` §2 已有该行）：

```
流量      已用 128 GB · 可用 352 GB        12 月 3 日重置
```

| 状态 | 展示 |
|---|---|
| `ok` | `已用 X GB · 可用 Y GB`，数字 `--ink-2` |
| `near`（已释放额度的 80%） | 同上 + 一行琥珀小字「流量快用完了」 |
| `over` | `已用 X GB · 超出 Y GB，按 $0.02/GB 从余额扣` |
| `unpaid`（超支且余额不足已停） | `流量超支，余额不足已停机`，状态点琥珀 |

- 列表行只给紧凑状态，不显示百分比。
- 单位统一用 **GB** 展示、**GiB** 计算（差 7%，不要混用）。

### 8.1 近 30 天消费账单（需求，设计待定）

用户要能在界面上看到**最近 30 天每天的消费**，而不是只有余额一个数。

- 展示内容：每天一行，含机器费、流量超支、当日合计；只做最近 30 天。
- 目的：让用户看得见钱花在哪，减少「为什么扣这么快」的客服；也是流量超支最直观的可见化。
- 数据来源：钱包流水（`wallet_ledger`）与各机器的 `charged_cents`，按天归集。
- 说明：30 天会跨两个计费周期，**不能只读当前周期的 `server_traffic` 行**，必须按天归集流水。
- 界面与入口见 `account-billing-ui.md`（设置 › 账户的「近 30 天账单」弹层）。

### 8.2 账号级总可用带宽

多台服务器不需要单独算法，账号级就是一个式子：

```
账号可用 = Σ 各机器已释放额度 − Σ 已用流量
```

- 为正：`可用 X GB · 12 月 1 日重置`。
- 为负：`已超出 X GB，按 $0.02/GB 扣余额`（琥珀）。
- 与扣费口径同源——超额本来就是按账号判的，界面不必按机器分别展示再相加。
- 待定（下一轮讨论）：
  - 入口放哪：账户/钱包页，还是服务器详情；
  - 按账号汇总，还是按机器分列；
  - 日界用 UTC 还是用户本地时区（与周期清零的 UTC 口径不同，需要单独定）；
  - 是否允许点某一天看明细。

## 9. 内部视图与对账

- 每日估算表（不进客户端）：按账号列「机器·天 / 已释放 / 已用 / 应扣超支」，加团队合计。
- **周期内没有外部校验**（2026-11-26 实测）：`billing insights` 的夜间账单项只有按时计费的资源费，**不含带宽**——带宽超额是整个周期用量减整池，只能在周期末算出来，因此只出现在月末发票的 `overages` 里。周期内 DO 侧唯一能看到的是 Billing 页的带宽概览（每天更新、有预估，无 API，只能人工看）。
- 因此自建计量是**周期内唯一依据**；我们的数必须偏保守（nft 数整机公网出站，比只数 sing-box 略高），不能偏低。
- 月度对账：以发票的 `overages.amount` 为准（当前带宽是唯一的超额来源，聚合值够用）；算出系数 `k`，只用来校准阈值，不改用户记录。
- 告警：团队估算用量达到团队池的 80% 时通知我们——这是唯一会真正花我们钱的地方。

## 11. 验收

1. 新建 500 GB 机型，详情页立刻显示「可用约 17.9 GB」，不用等。
2. 25 分钟跑 100 GB、余额充足：扣 $1.64，机器不停，状态为 `over`。
3. 同上但余额为 0：按 GB 扣到 0 后停机，原因 `traffic_overage`。
4. agent 重启：累计值不回退，控制面不重复扣。
5. 跨周期：额度清零、`charged_cents` 归零、`cycle_id` 更新。
6. 换机型重建：新机按新机型释放额度，旧机已用仍在账号账上。
7. nft 计数只含公网出站：VPC 私网与 loopback 流量不计。
8. 与 DO 账单对比：只对**整月用量确实超过机型月额度**的账号对账，我们的计量与发票中带宽超额部分的差额在 5% 以内。被即时扣费、但月末整月净额为零的部分不计入对账偏差（口径差异见 §5.1）。
