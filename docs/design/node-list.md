## 1. 现状与问题

### 1.1 入口不可发现

`Console.tsx:474-506` 的节点卡：节点名是一个 `node-card__name--button` 按钮，但样式与旁边的纯文本没有区别；
旁边只有「更换」「检查」两个 ghost 按钮。`docs/center-panel.md:60` 写的是「底部的节点名可点，展开全部节点」，
但没有规定任何可展开的外观，于是实现成了「看起来像文字、点开才知道是按钮」。

用户不知道这里有列表，就不会去点。**这是入口的可见性问题，不是交互深度问题。**

### 1.2 节点多了就没法用

- `node_probe`（`commands.rs:444`）一次只测一个节点；100 个节点要点击 100 次。
- 节点选择器（`node-picker`）是一个无搜索、无测速、无标记的平铺 `listbox`。
- 已连接时探测走 Clash API，未连接时走 TCP；能力是有的，只是没有批量入口。
- 没有任何地方保存测速结果，切换面板后结果就丢了。

## 2. 横向调研

看的是「用户想换一个节点、或者想知道哪个节点快」时，各产品怎么做。

| 产品 | 入口与列表形态 | 批量测速 | 当前节点标记 | 延迟与新鲜度 | 大量节点 | 自动最快 |
|---|---|---|---|---|---|---|
| **Clash Verge Rev** | 左侧 Proxies 页；代理组卡片内平铺节点 | 组头闪电 = 整组测；节点悬停闪电 = 单个 | 组内选中项高亮 | 测完显示 ms，未测显示「检查」；结果在内存里 | 组内滚动；是否搜索/虚拟滚动未核实 | 有 `url-test` 组，手动选择可能被下次自动测速覆盖 |
| **ClashX Meta** | 菜单栏下拉；代理组是子菜单 | 组级「Test latency」+ 单节点 | 当前项加勾/加粗 | ms 显示在行尾；菜单打开时按需测（lazy） | 菜单滚动，无搜索、无虚拟化 | `url-test` 组 |
| **Surge** | 策略组列表；组头有测试按钮 | 组级测试；`url-test` 按 `interval` 自动重测 | 组内当前策略标记 | 结果带时间；`interval` 默认 600s，`tolerance` 默认 100ms | 列表；搜索未核实 | 有；手动选择可**临时覆盖** `url-test` |
| **Stash** | 策略组页面；组头右上角按钮测试 | 组级测试 | 当前项标记 | `interval` 默认 600s，可 `lazy` 跳过；可按延迟排序 | 未核实 | `url-test` / `fallback` |
| **Quantumult X** | 首页显示节点延迟，Servers 面板可测；策略组 | 组级 / 全部测试 | 当前策略标记 | 点按刷新延迟 | 未核实 | `url-latency-benchmark`（`interval` / `tolerance`） |
| **v2rayN** | **主窗口整页表格**，不是下拉 | 多选/全选后右键「真连接延迟」；并发可配置；状态栏进度；可取消 | 当前服务器行标记 | 延迟列，可排序；结果留在列里 | 表格排序、多选；搜索未核实 | 无自动组；按结果排序后手动选 |
| **Hiddify** | 首页代理卡 → Proxies 列表；右下闪电 | 一键测全部；可按结果排序；v5.5 支持「只留最快的」 | 活动节点卡片 | ms；超时显示 Timeout；点按重测 | 大订阅提供「只保留最快」；虚拟滚动未核实 | 「自动」组会被 url-test |
| **Mullvad** | 服务器选择器，按国家/城市；可搜索 | 未见批量测速 | 当前服务器 | 逐服务器延迟的具体形态未核实 | 搜索 + 分组 | 「最近 / 最快」入口 |
| **Proton VPN** | 服务器列表按国家；快速连接「Fastest」 | 无批量测速 | 当前服务器 | 展示**负载百分比**而不是延迟 | 搜索 + 国家分组 | Fastest 算法（负载 / RTT / 带宽） |

> 未核实的不编。调研的目的不是照抄，是确认哪些约束是行业共同做法。

### 2.1 五个共同不变量

1. **入口自己说明「这里有一份列表」**：箭头、数量或当前值，不会只有一个纯文本节点名。
2. **当前节点在打开列表时可见并标记**；是否置顶各产品不同，但「哪个是当前」永远一眼能看出来。
3. **延迟是带时间戳的快照，测试显式触发**。没有产品把延迟当成实时值；未测、超时、过期是三种不同状态。
4. **批量测速 = 显式动作 + 进度 + 可取消**；单个节点失败不终止整批，也不弹错误。
5. **排序是视图，自动最快是策略**。排序不改数据；自动组存在时，手动选择优先，并能随时被覆盖。

## 3. 信息架构：底部上拉面板

### 3.1 选项对比

| 方案 | 优点 | 否决理由 |
|---|---|---|
| A. 把现有下拉加宽 | 改动最小 | 100 行 + 搜索框 + 进度条塞进 popover；`listbox` 里放输入框语义不对；高度受限 |
| B. 二级页面（替换控制台内容） | 空间最大 | 选节点时最需要看到「现在连的是哪个、状态如何」，整页跳走会把这两个事实藏起来 |
| C. 右侧抽屉 | 空间大 | 右缘是对话栏的位置，再滑出一个面板会像第二对话区；中间区宽度本身有限 |
| **D. 底部上拉面板（sheet）** | **空高足够、控制台顶部与节点卡都还在、不改变路由** | — |

**选 D。** 面板从节点卡上方向上展开，锚在中间区底部：宽度等于中间区，最大高度 60%，
覆盖 AI 编排区，节点卡与顶部连接按钮保持可见。它不是一个页面，不参与导航，也不改中间区布局。

这样「一个事实只有一个住处」仍然成立：

| 事实 | 住处 |
|---|---|
| 全部节点、延迟、测速进度 | **只有面板** |
| 当前节点、地址、端口、加密方式 | 节点卡（面板里切换后立即更新） |
| 连接状态、出口 | 控制台顶部 |
| AI 的说法 | 对话里只描述结论，不列节点清单 |

### 3.2 打开与关闭

- 打开：点节点卡整行（节点名 + `⌄` + 「N 个节点 + 延迟」）、或键盘 Enter。
  整行是**唯一入口**，节点卡上没有同名的「选择节点」按钮——同一个动作两个入口会让人犹豫两者是否不同。
- 关闭：Esc、点面板外、点右上角关闭。
- 打开时**不自动测速**——见 §12。
- 打开时把当前节点滚入可视区（不是置顶，见 §6.3）。
- 面板开着时切换配置：直接关闭面板并回到新配置的节点卡，避免「面板里还是旧配置的节点」。
  旧配置的批次**继续跑完**；新配置的节点卡不显示它的进度，切回来时再从 `snapshot.run` 恢复。

## 4. 节点卡（入口）

节点卡只加可见性，不改结构：

```
当前节点  ┌──────────────────────────────┐
          │ 东京 01   ⌄   23 个节点  38ms │   ← 整行是按钮
          └──────────────────────────────┘
          1.2.3.4:20343 · aes-256-gcm
          2 分钟前测过
          [ 测这个节点 ]

（有批次在跑时，第二行换成：）
          正在测速 12/23 · 点开可停止
```

- 节点名行：整行可点，高 ≥44px；右侧固定显示「N 个节点」与当前节点的最近一次延迟（没有则不显示）。
- `⌄` 跟随 `aria-expanded` 旋转；`aria-haspopup="dialog"`。
- 「更换」按钮**删除**，由整行承接；「检查」改名「测这个节点」——「检查」听不出在检查什么。
- 「测这个节点」保留单测能力，调用现有 `node_probe`。它是单节点探测，不是打开列表，所以不算第二入口。
- **0 个节点时既不渲染整行入口，也不渲染动作区**，整张卡只剩「还没有节点」。
  打开一个空列表没有意义；「选择节点」从来没在空态出现过，删掉它不影响空态。
- 「测这个节点」是 ghost：同屏唯一主按钮仍是顶部的 `启动 VPN`（`veyl-ui` 的硬约束）。
- **活动批次可见**：本配置有批次在跑时，折叠状态必须显示「正在测速 12/23」，整行可点开面板。
  准备阶段显示「正在准备测速…」。
  面板关闭不等于任务结束，用户得在面板外也能知道有东西在跑，并且有入口去停止它。
  批次属于别的配置时不显示（避免「切了配置还看到上一套的进度」）。

## 5. 面板结构

```
┌ 节点 · 公司 ──────────────────────── [关闭] ┐
│ [ 搜索节点                            ]      │
│ 共 23 个 · 18 个可用 · 3 分钟前测过  排序:延迟│
├──────────────────────────────────────────────┤
│ ● 东京 01        当前        38 毫秒  刚刚   │
│ ○ 东京 02                    120 毫秒 3 分钟前│
│ ○ 洛杉矶 01                  超时            │
│ ○ 法兰克福 01                未测            │
│ …                                            │
├──────────────────────────────────────────────┤
│                            [ 全部测速 ]       │
└──────────────────────────────────────────────┘
```

- 标题带配置名，避免面板开着时忘了这是哪套配置。
- 搜索：按名称与地址过滤，客户端即时；有过滤时，批量按钮文案变成「测这 12 个」，作用于当前过滤结果。
- 汇总行：总数、可用数、最近一次测速时间；排序切换是文字按钮（`手动` / `延迟`）。
  **批次在跑时，汇总行改为「正在测速 12/23」并显示细进度条**，底部按钮 `全部测速` 变成 `停止测速`；
  未连接、正在起临时运行时时显示「正在准备测速…」（§6.5），不要显示 `0/23`。
- 行高固定 44px：左侧状态点、名称、右侧延迟与时间；「当前」是文字徽标，不是只靠颜色。
- **点一行立刻切换**：调用 `node_switch`，行内短暂显示「切换中…」；成功后「当前」徽标移到该行，
  面板保持打开。失败时该行显示原因（一句），当前节点不变。
  点当前节点不发起调用；「切换中…」期间再点其它行忽略，避免并发切换。
- 底部只有一个按钮 `全部测速`（ghost，次级）；**没有提交按钮**，也没有「已选择 X」这类中间态文案。
- 键盘：↑↓ 移动焦点；Enter = 切换；Esc 关闭；输入即搜索。
- 关闭面板不会撤销已经发生的切换，也不取消正在跑的批次。
- 重新打开时按 `node_probe_snapshot.run` 恢复进度与 `停止测速`，不把「有缓存但仍在跑」显示成「已测完」。

### 5.1 为什么这里可以「点哪切哪」

`center-panel.md:64` 的「选中 ≠ 切换」管的是**中间控制台的节点预览**：那里的用户可能只是翻一翻所有节点，
不应该点一下就把网络换掉。**节点选择面板是那条规则的例外**：打开它本身就是为了换，
点击就是用户的决定；再要求点第二次，等于把「不能一个个切换」的问题原样留着。

两条规则不冲突，因为它们回答的问题不同：控制台问「你想看哪个」，面板问「你要用哪个」。
以后若有人拿 `center-panel.md:64` 想把这里改回两步，先看这一段。

### 5.2 单击即切的风险与处理

- **重排**：测速结束时的重排会让行在指针下移动，可能误点。处理沿用 §7.1 的
  「运行中锁定排序、结束后只重排一次」，并配合 44px 行高与行间分隔，减少落点漂移。
- **误点代价**：节点切换是热切，不中断连接、不断开隧道，最坏结果只是再点一次原节点。
  如果将来切换变成「断开再连」，这条要重新评估，不能沿用。
- **批次进行中允许切换**：切换只改当前节点，不影响在飞的探测；后续行仍按原批次测该配置的节点，
  **不取消、不重启**。批次的结果描述的是节点本身，与「当前用哪个」无关。

### 5.3 行状态

| 状态 | 行尾显示 | 说明 |
|---|---|---|
| 未测 | `未测` | 本次运行内没有结果 |
| 测速中 | 转圈 + `测速中` | 该行正在飞 |
| 可用（真实） | `可用 38 毫秒` | `probe_method = "clash_delay"`，验证了凭据与出口 |
| 可达（仅端口） | `可达 38 毫秒` | `probe_method = "tcp"`，只证明服务器端口活着（§6.5） |
| 过期 | `可用 38 毫秒 · 12 分钟前`，淡化 | 超过 TTL（10 分钟） |
| 超时 / 不可达 | `超时` | `reachable = false` |

「可用」和「可达」必须写成两种词，不能都叫「延迟」：前者能用来选节点，后者只能说明服务器在线。
颜色只做辅助，文字状态必须存在（与强制重置的步骤列表同一规则）。

## 6. 批量测速契约

### 6.1 为什么不用 Job

Job 是持久化的长任务（`tools.md` §4.16），面向安装、升级这类跨重启还要交代进度的事。
批量测速是 10–60 秒的瞬时操作，结果本身是缓存，重启后没有恢复价值。
所以用**独立命令 + 两个事件**，不写 `job-progress`，不进设置页。

**批次随进程结束而结束**：应用退出时直接丢掉在飞的探测，不持久化批次、不做退出前等待、不发完成事件。
不要因为「关面板不取消」就误以为它需要跨进程存活——那是 Job 的职责，这里刻意不要。
重启后面板显示「未测」，符合「延迟是快照」的语义。

### 6.2 命令

```ts
// 启动
node_probe_all { configId?: string }
  → { run_id: string; config_id: string; total: number; concurrency: number }

// 取消
node_probe_cancel { runId: string } → { cancelled: boolean }

// 读现有结果与运行态（打开面板时先渲染缓存，不发网络请求）
node_probe_snapshot { configId?: string }
  → {
      config_id: string;
      results: NodeProbeData[];
      run: null | {
        run_id: string;
        done: number;
        total: number;
        started_at: number;
        phase: "preparing" | "probing";
        method: "clash_delay" | "tcp" | null;
      };
    }
```

- `run` 只在 `run.config_id == configId` 时返回；全局仍只有一个批次，别的配置在跑时本配置拿到 `null`。
- `run` 非空 = 该配置有批次在跑。UI 据此恢复进度条与「停止测速」，
  并从 `done` 继续接收进度事件——**不能因为 `results` 有内容就显示成「已测完」**。
- `run` 为空 = 纯缓存浏览；`results` 里是上次测过的结果（可能已过期）。

- `configId` 省略 → active 配置；没有节点 → `PRECONDITION_FAILED / no_nodes`。
- 已有运行中的批次 → `BUSY` + `details.run_id`；同一时间只允许一批。
- **并发 6**：降级时是对不同主机的 TCP 握手，6 路足够；探针运行时可用时是发往本机 Clash API 的
  延迟请求，再高也只会压本地。单个节点沿用现有 3 秒超时，不做重试。
- **探测方式按 §6.5 的矩阵决定**，一批只在一种方式下跑：真实（`clash_delay`）或仅端口（`tcp`）。
  单测与批测用同一个单节点函数，不复制探测逻辑。
- 结果按完成顺序流出；**单节点失败不中断**，失败也是一种结果。
- 取消是尽力而为：在飞的探测丢弃，不再发进度；已出的结果保留在缓存里。

### 6.3 事件

```ts
node-probe-progress {
  run_id: string;
  config_id: string;
  done: number;
  total: number;
  phase: "preparing" | "probing";
  method: "clash_delay" | "tcp" | null;   // 准备阶段还不知道
  result: NodeProbeData | null;          // preparing 时没有结果
}

node-probe-finished {
  run_id: string;
  config_id: string;
  total: number;
  ok: number;
  failed: number;
  cancelled: boolean;
  method: "clash_delay" | "tcp";
  network: "ok" | "offline";   // 见 §9
}
```

- **第一条进度是 `preparing`**（未连接、需要临时起运行时才有），`done = 0`、`method = null`；
  运行时就绪或确定降级后发一条 `probing`，`method` 定下来，之后每个节点一条带 `result` 的进度。
- 一批只在一种 `method` 下跑，不会同一批里既有 `clash_delay` 又有 `tcp`。
- 每测完一个节点发一条进度；`done` 单调递增。
- `config_id` 让 UI 能丢弃「已切走的配置」的迟到事件。
- 事件是应用级的，重新打开面板不需要重新订阅：按 `run_id` 匹配，忽略不是当前批次的事件，
  按 `done` 去重（重开后可能先收到一条早于 `snapshot.run.done` 的迟到事件）。
- `node-probe-progress` 只在批次运行时出现；面板关闭后仍在后台跑完（用户没点取消）。
- UI 重开面板时先 `node_probe_snapshot` 渲染结果与运行态，再继续接收进度事件。

### 6.4 单测是否保留

保留。`node_probe` 同时服务三处：AI 的 `NodeProbe` 工具、节点卡的「测这个节点」、批量实现内部的单节点函数。
批量只是加了调度与缓存，不改单测语义。

### 6.5 未连接时能不能测：A/B/C 决策

现状是「能测，但深浅不同」：已连接且节点属于当前配置时走 `clash_delay`，验证凭据与出口；
其余情况走 TCP 握手，只证明 `server:port` 活着。问题在于两者都叫「延迟」，用户分不出差别。

| | A. 只保留 TCP，把话说明白 | B. 临时起运行时，测完停掉 | C. 运行时常驻，不上系统代理 |
|---|---|---|---|
| 用户看到 | 「可达 38 毫秒」；批量汇总区分「可达 / 超时」 | 「可用 38 毫秒」，与已连接时完全一致 | 同 B |
| 能回答「哪个能用」 | **不能**：密码/UUID 错、套餐过期、服务端拒绝握手，TCP 全测不出来 | 能 | 能 |
| 失败模式 | 数字骗人：端口开着但连不上，用户按 38ms 挑完再失败 | 运行库缺失、配置无效、端口占用、启动超时；必须降级 | 常驻进程、本地监听面、内存占用 |
| 对并发/取消 | 最简单：6 路 TCP，取消即时 | 多 1–8 秒准备；取消要停掉自己起的运行时；与连接请求互斥 | 与已连接时相同 |
| 与现有架构 | 不改 | 复用 `runtime_start` 与 Clash delay，单写者约束要处理 | **推翻「断开即停运行时」与 helper 空闲退出** |

**结论：选 B，A 作为它的降级路径，C 否决。**

理由：

- 用户要的是「哪个能用」。TCP 结果在订阅节点上经常是假阳性——端口开着、握手被拒，
  用户按「38 毫秒」选完再连不上，比没有数字更糟。
- 底层能力已经现成：运行时的启动计划、Clash API、单节点探测都在；缺的只是一个「只起进程、
  不设系统代理」的入口。**`runtime_start` 命令不能直接复用**——它走完整连接流程
  （`services.rs` 的 `connect`），会把系统代理设上；B 需要复用它的前半段（生成计划、启动进程），
  在 `set_system_proxy_enabled(true)` 之前停住。
- C 直接违反 `helper-update.md` 与「断开即停运行时」的决定，为一个测速功能把常驻进程和监听面请回来，不值得。

#### B 的强制约束

1. **只在完全未连接时启动临时运行时**。已连到本配置 → 直接 `clash_delay`；已连到**别的配置** →
   不能起第二个运行时，整批降级 `tcp`。
2. 临时运行时强制 `system_proxy` 模式，**不写系统代理、不启 TUN**；用临时端口，只绑 `127.0.0.1`，
   不占用用户配置里的端口。启动路径复用连接流程的前半段，在设置系统代理**之前**停住；
   不要调用 `runtime_start` 命令。
3. **启动失败（或 8 秒内没就绪）→ 整批降级 `tcp`**，不报错、不中断；文案随之变成「可达」。
   这条是硬要求：不能让「运行时起不来」把一次测速变成全部失败。
4. **探针运行时不能污染连接状态**：管理器为它单开一个 probe 槽（独立进程/端口），
   `runtime_status` 与 `runtime-state-changed` 在探针期间仍报「未连接」，
   顶部按钮不能变成「断开」。否则用户会看到「没连却显示已连接」。
5. 结束或取消时停止**自己起的**运行时；如果期间用户点了「启动 VPN」：
   - 批次立即取消，`finished.cancelled = true`，并带 `reason: "connected"`；
   - **先停掉探针运行时，再走正常的连接流程**。不要把探针进程移交给连接——那样连接状态会从
     「未连接」直接跳到「已连接」，却跳过了正常的代理设置与校验。
6. 应用退出：批次随进程结束（§6.1），运行时由现有退出清理负责。
7. **单节点「测这个节点」不启动运行时**：一个节点的测试不值得等 8 秒启动；
   未连接时仍走 TCP 并标「可达」。批量才是「替用户做决定」的那条路径。

#### 文案后果

- 真实结果：行尾 `可用 38 毫秒`；汇总 `18 个可用 · 5 个超时`。
- 降级结果：行尾 `可达 38 毫秒`；汇总 `18 个可达 · 5 个超时`，并加一行
  「没连上，只能确认服务器连得上，不验证密码和出口」。
- 两种词不能混用，「可达」不得简写成「可用」。

## 7. 排序、缓存与新鲜度

### 7.1 排序模式

| 模式 | 规则 | 默认 |
|---|---|---|
| **手动** | 配置内节点顺序（当前即添加顺序） | ✅ |
| **延迟** | 可用（新鲜升序）→ 可用（过期升序）→ 未测 → 超时 | |

- **当前节点不置顶**，只标记并滚入可视区。置顶会让「300 毫秒排第一」看起来像最快，排序就不诚实了。
- 测速**运行中锁定排序**，行内原地更新数值；结束后如果当前是「延迟」模式，整表重排一次。
  实时重排会让行在鼠标下跳动；单击即切之后，这更是误点来源。
- **重排为什么可以接受**：节点切换是热切，不断连接；即使重排后误点，代价也只是再点回原节点。
  这条成立的前提是「切换不断线」——如果哪天切换变成重连，必须先停用运行时重排。
- 手动模式永远不因测速结果改变顺序。

### 7.2 偏好持久化

排序模式是**视图偏好**，不是配置数据：

- 存储：前端 `localStorage`，键 `veyl.nodeSort`，取值 `manual | latency`，默认 `manual`。
- 作用域：整个应用，不按配置区分（用户对「怎么排」的偏好和对「哪套配置」无关）。
- 不写进配置、不发事件、不同步后端。将来若要多端同步，再迁到 settings 表。

### 7.3 结果缓存

| 项 | 规则 |
|---|---|
| 位置 | 后端内存 `HashMap<node_id, NodeProbeData>`，进程内有效 |
| 不落库 | 重启即空，面板显示「未测」；避免几天前的数字被当成现状 |
| 新鲜度 | `checked_at` 起 10 分钟内算新鲜；超过只淡化显示并标「N 分钟前」 |
| 失效 | `node-list-changed` 中该节点被删除 → 移除；节点仍在则保留 |
| 配置切换 | 键是 `node_id`，跨配置共用（延迟是节点属性，不是配置属性）；`probe_method` 随结果保存 |
| 与排序 | 过期结果仍参与排序，但排在新鲜结果之后 |

面板每次打开调 `node_probe_snapshot`，拿到的就是这份缓存的内容，外加该配置的运行态 `run`。

## 8. 自动选最快

**v1 不做自动。** 理由：

- 自动切换会在会话中途换出口 IP：下载、登录态、长连接全部受影响，用户看到的是「网络自己变了」。
- 与「每一次切换都是用户点的」冲突：面板里的切换是可解释的操作，自动切换是后台替用户做决定。
- 各产品的自动组（`url-test`）解决的是「策略组」问题，不是「节点列表」问题；我们还没有策略组。

批量测速之后，用户按延迟排序、点一行就切过去；不再有「选中再确认」的第二步。

如果将来要做，规则必须是：只在**建立连接时**选一次；界面上有「自动」徽标和「停止自动」；
用户手动选择后暂停自动，直到下次断开或显式恢复；绝不在连接中途静默切换。

## 9. 失败语义

「失败」是测速的正常输出，不是应用错误：命令返回 `Ok`，失败体现在 `reachable = false`。

| 情况 | 界面 | 说明 |
|---|---|---|
| **部分失败** | 各行显示 `超时`；汇总「18 个可用 · 5 个超时」（降级时写「可达」） | 不弹窗、不 toast、不登记问题 |
| **全部失败，但本机有网络** | 汇总「都没测通」+ 一句「这些节点可能都不可用」 | 仍需逐个行保留超时状态 |
| **全部失败，且本机离线** | 顶部提示条「现在没有网络，测速结果不代表节点状态」+「检查网络」 | `finished.network = "offline"` |
| **临时运行时没起来**（§6.5） | 不报错；整批按 `tcp` 跑，文案变「可达」+ 一行说明 | 降级不是失败，用户仍拿到结果 |
| 取消 | 汇总回到「上次测速：3 分钟前」；不加错误文案 | 已出的结果保留 |

离线判定：只有**全部节点都失败**时才做一次本机连通性检查（直连的 204 请求，不走 Veyl 代理，
否则代理本身坏了会被误判成本机断网），避免每批都多一次网络调用，也避免把节点故障误报成本机断网。
「检查网络」复用现有诊断入口，不新造流程。

## 10. AI 侧

**不给模型批量测速工具。**

- `NodeProbe` 保留：一次一个节点，5 秒预算，适合「帮我看看东京 02 通不通」。
- 批量测速是界面尺度的操作：100 个节点、进度、取消、结果表格。做成工具会带来长工具调用、
  大量结果 token，以及「一句话触发几百个出站连接」的注入面。
- 模型要说「哪个最快」时：先问用户要不要在面板里测；或只测 1–3 个候选，并说明这是抽样。

若将来必须给：只允许用户明确要求时调用；上限 20 个节点；只返回汇总（最快 3 个 + 可用/超时计数）；
对话里只显示一行「测了 20 个节点，最快的是 东京 02」，不逐条铺开。

## 11. 性能与搜索

| 项 | 规则 |
|---|---|
| 搜索 | 客户端过滤，匹配名称与地址，忽略大小写；不做模糊拼音 |
| 虚拟滚动 | 节点数 > 60 时启用窗口化：固定行高 44px，只渲染可视区 ±6 行；搜索后按过滤结果重新计算 |
| 分组 | **v1 不做**。节点模型没有分组字段（`store/configs.rs` 的 `Node` 只有 `source`），按名称猜地区不可靠；等模型有 tag 再做 |
| 列表更新 | 测速进度只更新对应行，不重建整个列表；排序模式下不移动行 |
| 滚动 | 打开时滚到当前节点；搜索变化时回到顶部 |

节点上百个时，真正的瓶颈是渲染与重排，不是网络请求数——所以虚拟滚动比「限制测速数量」更优先。

## 12. 权限与触发

- 批量测速是**只读操作**：不改配置、不改当前节点、不登记问题、不发 `*-changed` 事件。
- 但它会发起最多 N 个出站连接，所以**必须由用户显式点击**：
  - 打开面板不测速；
  - 不提供自动定时测速；
  - 不因为「打开了应用」而测速。
- 不需要确认卡：没有状态改动，取消也随时可以。
- 「全部测速」永远不是主按钮：面板里只有 ghost 按钮，主按钮仍然是控制台顶部的连接按钮。
