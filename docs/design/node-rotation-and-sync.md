# 节点可恢复性与配置同步：五项任务

> 日期：2026-11-21
> 状态：**待评审**。本文件只整理问题与选项，不定实现、不改代码。
> 上游：`my-servers.md`（建机与凭据模型）、`mobile-export-technical.md`（手机端导出与多格式）、`node-list.md`（测速口径）

## 0. 今天验证到的事实（作为后面所有判断的依据）

新加坡那台机器（`165.22.103.87`，sgp1）这次排障得到的证据：

| 观测 | 结果 | 说明 |
|---|---|---|
| 旧端口 36940：ICMP | 通（3/3） | 主机在线 |
| 旧端口 36940：TCP | 从本机超时（4.0s 丢包） | 不是 RST，是包被丢 |
| 旧端口 36940：境内外对照 | 香港/新加坡/英国/美国等 8 个节点 TCP 全部连通（6–250ms） | 服务在跑、DO 防火墙正确 |
| 开放 22 后 TCP 22 | 从本机 0.26s 连通 | 这个 IP 的 TCP 通路本身没问题 |
| 新端口 26940：TCP | 从本机 0.26s 连通 | — |
| 新端口 26940：数据面 | 随包 sing-box 实测出口 = `165.22.103.87`，baidu 200 | 换端口后完全可用 |

**结论（限定范围）**：这次是**端口级**的路径阻断；换端口恢复了可用。改密码在这个实验里没有、也不可能起作用——`nc` 只做 TCP 握手，根本没走到密码校验。

**不能从这次推出的**：
- 不能推出「凭据轮换是可用能力」——服务器侧没有管理通道，这次是人工走 DO 控制台改的。
- 不能推出「换端口长期有效」——端口级封锁会跟随；IP 被整体 TCP 封掉时换端口无效。
- 不能推出「密码无关」——只说明这次故障不是密码造成的。

## 1. 重置端口与密码的逻辑

### 1.1 现状

- 端口与密码在**首次开机时由 cloud-init 生成并写死**：`/usr/local/etc/sing-box/config.json`（`cloud_init.ts:101–119`）。
- 机器起来后通过 enroll 把 `{port, password}` 回传给控制面，控制面封成 `credentials` 行（`servers.ts` enroll）。
- **没有任何下发通道**：SSH 在开机第一步就被 `stop + disable`，DO 防火墙也不放行 22；DO API 不能执行命令。
- 因此今天之前，「重置」只能靠人工进 DO 控制台，且没有回写 `credentials` 的接口——这次是临时写了个本地脚本重新加密再 `wrangler d1 execute`。

### 1.2 已收敛的路线

> **2026-11-21 更新**：本节原先的三条路线已收敛为「节点 agent」，细节拆到两份独立文档：
> - 机器侧的执行器与 MCP 接口：`node-agent-mcp.md`
> - 端口带与共享防火墙：`shared-firewall.md`
>
> 保留下来的判断：**重建换机（原 A）只作为兜底**——端口级故障走 agent 轮换，IP 级不可用才重建；**预置多端口（原 B）被取代**，因为 agent 可以直接改监听端口，不再需要预置。

### 1.3 为什么不做「预置多端口」

原方案 B 是「建机时开 N 个入站、控制面切换」。它不需要下发通道，但候选项有限、切换次数用完就得重建，而且客户端要么等同步、要么面对多条红灯节点。agent 方案把「改端口」变成一次受控调用，端口可以在端口带内任意选，覆盖范围大得多。代价是要维护一个常驻进程（见 `node-agent-mcp.md` §10 的安全边界）。

### 1.4 待定

原有三条（预置几个端口、旧端口关不关、谁来触发切换）随预置方案一起作废；agent 方案的新问题清单在 `node-agent-mcp.md` §11。

## 2. Mac 端更新配置与故障判定

### 2.1 现状

- 节点探测走 Clash `/proxies/node-<id>/delay`，是经 sing-box 真发一次请求的口径（`probe_batch.rs`）。单点失败只能得到「不通」，**不区分**是服务器死了、端口被封、还是凭据过期。
- 已有三态：`ok` / `unreachable` / `untested`（含 `no_credentials`）。
- 连接路径会跳过没有密码的节点，但**没有任何「修复」动作**。

### 2.2 要回答的问题

「探不通」时，要能回答三种情况之一：

1. **服务器不在了 / 服务挂了** → 重建。
2. **服务器在、服务在，但这条路径到不了**（今天的端口级封锁）→ 换端口。
3. **服务器在、路径通，只是本机凭据是旧的** → 刷新凭据。

### 2.3 建议的判定分层（全部是诊断证据，不改测速口径）

| 层 | 证据 | 能排除什么 |
|---|---|---|
| L1 | 控制面查 DO：droplet 是否存在、状态是否 `active` | 排除「机器没了」 |
| L2 | 控制面用 `cloudflare:sockets` 从边缘连目标端口（待验证可行性） | 排除「服务没监听 / DO 防火墙没放行」——边缘通说明服务在 |
| L3 | 本机 TCP connect 到节点端口（只作诊断，不进 UI 延迟） | 区分「本机路径不通」与「机器不通」 |
| L4 | Clash delay（现有口径） | 端到端是否可用 |

判定组合：

- L1 失败 → 重建。
- L1 通、L2 通、L4 不通 → 路径问题（大概率端口被封）→ 走 agent 的 `rotate_credentials`（`node-agent-mcp.md`）。
- L1 通、L2 不通 → 服务/防火墙问题 → 报给用户，走重建或人工排障。
- L2/L4 通但本机凭据与 DO 侧不一致 → 刷新凭据（第 5 项）。

**注意**：L3 用裸 TCP 只用于「我们自己的判定」，结果一律不显示成延迟；UI 延迟仍只认 Clash delay（既有硬规则）。

### 2.4 待定

- 判定由谁执行：Mac 本地组合，还是控制面一次返回结论？（控制面更适合做 L1/L2）
- 自动修复的边界：用户点了「测速」不通就自动换端口，还是必须用户确认？自动换端口会改变所有设备的行为，倾向「提示 + 一键执行」。
- 每个节点多久判定一次？和第三项的同步周期是否共用？

## 3. 配置同步（定时 + 手动）

### 3.1 现状

- 手机端：客户端自己按订阅机制刷新（我们不可控，也没法配置）。
- 桌面端：**只在「本地没有节点行」时取一次凭据**（`useServerNodePooling`）。已经有节点行的服务器不会再取——今天端口改了之后，Mac 上那条记录一直是旧值，就是这个原因。
- 没有定时同步，没有手动刷新入口，间隔不可配置。

### 3.2 要做的

1. **手动刷新**：一个明确入口，立即拉一次服务器列表与凭据，更新本地节点。UI 位置交给界面组定（服务器列表 / 设置）。
2. **定时同步**：默认 30 分钟，间隔可在设置里改（建议档位：5 / 15 / 30 / 60 / 手动）。只在应用运行时进行。
3. **同步内容**：服务器状态、节点凭据（端口/密码）、节点池成员关系。**不**包括主动断开或重连——正在用的连接只在用户下次连接时使用新值，除非新凭据对应的就是当前节点且当前节点已不可用。
4. **失败语义**：拉取失败不删本地节点、不清密码；只记日志并保留旧值（与手机端「订阅拉取失败」一致）。

### 3.3 待定

- 定时器在应用挂起 / 睡眠后如何处理（醒来补一次？）
- 同步发现端口变化时，是否给一次轻提示（「新加坡节点已更新到新端口」）？
- 与第 2 项的自动判定合并成一个「健康检查 + 同步」的周期任务，还是两条独立定时？

## 4. 销毁验收（共享防火墙模型）

> 共享防火墙（`shared-firewall.md`）落地后，建机不创建防火墙、销毁不删防火墙。这里只验证这一点。

1. 新建一台服务器：DO 上**不出现**新的防火墙；该 Droplet 的 Firewalls 显示 `veyl-nodes-<env>`。
2. 在应用里销毁它：Droplet 消失，`veyl-nodes-<env>` 仍在，其 Droplets 列表为空。
3. 连续建、销 2–3 台：始终只有一条 `veyl-nodes-<env>`。
4. 不做定时清扫（已否决：启发式删云资源，误删会让在线机器裸奔）。

## 5. 讨论：节点没有密码

### 5.1 澄清（2026-11-21）

产品负责人确认：第 5 项指的是**服务器没有 root 密码、也没有开放 SSH 端口**这件事——即「人怎么进机器」，不是「节点凭据缺失」。本节先记录现状，细节后续单独讨论。

### 5.2 现状

- 建机时不设置 root 密码（cloud-init 不写 `chpasswd`），也不注入 SSH key。
- SSH 服务在 cloud-init 第一步被 `stop + disable`；DO 防火墙只放行节点端口 + ICMP，不放行 22。
- 因此常规手段进不去；只有 DO 网页控制台（需先 Reset Root Password）可以。
- 本次排障就是走这条路改的端口：属于人工、带外操作，产品里不提供。

### 5.3 要讨论的

1. 要不要给「我们自己的运维」一条受控入口（而不是每次都走 DO 控制台 + 重置密码）？
2. 这条入口与 `node-agent-mcp.md` 的 agent 是什么关系：agent 是否承担「受控运维」的角色？
3. 安全边界：怎样的入口不会变成对用户开放的 root 通道。

## 6. 建议的实施顺序

1. **共享防火墙 + 端口带**（`shared-firewall.md`）：它是端口轮换能被放行的前提，改动集中、可独立验证。
2. **第 3 项**（同步）：把「值能更新」打通，否则轮换在桌面上落不了地。
3. **节点 agent**（`node-agent-mcp.md`）：机器侧的安装者与管理器，先做出站登记与命令执行，再接 MCP 端点。
4. **第 2 项**（判定）+ 桌面端「智能修复」：判定输出结论，调用 agent 的工具。
5. **第 4 项**（防火墙验证）：共享防火墙落地后按 `shared-firewall.md` §7 验证。
6. **第 5 项**（机器访问）：单独讨论，不阻塞以上。

## 7. 仍然开着的设计约束

- 用户侧没有 SSH：机器上的管理通道由 `node-agent-mcp.md` 的 agent 提供，不再依赖人工登录。
- 测速只认 Clash delay，`ok / unreachable / untested` 三态；裸 TCP / ICMP 只能作内部诊断证据。
- 不做定时清扫云资源；共享防火墙（`shared-firewall.md`）落地后也不再需要按机器删防火墙。
- 界面文案与入口位置由界面组定，本文只给能力与语义。
