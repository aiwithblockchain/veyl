# Veyl 用户分层与需求层级

> 建立：2026-11-03，产品负责人口述，项目经理记录。
> 关联：`docs/phase-1-5-requirements.md` §8.6、`docs/user-flows.md`

---

## 0. 本阶段的定稿原则

**底层实现可以按规划走，前端界面与业务流程必须现在定死。**

本阶段交付的是**界面与流程的最终形态**，不因为后端能力未就绪而简化、也不允许再改方向。凡是流程里出现的能力，一律按「已具备」设计界面；后端补齐是后续工作。

---

## 1. 两个需求层级

| 层级 | 内容 | 典型场景 |
|---|---|---|
| **一级需求** | 通过浏览器访问国外网站 | ChatGPT 网页版 |
| **二级需求** | 在**桌面客户端软件**里使用国外服务 | Codex 桌面版、Claude Code、Google 邮箱 / 会议桌面 APP、游戏客户端 |

二级需求的共同点：都是**独立的桌面应用**，不是浏览器。

---

## 2. 四类用户

| 层级 | 定义 | 对应需求 | 会不会配 proxy | 产品手段 |
|---|---|---|---|---|
| **一级用户** | 普通用户，**不会**配置代理 | 一级需求 | 不会 | 系统代理即可覆盖浏览器，全自动 |
| **二级用户** | 电脑操作人员，**不会**配置代理 | 二级需求 | **不会** | **TUN 模式**，全自动 |
| **三级用户** | 懂网络设置，**会**配置代理 | 一级或二级需求 | **会** | 连接方式与分流由他选 |
| **四级用户** | 自己搭建 VPN 服务器节点，提供给他人使用 | 二级需求 + 供给 | 会 | 节点创建与发布引导（见 §4） |

**分类由能力决定，不由需求决定。** 同样的「只用浏览器」，不会配的人是一级，会配的人是三级——因为我们给他的东西完全不同：一级只拿到一个已配好的系统代理，三级还要选连接方式与分流规则。

### 2.0 两次能力提问

| 需求（第一问） | 能力（第二问） | 结果 |
|---|---|---|
| 仅网页 | 不了解 TUN / proxy，也不想自己改 | 一级 |
| 仅网页 | 了解并能自己配置 | 三级 |
| APP 也要 | 不会配 APP 的 proxy | 二级 |
| APP 也要 | 会配 | 三级 |

两条线判定为三级之后，后面问完全相同的内容。详见 `docs/user-flows.md` §2.2。

### 2.1 为什么二级用户只能走 TUN

当前 proxy 模式的做法是把系统代理指向本地端口。问题在于：

- 浏览器、部分 GUI 应用读系统代理，能用。
- **独立的桌面客户端不读**：Electron 应用、自带网络栈的软件、命令行工具（git / npm / curl 等，已实测）都不会自动走系统代理。
- 二级用户**不会**去软件设置里手动填代理，也不会设环境变量。

结论：对二级用户，proxy 模式等于不可用。**TUN 是唯一不需要用户配合的方案**。

### 2.2 三级用户自己选连接方式

三级用户会在客户端软件里配置 SOCKS/HTTP 代理，也会设环境变量（例如 `https_proxy=http://127.0.0.1:<port>` 后 `git push`）。

对他们，proxy 模式够用，而且比 TUN 更可控——只影响他们指定的软件。所以**默认给 proxy**，但由他确认，不替他定死。

### 2.3 三级用户也常常需要 TUN

典型例子：**Claude Code 按 IP 封锁中国账号**。这是按归属判断的，用户只要全部流量出口在国外就能绕开，需要的是**全流量**（含 CLI 与后台进程），TUN 比逐个软件配代理更省事、也更有效。

所以第三问「TUN 还是 proxy」对三级用户是必须问的，不能按「会配 proxy」推断他想用 proxy。

### 2.4 二级与三级的边界是「能力」，不是「目标」

- 游戏玩家要桌面 APP 走代理：会配的是三级，不会配的是二级。
- 同一类需求，因能力不同落到不同手段。**不要按「写代码的 / 玩游戏的」分类。**

---

## 3. 一级与二级的界面差异

一级与二级在**用户操作上完全一致**：打开、点连接、直接用，零配置。
差异只在其后：一级只需要浏览器通；二级要保证所有桌面客户端都通（TUN）。

因此产品**不需要让用户理解 proxy 与 TUN**。用户要做的是选择「我要让什么能用」，不是选技术模式。

三级用户才需要看到代理地址与配置方式。

---

## 4. 四级用户的能力边界

四级用户：**自己搭建 VPN 服务器节点，并提供给别人使用。**

Veyl 在这条链路上承担的是**引导与校验**，不是代替用户操作。能力边界如下。

### 4.1 Veyl 做

| 环节 | Veyl 做什么 |
|---|---|
| 选服务商 | 引导用户到合适的网站（VPS / 节点服务商），不该由用户自己找 |
| 读懂页面 | **感知网页内容**，把当前页面讲清楚：这一步在选什么、价格与配置差异、哪些选项有影响 |
| 创建节点 | 按步骤指导用户完成节点创建，并在关键字段上给出填写建议与校验 |
| 获得收益 | 指导用户通过智能合约收款，讲清收益来源与风险 |
| 发布节点 | 生成可发布的节点信息，指导用户完成发布，让其他人能用上 |

### 4.2 Veyl 不做（边界）

- 不代替用户注册账号、不代替付款。
- 不托管用户私钥，不代替用户签署合约。
- 不承诺收益，不对节点可用性与合规性做担保。
- 不提供通用浏览器自动化：**只在引导流程内的特定步骤感知页面内容**，不做任意网址的抓取。

以上四条是产品边界，具体实现方案由产品负责人后续给出。

### 4.3 与一/二/三级的关系

四级用户同时也是二级需求用户——他们自己也用这些服务。
因此四级不是「另一条产品线」，而是**在正常使用之上多一条「提供节点」的引导流程**，入口在设置页，不影响主流程。
