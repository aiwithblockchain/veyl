# 升级方案

> 日期：2026-11-03
> 参照：TweetPilot 的实现（`src-tauri/src/commands/updater.rs`、`src-tauri/src/services/prompt_templates.rs`、`scripts/assemble-update-manifest.py`）
> 原则：**用户不需要知道有升级这回事。**

---

## 1. 两类升级，分开做

| | APP 本体 | 预置资源 |
|---|---|---|
| 包含 | 安装包、sing-box 运行时 | 提示词、默认配置模板、规则集、分类目录 |
| 频率 | 周 / 月 | 提示词随 APP；规则集约每日 |
| 方式 | Tauri 官方 updater | **独立于 APP 版本的资源同步** |
| 生效 | 重启应用 | 下次启动 / 下次连接 |

分开的理由：改一句提示词不该逼用户重下一整个安装包；而 sing-box 升级必须跟 APP 一起验证，不能单独推。

---

## 2. APP 本体升级

照 TweetPilot 的做法，**只简化一处**。

| 项 | 做法 |
|---|---|
| 方案 | `tauri-plugin-updater` 2.0 |
| 签名 | minisign，公钥写进 `tauri.conf.json`，私钥只在发版机器上 |
| 检查时机 | 启动后延迟若干秒静默检查；之后每天一次 |
| 提示 | 有更新时在侧栏与设置页出一个小条，**不弹窗**，不打断 |
| 用户动作 | 点「立即更新」，显示进度，完成后重启 |
| 版本号 | `tauri.conf.json` / `Cargo.toml` / `package.json` 三处，脚本同步改 |

### 与 TweetPilot 的差异：不搭服务端

TweetPilot 自建了 Cloudflare Worker 做清单与下载代理。我们**没有自定义域名**（约束已定），所以：

**直接把 updater 的 endpoint 指向 GitHub Releases 的 `latest.json`。**

```
https://github.com/<owner>/<repo>/releases/latest/download/latest.json
```

这是 Tauri updater 原生支持的静态清单，不需要服务端，也不需要发版脚本重写任何东西。

**已知风险**：GitHub 在国内**时通时不通**——封是按 IP 封的，解析到没被封的 IP 就通，解析到被封的就超时。所以：

- 检查失败**不提示、不留痕迹**，但外层必须重试：**最多 3 次**，带退避，全程用户无感
- **每次重试都发起新的请求**，不复用同一条连接——系统会重新解析 DNS，换一个 IP 就可能通。不要去手写解析逻辑
- 三次都失败才在本地日志留痕：**域名 + 解析到的 IP + 错误类型**，下一轮自然再试；**不做无限重试**（后台检查不值得烧电池）
- **代理是兜底路径，不是唯一路径**：直连能通就直连，不通再走代理
- 设置页给一个手动入口：「从官网下载最新版」，走系统浏览器
- 升级本身不是救命通道。真正的自救是 E3 重置网络（`docs/capabilities.md` §3），它不依赖任何网络

## 3. 预置资源升级

### 3.1 双层结构

```
随包基线（离线可用）  +  在线增量（联网后覆盖）
```

第一层是 `docs/user-flows.md` §1.3 已经定下的离线原则：用户打开产品那一刻网络恰是坏的，不能要求他先联网才有资源。

第二层是 TweetPilot 的 `prompt_templates.rs` 模式。

### 3.2 清单

每个资源类别一份清单：

```json
{
  "version": 12,
  "items": [
    { "id": "prompts/zh/system", "version": 7, "sha256": "..." },
    { "id": "config/default-tun",  "version": 3, "sha256": "..." }
  ]
}
```

- **逐条版本**，不是整目录版本。整目录版本会导致「改了一条提示词，所有资源全量重下」，也让漏 bump 变成全局事故
- **带 `sha256`**。TweetPilot 没有做资源校验，只签了安装包——从网络下载的提示词是可被中间人替换的，而提示词直接决定 AI 的行为

### 3.3 同步

| 项 | 做法 |
|---|---|
| 时机 | 启动 5 分钟后首跑，之后每小时 |
| 比对 | 按 `id` 逐条比版本号，不等的才下载 |
| 写盘 | 先下到临时目录 → 校验 sha256 → 原子替换 |
| 失败 | **逐条隔离**：一条失败不影响其它条，磁盘保留旧文件，清单保留旧版本号，下轮重试。网络类失败在当轮内也要重试，且**每次重新解析 DNS**，不复用上次的 IP |
| 清单损坏 | 删除并全量重拉 |

### 3.4 只向前，不回滚

**不做用户可见的回退。** 没有「回到上一版提示词」的按钮，没有问题提示用户「新版本可能不稳定」。

本地在新版本校验通过之前保留旧文件，这是**原子切换**，不是回滚能力——切换失败就继续用旧的，用户无感。

理由：提示词是产品资产，用户没有判断两版提示词优劣的信息，给他一个回退按钮只会制造焦虑。

### 3.5 例外：默认节点的种子包

`veyl_seed.json` **不走随包基线**，只从 `meshnetprotocol.github.io` 拉取并缓存。原因见 `docs/config-execution.md` §9——打包进安装包的节点凭据会被提取滥用。

它**只含节点**，421 字节，由 4.6KB 的 `bootstrap.json` 抽取而来。**分流规则不进种子**——那是 AI 在对话里问出来的用户偏好，覆盖种子时不能动它。

文件很小，变更检测直接比对内容哈希，不依赖手写的 `version` 字段。

## 4. 生效时机

| 资源 | 何时生效 | 为什么 |
|---|---|---|
| 提示词 | **下次启动** | 对话中途换人格最让人困惑 |
| 规则集 | **下次连接** | 路由配置不能热重载（`docs/user-flows.md` §1.4） |
| 默认配置模板 | 下次新建面板 | 不改变用户已有的面板 |

**不为生效而重启用户的连接。** 下载好、存好、等下一次自然发生的机会。

### 4.1 例外：TUN 用的 sing-box 只认随包那一份

TUN 的运行时由特权 helper 执行，而 helper **只执行随 App 签名分发的那一份**。
`start` 请求里不带任何运行时标识，helper 用编译进自己的完整 sha256 校验，
文件来自 `Contents/Resources/runtime/sing-box`。

后果：**后台升级的运行时不会反映到 TUN 上**，要等下一次 App 本体更新。

这不是 bug，是刻意的。让 helper 接受「App 说有新版本」等于让它执行一个
它不是从自己签名过的包里拿到的二进制——那正是两轮评审反复打回的那类问题
（见 `docs/tun-privilege.md` §1）。如果将来确实需要运行时独立升级，
必须另外设计一份**签名清单**，而不是放宽这条约束。

## 5. 必须自己写的（TweetPilot 没有）

| 缺口 | 为什么要补 |
|---|---|
| **资源签名 / 校验** | TweetPilot 只对安装包做了 minisign，资源文件裸传。我们的提示词决定 AI 行为，必须校验 sha256，清单本身也应签名 |
| **构建期版本校验** | TweetPilot 有过「忘了 bump 版本号，老用户永久停在旧版」的事故（其 `docs/update-helper-requirements.md:27` 有记录）。构建时比对资源目录内容 hash 与清单版本，不一致就让构建失败 |
| **离线基线** | TweetPilot 是纯线上拉，我们有首启无网的硬约束，必须随包基线 |
| **GitHub 时通时不通的降级** | 封是按 IP 封的，解析到不同 IP 结果不同；必须重试并每次重新解析，代理只做兜底。TweetPilot 用自建 Worker 绕开了这件事，我们绕不开 |
