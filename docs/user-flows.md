# Veyl 业务流程（本阶段定稿）

> 日期：2026-11-03
> 定位：界面与业务流程的最终形态。底层能力未就绪的部分一律按「已具备」设计。
> 依据：`docs/user-segments.md`

---

## 0. 核心原则：智能优先

**先让产品获得智能 → 智能去获取节点 → 建立网络连接。**

连接不是用户手动点出来的结果，是 AI 完成之后的产物。
对应地，产品的主入口是「配置 AI」，不是「点连接」。

---

## 1. 首次启动：一屏，三个入口

```
                    Veyl

        配置 AI 后，我来帮你连上网络。

        ┌──────────────────────────────────┐
        │  DeepSeek API Key                │
        │  sk-________________________     │
        └──────────────────────────────────┘
              [ 保存并验证 ]

      获取 DeepSeek API Key ↗   使用其他 AI 服务 →

        ────────────────────────────────────

        [ 使用 Google 登录 ]

        [ 我懂网络，不用 AI ]
```

| # | 入口 | 面向谁 | 进去之后 |
|---|---|---|---|
| 1 | 配置 AI API（默认展开） | 大多数用户 | AI 主动获取节点并建立连接 |
| 2 | 使用 Google 登录 | 有 Veyl 账号的用户 | 同上；账号体系后续接邮箱注册与付费 |
| 3 | 「我懂网络，不用 AI」 | 三级、四级用户 | 直接进主界面，手动操作网络 |

- 三项在**同一屏**，不分成多步向导。
- 第 1 项是视觉重点；第 2 是次按钮；第 3 也是按钮，但用最轻的样式，位置在最下面。
- 第 1 项下方有两个次要动作：`获取 DeepSeek API Key ↗`（系统浏览器打开 `https://platform.deepseek.com/`，不内嵌）与 `使用其他 AI 服务 →`（自定义表单）。

### 1.1 自定义 AI 服务表单

点「使用其他 AI 服务」展开：

| 字段 | 说明 |
|---|---|
| API 类型 | OpenAI 兼容 / Anthropic 兼容 |
| Base URL | 自定义地址 |
| 模型 | 如 `deepseek-chat`、`claude-sonnet-4-6` |
| API Key | 该端点所需的 Key |

DeepSeek 主路径只是这个表单的预设：OpenAI 兼容 + `https://api.deepseek.com` + `deepseek-chat`。两条路共用同一套保存与验证逻辑。

- 验证成功 → **自动进入第二页**，与主路径行为一致。
- 验证失败 → 留在原页，不清空输入，旁边给出可读原因。

### 1.2 第三个入口的文案

用 **「我懂网络，不用 AI」**。

它是一句自我识别，不是功能描述。不用「跳过」（像在挽留）、「高级模式」（让人怀疑自己不够格）、「开发者」（暗示这是残缺版）。
备选：`不需要 AI，我自己管网络`。

## 1.3 进入第二页之前：资源就位（不联网）

**全部资源随安装包预置。首次启动不需要任何网络。**

| 资源 | 形式 | 联网后 |
|---|---|---|
| sing-box 运行时（约 80MB） | **压缩随包**，首启解压 | 可后台升级 |
| 默认配置包 | **种子随包** | 后台刷新 |
| 分流规则集（< 500KB） | **随包** | 后台更新 |

- 首启只做解压与校验，预计一两秒，不是下载页。
- 不存在「下载失败」这条路径，也不需要断点续传、重试、镜像切换。

**唯一例外：默认配置的种子包**（含节点与默认分流规则）。它从 `https://meshnetprotocol.github.io/bootstrap.json` 拉取，不随包——因为安装包是公开下载的，打包进去的节点凭据会被提取滥用。拉取后落盘缓存，只有第一次启动需要网络；拉不到时给「重试 / 手动添加节点」。详见 `docs/config-execution.md` §9–10。

### 产品原则：离线启动

> **一个用来解决网络问题的工具，不该要求你先有网才能用。**

这条决定了上面三项必须预置。理由是一条死锁：

> 没装 sing-box → 起不了运行时 → 连不上 → 下不动 sing-box。

默认配置包与规则集同理：它们都要从 GitHub 拉，而目标用户打开产品的那一刻，网络恰恰是坏的。下载方案对最需要它的人最不可用。

**代价**：安装包增大约二三十兆（二进制压缩后）；sing-box 的基线版本跟 App 版本走，联网后可后台升级覆盖。

**许可证**：sing-box 与规则集都是 GPL-3.0-or-later。以独立进程方式调用、不链接进自身代码，属聚合分发，义务是随包附许可证与源码获取声明。

## 1.4 分流设置：四步

**「国内」是一个相对于用户所在国家的说法**，不是指中国。对中国的用户是「中国大陆直连」，对美国的用户是「美国直连」。规则必须按用户所在国家生成，不能写死成 CN。

| 步骤 | 做什么 |
|---|---|
| **1** | **检测所在国家**，把结果显示给用户确认（「你现在在中国大陆，对吗？」） |
| **2** | 加载 geosite 分类的**描述文件**作为 AI 的参考；**精选一套随包预置**，保证没有 VPN 时也能用 |
| **3** | 如果用户的需求没命中精选，先用随包的默认配置**建立连接**，再下载缺的那部分分类 |
| **4** | 根据已确认的地区，给出该地区的分类**推荐**，用户确认后再确定：走 proxy 还是 TUN、是「本地直连其余走 VPN」还是「目标走 VPN、其余直连」 |

第 3 步是关键设计：**用已经能连上的预置配置，去换那些连上之后才能下的东西**。这样长尾需求不会因为「没网下不了」被卡住。

### 用户看到的选择

不列规则文件名，只问意图：

```
你希望哪些流量走 VPN？

○ 本地网站直连，其他都走 VPN      ← 最常用，本地网站不变慢
○ 只有我指定的服务走 VPN          ← 只想访问 ChatGPT、Google 这类
○ 全部走 VPN                     ← 最简单，但本地网站会变慢
```

用户选完，AI 把意图翻译成规则集组合。他永远不需要知道 `.srs` 是什么。

### 决策（2026-11-03）

| # | 决定 | 理由 |
|---|---|---|
| 1 | **规则数据全量预置**（2.25 MiB / 2,233 文件） | 体积可忽略，换来流程里彻底没有「下载规则」这一步，长尾需求不卡 |
| 2 | **只有中国用户提供「本地直连」**；其它国家默认「目标分流」或全局 | 按国家的网站列表只有中国有，其它国家只能 IP 层近似，会双向误判，不如不承诺 |
| 3 | 分类描述文件**由我们自己生成**，配套一个 AI 工具支持下载更新与生成 | 上游只发 `.srs`，没有清单与描述 |

数据打包成归档随包，首启解压；运行时**按需加载**（用户所在国家 + 目标国家 + 少量共享分类），不全量加载——全量 2,233 套外推常驻 200MB+。

### 规则数据怎么更新

| 环节 | 做法 |
|---|---|
| 基线 | 随包快照，记录 `geosite` tag（形如 `20261102203016`）与 `geoip` tag（形如 `20261012`） |
| 检查 | 已连接时后台比对上游 tag。**源在国内不可达，必须走代理下载** |
| 下载 | 下到临时目录，校验 sha256，不直接覆盖 |
| 切换 | 解压到新的版本目录后原子切换；保留上一版用于回滚 |
| 生效 | 路由配置不能热重载，所以**下次连接生效**，不打断当前连接 |
| 失败 | 静默保留基线版，不打扰用户 |

频率参考：geosite 约每日、geoip 约每月。过期阈值：geosite 超 3 天、geoip 超 35 天时在设置页提示可更新。

### 技术结论（Bob 实测 1.14.4）


- 两种方式是**同一套机制**（`route.rule_set` + `rules` + `final`）的不同配置，不是两套实现。
- **用超集规则 + selector 实现免重启切换**：把两种方式需要的规则放进同一份配置，切换时只调 selector（实测 204，新连接立即生效），**不断流**。
- `geoip` / `geosite` 已在 1.12 移除，只能引用 `.srs` 规则集。
- `download_detour` 在 1.14 弃用、1.16 移除，改用 `http_clients`。
- 路由配置**不能热重载**（`PUT /configs` 返回 204 但不生效、SIGHUP 被忽略），只有 selector 可热切。

### 规则数据更新

- 规则集随包预置一份，联网后后台更新，用户无感。
- 频率参考：geosite 约每日、geoip 约每月。判断过期建议阈值：geosite 超 3 天、geoip 超 35 天。
- 记录 `URL + fetched_at + sha256`，用于判断是否更新。
- 许可证：规则集是 **GPL-3.0-or-later**，随包分发需附带许可证与来源声明。

### 配置过程中的动画（待定）

规则集预置之后，「下载动画」没有下载可藏了。它还剩两个可能的价值：掩盖生成配置、启动运行时的那一两秒，或作为「正在按你的情况配置」的过渡。**是否保留、改成什么形态，待产品负责人确认。**

## 2. 第二页：主界面的三段结构

| 位置 | 内容 | 状态 |
|---|---|---|
| 左侧 | 最外是 activity bar，现阶段**只有「客户端」一项**；里面是**配置列表**。不放对话历史 | **已确定** |
| 中间 | 上中下三段固定骨架，只有中间那段由 AI 编排，见 `docs/center-panel.md` | **已确定** |
| 右侧 | AI 对话页 | **已确定** |

**最左侧是 activity bar**（客户端 / 服务商 / 自建节点），**左栏是配置列表**——配置的切换入口在这里，不在中间区域顶部。一套配置 = 一套完整方案，切换配置就是切换连接方式与分流，见 `docs/configs-and-nav.md`。

对话历史不放在左栏，收进右侧 AI 面板的二级页面。

### 2.1 右侧 AI 面板（已确定）

#### 结构

```
┌─────────────────────────────────────┐
│ ‹ 标题                  ＋  ☰  ⚙    │  ← 头部
├─────────────────────────────────────┤
│                                     │
│              消息流                  │
│                                     │
├─────────────────────────────────────┤
│  输入框                          ↑  │
└─────────────────────────────────────┘
```

一个一级界面（对话）+ 两个二级页面（会话列表、AI 设置），**都在面板内部整页切换，不弹层**。

不弹层的理由：400px 宽度里弹层太挤；而且会话列表本质是「换个视角看同一个面板」，不是一次打断式的操作。

**头部**：左为返回箭头（在一级界面时不显示）与当前会话标题；右为`＋新建`、`☰ 历史`、`⚙ 设置`。

**一级 · 对话**：消息流 + 输入框。沿用现有 ChatView 的渲染（消息、工具卡、思考块、Markdown），不改逻辑。

**二级 A · 历史会话**：点 `☰` 进入，面板内整页切换。列表项显示标题与最后时间，点击切换；悬停出现删除；改名沿用现有的双击进入编辑。`＋`新建会话。

**二级 B · AI 设置**：点 `⚙` 进入。显示当前服务商与掩码后的 Key、`更换`、以及 `使用其他 AI 服务` 的完整表单（字段同 §1.1）。

#### 未配置 AI 时

- 面板顶部常驻一条提示：`还没有配置 AI，现在只能手动操作网络。 [去配置]`
- 输入框仍可输入。**点发送时若仍无 Key，直接打开 AI 设置页**，不报错、不吞掉用户已输入的内容。
- 输入框内容保留，配置完成后可继续发送。
- **选了「我懂网络，不用 AI」的用户，这个面板仍然保留**：可以打开，打开就是上面这条提示，随时能补配。不隐藏——否则以后想接 AI 就找不到入口。

#### 自动打开规则（硬要求）

1. **首次配置 AI 成功后，右侧对话自动展开**，AI 主动办第一件事并报告结果，让用户看见「配完就能用」。
2. 用户手动关闭过之后，不再自动打开。
3. AI 在面板关闭期间有新动作或新消息时，顶栏的 AI 按钮显示一个小圆点。

#### 宽度与开关

- 默认 400px，可拖拽 360–560。
- 开关与宽度记入 `localStorage`。
- 窗口过窄时改为覆盖式浮层，Esc 关闭。

#### 与中间的边界

右栏**不做网络操作**，中间**不做对话**。唯一的交叉是：AI 执行网络动作时，结果在中间可见，右栏只负责解释。

### 2.2 配置完成后的第一步：AI 主动开局

进入第二页时，**右侧 AI 对话立即展开并成为焦点**。用户第一眼看到的是一个已经在工作的助手，不是一张空界面。

**第一条消息分三段：**

**第一段 · 身份与能力**
说明自己是谁、能做什么：帮用户配置和管理 VPN，并能根据需求修改配置。一句话说清，不铺开介绍功能。

**第二段 · 检测前的确认**
立即执行环境检测，但**先确认用户当前是否已经开着别的 VPN**。

> 检测到你现在有一个 VPN 正在运行。先把它停掉再检测，否则测出来的出口和线路都不是真实的。
> 停好之后告诉我。

理由：别的 VPN 开着时，出口 IP 与路由不代表真实情况，基于它做的国家判断和分流配置都会错。用户确认停掉之后再继续。

**检测其它 VPN 只在这一刻做一次。** 它是定位环节的一次性采样，不是常驻监控——之后就再不检查了。理由：用户之后开什么我们无权干涉，持续报警只会变成噪音。

**先看离线信号，不要一上来就让用户停 VPN。** 时区与区域设置（`H1`）不联网就能给出国家，且不受 VPN 影响。顺序是：

1. 离线信号能确定国家 → 直接确认，**不打扰用户**
2. 离线信号与出口 IP 不一致 → 才是「可能开着 VPN」，这时才提示
3. 两者都不确定 → 直接问用户

这样只有真正存在冲突的人才会看到「先停掉 VPN」这句话，而这类人停下之后大概率**还有本地网络可用**（他本来就有一层联网能力）。

**第三段 · 检测结果与提问**

检测只做一件事：**确定加载哪个规则文件**（`geoip-cn` + `geosite-cn` 域名级，或 `geoip-<cc>` IP 级）。它不直接变成给用户看的选项。

检测完成后问**第一问（单选）**，它只区分**需求**：

```
1. 仅使用网页浏览网站
2. APP 也需要使用 VPN
3. 我要自建 VPN 节点
4. 其它服务
```

| 选择 | 去向 |
|---|---|
| **1** | 进入**一级线**第二问 |
| **2** | 进入**二级线**第二问 |
| **3** | 四级。**本期不开发**，实现时可不显示该项 |
| **4** | 让用户描述具体需求，由 AI 理解 |

需求不决定用户类型，**能力才决定**。所以两条线各自再问一次能力：

### 一级线（第一问选 1）

```
你会自己设置网络代理吗？

1. 不会，也不想自己改
2. 会，我自己来
```

**不要在这里出现 TUN、proxy 这些词。** 选「仅浏览网页」的人看到技术名词会以为自己走错了门。问的是他能做什么，不是他知道什么。

| 选择 | 类型 | 后续 |
|---|---|---|
| **1** | 一级 | 直接生成配置，**不再提问** |
| **2** | 三级 | 进入共同追问 |

**为什么一级也要问这一句**：一级里藏着三级。只用浏览器的人完全可能是程序员，给他系统代理不算错，但我们从此不再问他——哪天真要用 Claude Code，还得从头来一遍。

### 二级线（第一问选 2）

```
你自己会配置 APP 里的 proxy 代理吗？

1. 不会
2. 会
```

| 选择 | 类型 | 后续 |
|---|---|---|
| **1** | 二级 | **TUN 全自动接管**。首次要求系统授权，必须用一句人话解释 |
| **2** | 三级 | 进入共同追问 |

### 三级 · 共同追问（两条线合流）

判定为「懂网络」之后，后面的问题**完全一样**，不关心他最初是为了浏览器还是 APP。

**第三问 · 连接方式**

```
1. 全部软件自动走 VPN
   我接管整个网络，你不用配任何东西

2. 只给我一个代理地址
   我自己填到需要的软件里
```

内部实现分别是 TUN 与 proxy，**界面上不出现这两个词**——会设代理不等于知道 TUN 是什么。同一条文案规则贯穿整个流程。

### 选「只给我一个代理地址」之后给什么

中间区域给一张卡：

```
代理已经开好

127.0.0.1:7890                  [ 复制 ]

在软件的代理设置里填这一组即可
HTTP 和 SOCKS5 都支持
```

**三条硬规则：**

| 规则 | 原因 |
|---|---|
| **单端口双协议** | sing-box 的 `mixed` 入站一个端口同时吃 HTTP 与 SOCKS5，用户不用判断「这个软件要哪种」 |
| **只听 `127.0.0.1`，不给局域网开关** | 开放到局域网等于把本机变成公共代理，同网段的人不经同意就能用你的出口，在公司/学校网络里还可能违规。给手机、虚拟机用的属于四级场景，让他自己改配置 |
| **端口避开常用号** | 不收 `1080` / `7890` 这类被其它代理软件占用的端口。被占用时自动换下一个，并**如实显示实际端口**，不能卡片写一个、实际跑另一个 |

系统代理同时设好（同 `docs/user-flows.md` 的确认文案），所以浏览器立刻可用，他只需要补剩下那几个软件。

**第四问 · 分流**

```
1. 本地网站直连，其它走 VPN
2. 全部走 VPN
3. 只有我指定的服务走 VPN，其它直连
```

选 3 时继续问：**哪些服务？**

用户给服务名即可（如「ChatGPT」「Claude Code」「公司 OA」），AI 用分类目录（能力 `I1`）反查它的域名与 IP 段，**查不到的才让他自己补**。不让懂网络的用户手打域名，是省他时间，不是看不起他。

> 五问全部通过 Claurst 的 `AskUserQuestion` 通道下发（单选、选项按钮、答案回传给模型），不用「看起来像问题、实际只是发一条消息」的假按钮。契约见 1.2.0 的 `ask-user-question` 事件与 `reply_user_question` 命令。

### 为什么按能力分而不按需求分

需求只决定「要不要连」，能力决定「谁来配」。同一个「APP 也要用」的需求，会配的人自己填端口就行，不会配的人必须我们全接管——**给出的东西完全不同**。

所以问法两头都是可执行的：说「会」的人我们给他地址和端口，说「不会」的人我们替他做完。没有一个分支需要用户再学新东西。

### 三级用户的回退路径

用户说「我会配」，实际配不好是常事。所以三级用户的界面上要有随时能转 TUN 的入口：**配不通的时候，AI 主动提一句「要不要我全自动接管」**，而不是让他卡在那里。

反过来也成立：二级用户如果后来表现出想自己调，同样可以转 proxy。类型是入口处的判定，不是终身标签。

### 路由与出口是两件事

- **路由**决定哪些流量进隧道（本地直连、哪些走 VPN）。本环节只定这个。
- **出口**在服务器配置里，由后续的节点选择 / 供应商市场决定。跟路由无关。

所以「本国直连 + 其余走 VPN」对任何国家的用户都成立——日本用户的出口可以放在德国，也可以放在中国，那是后面的事。

### 写配置之前必须让用户确认

AI 决定之后**不直接落盘**，先用用户能懂的话说出来：

```
我准备这样配置：

· 用系统代理，不改动你的网络结构
· 日本网站直连，其它都走 VPN
· 之后随时可以修改

[ 就这样 ]   [ 我想改 ]
```

- 用户点「就这样」→ 才写配置文件、建立连接。
- 用户点「我想改」→ AI 给出可改的几项（只让某些网站走 VPN / 全部走 VPN / 换成本地全走代理），改完再说一遍，直到确认。
- 文案里不出现 proxy、TUN、分流、规则集这些词。用户看到的是「不改动你的网络结构」「日本网站直连」。

**为什么要有这一步**：配置是我们替他做的决定。不告诉他，他不知道发生了什么；不给他改的机会，他觉得被摆布。说出来只要一句话，但这一步决定了他是「用了一个工具」还是「被工具安排」。

**TUN 模式的确认多一句内网网段**：

```
我准备这样配置：

· 接管全部网络，所有软件都会走 VPN
· 日本网站直连，其它都走 VPN
· 我只会绕开你当前所在的网段（192.168.1.0/24）
· 如果还有别的内网设备要访问，告诉我网段

[ 就这样 ]   [ 我想改 ]
```

那句网段来自**本机接口反推**，不是穷举。反推只能拿到本机所在的子网，用户其它位置的内网（公司、另一台机器）拿不到，所以要留一行让他补充。补充的存进本地偏好，下次沿用。详见 `docs/tun-mode.md` §6。

### 各类型的配置从哪来

| 用户 | 要不要提问 | 配置怎么定 |
|---|---|---|
| **一级** | 不问 | 系统代理 + 本国直连 + 其余走 VPN |
| **二级** | 不问 | **TUN** + 本国直连 + 其余走 VPN |
| **三级** | **问到底** | 连接方式与分流由第三、四问决定 |
| **四级** | — | 同三级，另给「提供节点」入口 |

| 用户 | 直连依据 |
|---|---|
| 中国 | `geosite-cn` + `geoip-cn` |
| 其它国家 | `geoip-<cc>`（IP 级近似） |

一级与二级**不需要回答任何分流问题**——检测到国家、走完能力那一问，配置就直接生成。三级是唯一会连续被问到四个问题的人，因为他确实有偏好要表达。

**为什么中国要两个文件**：`geosite-cn` 是域名清单但不全，只用它会有国内小站掉进「其余」被送进 VPN；加 `geoip-cn` 按 IP 兜底，服务器在国内就直连。

**三级选了 TUN 的，同样要走首次授权与内网网段确认**（见上）。选 TUN 与否不改变「谁来配」，只改变「接管范围」。

**出口不在这张表里**：上面只定了「哪些流量进隧道」。出口节点由后续的供应商市场决定，我们自己的配置作为默认兜底——那一步在后面讨论。

**TUN 模式的配置差异**（嗅探、DNS 劫持、内网排除、特权助手）见 `docs/tun-mode.md`。

**已知误差**：判断「本地站点」靠的是这两份文件，不是实时判断。国内小站没被收录会走代理（慢一点）；外国站在本地有服务器会直连（可能打不开）。后者对一级用户更显眼，AI 需要能接受「这个站打不开」的反馈并把它加进直连名单。



### 第一问选 3 的处理

四级用户本期不展开。实现时可以直接隐藏这一项；文档保留它，是为了后面接上时不用重新设计。


**贯穿全程**：第一条消息同时提供「点击连接尝试」入口，让用户先拿到价值再谈配置。

- 不要只说「你好，我是 Veyl 助手」这类没有信息量的开场。
- 第一个问题只问一个，不要一次抛一串。

中间区域此时**只保留一个按钮**（连接状态的那个主按钮），其余全部留白，由 AI 助手逐步配置。

这样做的两个好处：**能力边界收口**——中间能被 AI 改变的东西就是那几块预置块；**状态容易统一**——没有凭空出现的元素，连接状态只有一个来源。

问题怎么编排、每块显示什么内容，由产品负责人后续给出。

## 5. DNS 策略

TUN 模式下 DNS 查询也会被接管。处理不当会出现「显示已连接、网页打不开」，而且和路由故障长得一模一样，用户与我们都难以区分。

### 默认策略

| 域名类型 | 用哪个 DNS | 怎么走 |
|---|---|---|
| 本地（本国）域名 | 本国 DNS，**2–3 个候选**（运营商 + 公共，如运营商 DNS、`223.5.5.5`） | 直连解析 |
| 其它域名 | 境外 DNS，**2 个候选**（如 `1.1.1.1`、`8.8.8.8`） | **经代理查询** |
| 局域网 / `.local` | 本地 DNS | 不接管、不经过隧道 |

- **DNS 泄漏默认不防**：不为隐私多绕一圈。二级用户要的是好用和快，不是匿名。
- 候选之间尽量都能用，具体哪个生效由 AI 修改配置决定。

### 硬约束：分类必须同源

**DNS 分流用的域名分类，必须和路由分流用的是同一套。**

如果 DNS 认为某域名是国内的、解析出国内 IP，而路由认为它是国外的、把连接送进隧道，结果就是「解析对了、连错了」。

这条要落到代码，不能只写进提示词：**生成配置的地方必须只有一个分类来源**，DNS 规则与路由规则都引用它，不允许各自调一次分类函数。

### 5.2 失败处理：不做自动切换，做问题管理 + AI 定位

**已确认**：`dns.servers` 配多个服务器**没有原生失败切换**——只能按 `dns.rules` 和 `dns.final` 选一个，挂了不会自动换。配置层虽然能用 `evaluate` + `respond` 拼出顺序回退，但有副作用（NXDOMAIN 也会触发下一个）且不是官方特性。

**产品决定**：不追求自动切换，改成**问题管理 + 失败诊断**。

```
连接成功
   ↓
主动探测：DNS 能否解析 → 目标是否可达 → UDP 是否通 → 出口 IP 是否变化
   ↓
探测失败 → 登记到问题管理模块（本地，不依赖 AI）
   ↓
P0/P1 → 中间区域插「网络异常」卡（本地规则触发，不依赖 AI）
   ↓
用户点「让 AI 定位」→ 把结构化诊断包一次性交给 AI（新建或复用会话）
```

理由：自动切换只能覆盖「服务器挂了」这一类，而实际故障有 DNS 污染、解析到错误 IP、节点不支持 UDP、规则分类错误等等。**固定回退策略只能撞运气，交给 AI 看具体数据才有解。**

**中间这一层是独立模块**，不是一次性卡片。问题会被留存、计数、分级，重复出现时能告诉用户「这已经是第 3 次」。完整设计见 `docs/issue-management.md`。

**交出去的必须是结构化诊断包**，不能是一句「打不开」。至少包含：

- 连接状态、模式（proxy / TUN）、节点协议与能力（是否支持 UDP）
- 实际使用的 DNS 服务器与解析结果
- 路由命中了哪条规则、走的是直连还是代理
- 目标可达性、出口 IP 与直连 IP

**探测必须主动做**：用户打不开网页这件事浏览器不会告诉我们，只能靠自己的探测发现失败。

### 5.3 已知风险

运营商 DNS 有劫持历史，典型特征是把域名解析到广告页或 `127.0.0.1` / `0.0.0.0`。多个候选的价值在于——识别出这类异常之后，AI 可以换一个并改配置。

## 6. 与 Claude Code 桌面版的对应关系

| Claude Code | Veyl |
|---|---|
| 首次打开要求登录或填 API Key | 首次打开要求配 AI / Google 登录 / 明确选「不用 AI」 |
| 中间是对话 | **中间是网络操作台，对话在右侧面板** |
| 右侧面板按需出现 | 同样按需出现，但承载的是对话 |

差异原因：Claude Code 的工作对象就是对话，所以对话在中间；Veyl 的工作对象是网络，对话是助手，所以对话在右侧。
