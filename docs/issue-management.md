# 问题管理模块

> 日期：2026-11-03
> 适用：proxy 模式与 TUN 模式的**全部**连接问题
> 定位：介于「本地探测」与「AI 定位」之间的一层。没有它，问题只能一闪而过或者只能靠 AI。

---

## 1. 为什么单独做一层

连接出问题时，现在的做法是「插一张卡 → 点按钮 → 交给 AI」。这有三个缺口：

| 缺口 | 后果 |
|---|---|
| 问题不是一次性事件 | 同一个问题反复出现，用户每次都要重新描述，我们也看不出「这已经是第 5 次」 |
| 用户可能不想立刻处理 | 卡片一收起，信息就丢了，下次还得重测一遍 |
| 有些问题 AI 修不了 | 比如节点服务器挂了、账号失效。需要长期挂在那里被看见，而不是弹一次就消失 |

所以问题需要一个**有状态、可留存、可计数**的载体。这个载体就是本模块。

---

## 2. 三层职责

| 层 | 做什么 | 依赖 AI |
|---|---|---|
| **采集** | 探测与运行时事件 → 结构化问题记录 | **否** |
| **展示** | 中间区域插卡（仅当前阻塞项）+ 完整问题列表 | **否** |
| **转交** | 用户确认后，把记录连同诊断包一次性交给 AI 会话 | 是 |

**采集与展示完全不依赖 AI。** 网络坏了的时候 AI 大概率也不可用，这条路径要在断网状态下独立工作。

---

## 3. 问题记录

```
id            // 稳定标识，由 type + 目标构成
type          // dns_fail / no_route / udp_blocked / auth_failed /
              // tun_denied / helper_missing / probe_timeout / rule_stale / ...
severity      // P0 阻断 / P1 降级 / P2 提示
mode          // proxy / tun
first_seen    // 首次出现
last_seen     // 最近一次
count         // 出现过几次
evidence      // 结构化诊断包，见 §5
state         // open / handed_off / resolved / ignored
session_id    // 转交后的 AI 会话，用于回看与复用
```

**同类问题不新建记录**：`type` 相同就在原记录上 `count + 1`、刷新 `last_seen`、状态若已 resolved 则重开。

---

## 4. 分级与展示位置

| 级别 | 定义 | 中间区域 | 问题列表 |
|---|---|---|---|
| **P0 阻断** | 连不上，或连上了完全不通 | **立即插卡，占主位** | 显示 |
| **P1 降级** | 能用但明显不对：某类站点不通、UDP 不通、DNS 解析极慢 | 插卡，**不抢焦点** | 显示 |
| **P2 提示** | 规则数据过期、配置可优化 | **不上中间** | 显示 |

中间区域同一时刻**最多一张问题卡**。多个 P0 同时存在时，展示最先出现的那个，其余收进「还有 2 个问题」。

理由：中间是用户的主操作台，问题卡是打扰。打扰要克制到「不解决就没法用」的那一类。

---

## 5. 诊断包

转交时给 AI 的必须是结构化数据，不是一句「打不开」。至少包含：

- 连接状态、模式（proxy / TUN）、节点协议与能力（是否支持 UDP）
- 实际使用的 DNS 服务器与解析结果（含解析耗时）
- 路由命中了哪条规则、走直连还是代理
- 目标可达性、出口 IP 与直连 IP 对比
- 与问题相关的最近 N 条运行时日志

**诊断包在采集时就生成并随记录保存**，不是转交时才现采集——问题发生时的情况事后往往复现不出来。

---

## 6. 生命周期

```
探测失败 / 运行时非正常退出
        ↓
   登记问题记录（本地，无 AI）
        ↓
   P0/P1 → 中间插卡；P2 → 只进列表
        ↓
   用户点「让 AI 修复」
        ↓
   状态 handed_off，新建或复用 AI 会话，一次性投喂诊断包
        ↓
   AI 修复 → 复测通过 → resolved
   AI 修不了 → 停在 handed_off，卡片保留，可再次转交
        ↓
   用户点「先不管」→ ignored（仍可在列表里找到并恢复）
```

- **复测必须做**：AI 说「修好了」不算数，要跑一次同样的探测，通过才置 resolved。
- **resolved 不等于删除**：保留记录，同类问题再次出现时直接重开并计数。
- **重新出现时提示历史**：卡片上写「这个问题第 3 次出现了，上次是 10 月 28 日」。这正是单独做一层的价值。

### 卡片上的动作由类型决定

| 问题类型 | 卡片动作 | 为什么 |
|---|---|---|
| 权限类（`tun_denied` / `helper_missing`） | **只有「重试」** | AI 修不了权限问题，多给选项只是让人犹豫 |
| 诊断类（`dns_fail` / `probe_timeout` / `no_route`） | 「让 AI 定位」 | 需要看数据判断 |

不给权限类问题配「切换模式」之类的第二条路：对二级用户，切过去也是半残状态，还不如把话说清楚。

---

## 7. 入口

| 位置 | 内容 |
|---|---|
| 中间区域 | 当前 P0/P1 的问题卡（最多一张） |
| 问题列表 | **中间区域的二级页面**，入口是问题卡上的「查看全部」 |

问题列表不占左栏，也不进设置页：

- **左栏是导航级的**（配置列表），塞一个问题列表进去，它会变成两个不相干的东西并排
- **设置页太深**——网络坏的时候用户不会想到去设置页找

**没有问题时，问题列表没有任何入口。** 它只在用户真正需要的时候出现，不常驻、不占位。

---

## 8. 与「重置网络」的关系

E3（重置网络）**不经过本模块**，也不依赖 AI。它是最后一道防线：AI 不可用、问题列表也看不懂的时候，用户仍然能一键回到安装前的状态。

问题卡上带 E3 的入口，但两者是独立能力。
