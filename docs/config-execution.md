# 配置确认之后的执行

> 日期：2026-11-03
> 起点：用户在 AI 对话框里走完提问，AI 给出推荐配置。
> 终点：连接建立、中间区域变成可用状态；或用户取消、AI 接住。

---

## 1. 确认页：两种写法，按用户类型分叉

| | 一级 / 二级 | 三级 |
|---|---|---|
| 展示内容 | **人话**：会怎么接管、哪些直连、之后能不能改 | **人话 + 网络术语**：连接方式、端口、分流规则名、DNS 策略 |
| 按钮 | `开始配置` `取消` | `确认并写入` `取消` |
| 确认后 | **一路执行到连接成功** | **只写配置，准备好「连接」按钮，不自动连** |
| 为什么 | 他们不会自己动手。停在「配置好了但没连」等于把人卡住 | 他要自己决定什么时候连、连哪个，替他连是越界 |

三级用户看到的是**具体数值和行为**，不是术语标签：

```
连接方式    所有软件都走 VPN
直连范围    中国大陆的网站和地址
DNS         本地 2 个候选 / 境外 2 个候选，境外走 VPN 查询
监听        127.0.0.1:7890（HTTP 和 SOCKS5 都支持）
```

**仍然不出现 proxy、TUN、分流、规则集这四个词。** 他在第三问看到的就是「全部软件自动走 VPN / 只给我一个代理地址」，确认页必须用同一套说法，否则他会以为自己在确认两件不同的事。

技术细节给**数值和具体地址**，不给术语：端口给 `7890`，DNS 给实际服务器地址，直连范围给国家名。规则集文件名这类东西放设置页的高级区，不上确认页。

---

## 2. 一级 / 二级：确认之后依次做什么

顺序不可变，每一步失败都要能说清卡在哪。

| # | 动作 | 失败时 |
|---|---|---|
| 1 | 申请权限（二级：TUN 授权） | 见 `docs/tun-mode.md` §8，只给重试 |
| 2 | 渲染并写入 sing-box 配置 | 配置校验不过 → 不启动，报具体项 |
| 3 | 启动运行时 | 非 0 退出 → 问题管理模块 |
| 4 | 设置系统代理（一级；二级走 TUN 不设） | 逐网络服务确认，写好备份 |
| 5 | 探测：DNS 解析 → 目标可达 → 出口 IP | 失败 → 问题管理模块，中间插卡 |
| 6 | 设置中间区域的按钮与状态 | — |
| 7 | 报告结果 | — |

第 4 步的备份（`proxy_backup`）是 E3 重置网络的前提，**必须在改之前写**。

---

## 3. 三级：确认之后

只做两件事：

1. 渲染并写入配置，跑一次 `sing-box check`
2. 把中间区域的「连接」按钮准备好

**不自动启动。** 他点了才连。理由：三级用户选的可能是「只给我一个代理地址」，那时候连不连、什么时候连，取决于他手上那个软件配好了没有——替他连等于替他做了一个他还没准备好的决定。

---

## 4. 取消之后

不重复弹同一个确认。AI 接一句：

> 好，那先不配。你想改哪一项？还是先看看能连成什么样？

并列出可改的几项（走 VPN 的范围 / 全部走 VPN / 稍后再配）。用户不改就停在这里，中间区域保持未配置状态，`连接` 按钮仍然可用——**让他先试一次**，比逼他看完所有选项更有说服力。

---

## 5. 中间区域此时显示什么

| 元素 | 说明 |
|---|---|
| 主按钮 | 连接 / 断开，永远只有一个 |
| 状态区 | 已连接 / 未连接 / 连接中；已连接时显示出口国家 |
| 代理卡 | 仅三级选了「给我一个代理地址」时出现 |
| 一行提示 | 「有问题随时问右侧的助手」——常驻的轻提示，不是弹窗 |

这一屏是**首次配置完成后的稳定形态**。之后 AI 可以增删块，但主按钮与状态区不动。

## 6. 节点信息从哪来

**控制面板生成之后，问一次：**

```
服务器用哪一个？

1. 用我们提供的          已经配好，直接就能连
2. 用我自己的            我会给你一个地址，或者你自己填
```

选 1 → 用种子配置（§9），流程结束，用户可以点顶部按钮连接。
选 2 → 进入自定义配置，两种模式：

| 模式 | 用户做什么 | 我们做什么 |
|---|---|---|
| **URL** | 贴一个订阅链接 | 拉下来解析出 name / 地址 / 端口 / 密码 / 加密方式 |
| **编辑** | 手动一行行填 | 只做校验与保存 |

一个节点需要五个字段：

```
Name      洛杉矶
Server    <服务器地址>
Port      <端口>
Password  <密码>
Method    aes-256-gcm
```

**约定：**

- 密码**不落明文**，直接进 `secrets.enc`，配置里只留引用
- 解析或填写的结果必须**复述给用户确认**，尤其是 Method 与 Port——这两个错了连不上但看不出原因
- URL 模式**只解析，不自动连接**。拉下来的东西可能来自任何地方，用户确认之后才生效
- 本阶段**只做 Shadowsocks**

### URL 模式的三个边界

| 边界 | 要求 |
|---|---|
| 支持格式 | **本期只做 base64 编码的多节点订阅**（`ss://...` 列表整段 base64）。最常见、天然支持多节点，正好对上「一个配置挂多个节点」。其它格式明确报「暂不支持」，**不要猜着解析** |
| SSRF | 只允许公网地址；禁止重定向到内网；限制响应大小与超时。用户填的 URL 由我们发起请求，不设限就能访问本机与内网服务 |
| 拉不到 | 明确告诉用户「这条现在拿不到，等能上网再试」，**不保存空配置** |

### 后续会遇到的授权形态（本阶段不做，先记下）

| 形态 | 例子 |
|---|---|
| 账号密码 | 大厂给的邮箱 + 密码，登录后换取节点 |
| 加密 URL | 一次性订阅链接，内含多个节点 |
| 直接配置 | 贴一段 SS/VMess 链接 |

这些都要在节点导入处留一个入口，但本阶段的实现只到「URL 解析 + 手动编辑」。

## 7. 生成 sing-box 配置

四个字段映射到 outbound：

```json
{
  "type": "shadowsocks",
  "tag": "node-<id>",
  "server": "<server>",
  "server_port": <port>,
  "method": "<method>",
  "password": "<从 secrets.enc 取>"
}
```

生成后**先跑 `sing-box check`**，退出码非 0 不启动，把具体报错翻译成人话给用户。

---

## 8. 配置创建后的连通性测试

写入并启动之后，按顺序测一遍，任一项失败就登记到问题管理模块：

| 测什么 | 失败意味着 |
|---|---|
| DNS 能否解析一个境外域名 | DNS 配置错、或 DNS 被劫持 |
| 通过代理能否拿到出口 IP | 节点连不上、密码或加密方式错 |
| 出口 IP 与直连 IP 是否不同 | 分流没生效，流量没进隧道 |
| 一个目标站点能否打开 | 节点通了但目标被拦 |

前两项决定「能不能用」，后两项决定「用得对不对」。四个都过了，才把状态置为已连接并告诉用户。

## 9. 默认节点的凭据从哪来

**决定：不随包，只从种子 URL 拉。**

```
https://meshnetprotocol.github.io/veyl_seed.json
```

| 项 | 做法 |
|---|---|
| Git 仓库 | **不放** |
| 安装包 | **不预置** |
| 首次启动 | 从 URL 拉取，**落盘缓存** |
| 之后启动 | 直接用缓存，不依赖网络 |
| 更新 | 后台按版本号检测，自动升级 |

### 为什么不做成随包

安装包是公开下载的。打包进去的节点凭据等于半公开——任何人解包就能拿到，拿去白嫖、把节点打爆。**这个代价比「首次偶尔拉不到」更贵。**

### 怎么保证拿得到

这是**运维层面**的保证，不是代码层面的：

- 会持续保证这个 URL 可达，必要时调整
- 首次分发时，如果某个用户拉不到，通过其它渠道把种子给他
- 实测见 §10：无需代理即可直连

### 拉不到怎么办

不报错、不卡住：

```
现在拿不到我们的默认配置，检查网络后重试
也可以现在手动添加一个节点

[ 重试 ]   [ 手动添加 ]
```

「手动添加」就是编辑模式，本来就在设计里（§6）。

### 一条要写清楚的例外

**这是整个产品里唯一一处「首次启动依赖网络」。**

`docs/user-flows.md` §1.3 的离线原则要求所有资源随包。这里破例，是因为默认节点凭据属于「分发出去就会被滥用」的东西，和提示词、规则集性质不同。

例外要写在这里，否则以后会被人当成惯例——下一个资源也会有人主张「也别预置了吧」。

## 10. 种子配置的版本管理与更新

### 节奏

| 触发 | 说明 |
|---|---|
| 启动 5 分钟后 | 避开首启高峰，不跟首次拉取抢 |
| 之后**每 6 小时** | 常规轮询 |
| **连接失败、且当前用的正是种子节点** | **立即强制刷新一次** |

第三条最重要。定时是兜底，真正的信号是「连不上」——用户连不上时他等不了六小时。种子节点挂了而我们六小时后才知道，等于没有兜底。

### 怎么拉

- **每次直接拉全文，自己算内容哈希比对**，不依赖 `version` 字段
- 理由：`version` 要人手动改，「改了文件忘了改版本号」正是 TweetPilot 那次事故的根因（`docs/issues/tweetpilot-resource-version-gap.md`）。文件才 421 字节，没必要为省这点流量冒这个险
- 先带 `If-None-Match` 发条件请求，304 就直接结束——服务器说没变就不用下
- **同一时刻只允许一个请求在飞**，避免并发写坏缓存

### 我们消费的文件

`veyl_seed.json`，421 字节：

```json
{
  "version": 1,
  "updated_at": "2026-11-03T13:53:52Z",
  "nodes": [
    { "name": "meshflux69 [美国]", "server": "...", "port": 13774,
      "method": "aes-256-gcm", "password": "..." }
  ]
}
```

上游是 `bootstrap.json`（4686 字节，含服务商元数据、完整 sing-box 配置、`routing_rules`）。我们从中**只抽取节点**，生成这个精简文件。

### 分流不在这里

种子**只给节点，没有分流规则。**

分流由 AI 在对话里问出来（第四问：本地直连 / 全部走 VPN / 指定服务），在本机生成。

理由：**分流是用户的偏好，种子是运维资源。** 把偏好混进运维文件，每次覆盖种子就会把用户的改动一起冲掉——而且他不会知道为什么。

两层永远分开：

| 层 | 来源 | 覆盖种子时 |
|---|---|---|
| 节点 | `veyl_seed.json` | 整层替换 |
| 分流 | AI 对话 + 用户手动调整 | **永不动** |

### 可达性实测（2026-11-03）

国内网络、VPN 关闭、系统代理全关、`--noproxy '*'`：

| 文件 | 结果 |
|---|---|
| `veyl_seed.json`（客户端消费） | HTTP 200 · 484ms · 421 字节 |
| `bootstrap.json`（上游） | HTTP 200 · 330ms · 4686 字节 |

阿里 DNS（223.5.5.5）直接解析出 `185.199.108-111.153`（GitHub Pages 官方地址段），19ms 返回 `NOERROR`。

**结论：无需代理即可直连。** 这是「不随包」这个决定能成立的前提，所以要定期复测；一旦哪天不通了，这个决定就必须重新评估。

### 自动覆盖的边界

拿到新版本之后**自动覆盖本地缓存，不问用户**。但覆盖不等于重启连接：

| 情况 | 行为 |
|---|---|
| 当前未连接 | 直接替换缓存 |
| 当前用种子节点已连接 | **替换缓存，不动当前连接**，下次连接生效 |
| 新版本里没有当前正在用的那个节点 | 缓存照换；当前连接保持到用户主动断开，下次连接落到新列表里的第一个可用节点 |
| 拉取失败 / 校验不过 | 保留旧缓存，静默 |

**从不因为更新而打断用户的连接。** 网络产品最忌讳「用得正好好的，它自己断了」。

### 只向前

不做回滚。旧版本在校验通过前保留，那是原子替换，不是可回退的版本历史。

版本机制与 `docs/upgrade.md` 的其余资源相同，只是数据源不同。
