> 版本：v0.1

## 0. 阶段定义

把 Veyl 从「一个必须手动打开、必须聊天、出错只能问 AI 的窗口」改成：

> **一个常驻菜单栏、能把用户从零带到连上、连不上时能自己定位，并且用户随时能一键恢复网络的桌面网络工具。**

三条判断标准，任何一条不成立就不算完成：

1. 用户装上应用，**不读文档、不配 AI**，也能通过界面导入配置并连上。
2. 连接中关闭窗口，应用继续在后台工作；连接中退出应用，网络**一定**恢复。
3. 网络出问题时，用户有一个**不依赖 AI、不依赖外网**的「恢复网络」按钮。

## 1. 背景：P1 验收暴露的问题

| # | 现象 | 根因 | 本阶段回应 |
|---|---|---|---|
| 1 | 连接中退出应用 → 整机断网 | 退出只停运行时、不撤系统代理（D-26） | R4 退出即断开、R5 失败不放行 |
| 2 | 用户以为关窗口=退出，实际应用必须一直开着 | 没有托盘、没有后台概念 | R1–R3 |
| 3 | 首次打开不知道下一步干什么 | 首屏是空聊天框，引导只有一行不可点的文字 | R8–R11 |
| 4 | AI 找不到本地导入的节点 | 工具描述误导 + 协议枚举缺失（D-35） | 已修；R21 进一步把 AI 从主流程移开 |
| 5 | 没有配置文件时无路可走 | 默认目录服务仍是本地 mock（`127.0.0.1:18090`） | R13–R17 |
| 6 | 没有 VPN 就访问不了 GitHub，也就拿不到配置 | 分发与导入路径没有产品化 | R18–R20 |
| 7 | 状态面板是给工程师看的，主操作却不在面板里 | 面板只读，连接只能靠 AI | R26–R30 |
| 8 | UI 根本无法直接连接/断开/列节点 | 后端只暴露了 `runtime_status` 等查询命令 | R27、R28 |

第 8 条需要单独强调：**当前前端没有任何一条能发起连接或断开的 Tauri 命令**，`VpnConnect` / `VpnDisconnect` 只存在于 AI 工具层。这是本阶段 UI 化的前提。

## 2. 设计原则（本阶段确立，后续阶段沿用）

1. **手动路径优先**
   「连接 / 断开 / 导入配置 / 刷新配置 / 恢复网络」五件事必须完全离线可用，不得依赖 DeepSeek、不得依赖任何在线服务。AI 出问题不能导致用户断网且无法自救。

2. **AI 是助手，不是入口**
   应用启动不自动发起对话。只有用户主动点击「诊断网络」时才自动创建一次诊断会话。

3. **破坏性操作必须先可回滚**
   任何改动系统网络状态的路径，进入前必须已有回滚数据（系统代理备份），退出时必须验证已回滚。

4. **后台运行 ≠ 后台失控**
   应用在后台可以不打扰用户，但连接状态必须随时可见（托盘图标 + 菜单状态），且随时可一键断开。

5. **不静默失败**
   导入、连接、刷新配置、恢复网络，任一失败都要在界面上给出人话原因和下一步动作。

## 4. A. 常驻与生命周期

### 4.1 应用状态机

进程状态：

| 状态 | 含义 | 窗口 | 托盘 |
|---|---|---|---|
| `foreground` | 用户正在使用 | 显示 | 存在 |
| `background` | 用户关掉了窗口，应用仍在跑 | 隐藏 | 存在 |
| `quitting` | 正在执行退出流程 | 任意 | 存在（直到进程结束） |

连接状态与进程状态**正交**：后台运行时连接保持，托盘图标要能反映连接状态。

事件 → 行为：

| 事件 | 窗口 | 进程 | 连接 | 是否提示 |
|---|---|---|---|---|
| 点窗口关闭按钮 / Cmd+W | 隐藏 | 存活 | 保持 | 否 |
| Cmd+Q / 应用菜单「退出 Veyl」 | 不变 | 等用户选择 | 保持 | **是，阻塞对话框** |
| 对话框选「后台运行」 | 隐藏 | 存活 | 保持 | — |
| 对话框选「退出」 | 关闭 | 结束 | 断开 | 仅断开失败时 |
| 托盘「显示 Veyl」 | 显示并聚焦 | 存活 | 保持 | — |
| 托盘「退出」 | 关闭 | 结束 | 断开 | 仅断开失败时 |
| 再次启动应用（单实例） | 显示并聚焦 | 存活 | 保持 | — |

### 4.2 R1 菜单栏常驻

- 应用启动后，菜单栏（macOS status bar）始终存在一个 Veyl 图标。
- 图标可区分：`已连接` / `未连接` / `连接异常`。三态必须有肉眼可辨的差异，不能只靠颜色（色盲可用性）。
- 托盘在窗口隐藏时仍然存在，点击图标弹出菜单。

**验收**：启动应用 → 菜单栏出现图标；点击「关闭窗口」→ 窗口消失、图标仍在、进程仍在。

### 4.3 R2 关闭窗口 = 进入后台

- 点击窗口关闭按钮（红灯）或 Cmd+W：隐藏窗口，不退出进程，**不弹任何提示**。
- 连接状态保持不变。
- 再次打开：托盘「显示 Veyl」，或点击 Dock 图标，或再次启动应用。

**验收**：连接中关闭窗口 → 网络不断、sing-box 进程仍在、托盘图标显示已连接。

### 4.4 R3 Cmd+Q 阻塞确认

- Cmd+Q 以及应用菜单里的「退出 Veyl」必须被拦截，弹出一个**阻塞式**对话框。
- 文案必须说清后果：

  > 退出 Veyl 会断开当前连接并恢复网络。
  > 想让连接保持，请选择「后台运行」。

  按钮：主按钮「后台运行」，次按钮「退出」。
- 对话框必须在窗口隐藏、应用不在前台时也能出现在最前。
- 「后台运行」= 隐藏窗口，进程继续，连接继续。
- 「退出」= 走 §4.6 的退出流程。

**验收**：连接中按 Cmd+Q → 弹出对话框；选「后台运行」→ 窗口消失、网络不断；选「退出」→ 应用结束、网络恢复。

### 4.5 R4 托盘菜单

菜单**只有两个可点击项**：

1. **显示 Veyl** — 显示主窗口并聚焦；若窗口已显示则聚焦。
2. **退出** — 执行 §4.6 退出流程。

可选的第三行（不可点击的状态文案，如「已连接 · 东京 01」）本阶段可以做，但不作为验收项；若做，不得让菜单变成三项可点击操作。

**验收**：菜单项数量与行为一致；「退出」在连接中会先断开再退出。

### 4.6 R5 退出即断开（顺序不可变）

退出流程严格按顺序执行：

1. 标记 `quitting`，拒绝新的连接请求。
2. **撤销系统代理**，并确认已无可用的网络服务仍指向本地端口。
3. 停止 sing-box 运行时，确认进程已消失。
4. 删除渲染出来的明文配置文件。
5. 进程退出。

失败处理：

| 失败点 | 行为 |
|---|---|
| 第 2 步失败 | **中止退出**，提示「网络尚未恢复，退出会导致断网」，提供「重试」与「强制退出（会导致断网）」 |
| 第 3/4 步失败 | 记录日志后继续退出；启动时的遗留回收会兜底 |
| 用户强制退出 | 允许，但必须明确二次确认后果 |

**这条是硬要求**：宁可退出失败，也不能带着一个指向死端口的系统代理退出。

### 4.7 R6 单实例

- 同一用户只允许一个 Veyl 进程。
- 第二次启动（双击 App、Dock 再次点击、`open -a Veyl`）不创建新进程，而是唤起已有窗口。
- **第二实例在确认「已有实例」之前，不得执行任何崩溃恢复**——撤系统代理、回收 sing-box、清理明文配置这三件事会直接拆掉正在运行的那个实例。这是本阶段最容易漏、后果最重的一条：用户从 Dock 再点一次应用，后台连接就没了。
- 理由：两个实例会争抢 `runtime.pid`、系统代理备份与配置文件，属于必然损坏。

**验收**：连续启动两次 → 只有一个进程；第二次启动把窗口带到前台。

### 4.8 R7 Dock 行为

- 窗口显示时：Dock 有 Veyl 图标，激活策略为 `Regular`。
- 窗口隐藏时：**允许**切换为 `Accessory`（菜单栏应用形态），让 Dock 不残留图标。
- 若切换策略导致图标丢失、窗口无法恢复等技术问题，允许保留 Dock 图标作为降级方案，但必须在实现记录里写明。

### 4.9 异常路径

| 场景 | 期望 |
|---|---|
| `kill -9` / 强制退出 / 断电 | 下次启动靠 `proxy.recover_stale()` + 遗留进程回收 + 配置清扫兜底（已实现，本阶段只补验收） |
| 退出流程中崩溃 | 同上 |
| 托盘图标创建失败 | 应用仍能正常运行，日志告警；不得因托盘失败而无法启动 |

## 5. B. 首次使用引导

### 5.1 判定

首次引导的触发条件是**同时**满足：

- 没有完成过引导（`settings.onboarding_completed` 不存在）；且
- 没有 DeepSeek Key 或没有任何 profile。

只要用户曾经完成或跳过一次，后续启动一律进控制台（R11），不再弹引导。

### 5.2 R8 三步向导

向导为独立全屏页面，不可被聊天打断，三步：

| 步骤 | 内容 | 可跳过 |
|---|---|---|
| 1. 认识 Veyl | 一句话说明 + 「它现在能做什么、需要你准备什么」 | 否 |
| 2. 配置 DeepSeek Key | 见 R9 | **是** |
| 3. 准备配置文件 | 「使用官方默认配置」或「导入我收到的文件」 | 否（二者必须选一，或明确选择「稍后再说」） |

「稍后再说」允许进入主界面，但主界面必须持续显示一条可关闭的引导条，指向缺失的那一步。

### 5.3 R9 DeepSeek Key 引导

这是本阶段唯一要求用户准备的账号。

**界面元素**：

- 说明：AI 用来做什么（诊断网络、解释错误、推荐节点），以及**不做**什么（不代理流量、看不到账号密码）。
- 主按钮：**打开 DeepSeek 开放平台** → 用系统默认浏览器打开 `https://platform.deepseek.com/`。
- 同时显示可复制链接与分步说明：
  1. 注册 / 登录
  2. 进入「API Keys」
  3. 创建新的 Key
  4. 复制以 `sk-` 开头的字符串
  5. 粘贴回 Veyl
- 输入框 + 「保存并验证」按钮。
- 保存后展示掩码（如 `sk-••••••1a2b`）与验证状态：`已验证` / `已保存但未验证` / `无效或已吊销`。
- 全流程不得显示完整 Key，不得写入日志。

**行为要求**：

- 输入前后空白自动去除；不以 `sk-` 开头的直接在前端拒绝并说明原因。
- 验证失败时保留用户输入，允许直接改后重试，不要清空。
- 「打开平台」按钮不得被当作自动注册/代登录；应用不收集任何账号信息。

### 5.4 R10 允许不用 AI

- 跳过 Key 后，**手动路径必须全部可用**：导入配置、连接、断开、刷新默认配置、查看诊断结果。
- 输入框在无 Key 时禁用，并给出一行说明与「去配置」入口；不要静默报错。
- 无 Key 时点击「诊断网络」仍然可用，输出结构化检查结果，但没有 AI 解释。

**验收**：全新安装 → 跳过 Key → 导入文件 → 连接成功。

### 5.5 R11 主区域（没有 AI 会话时）

启动后默认进入**控制台**，不是空聊天。侧边栏结构：

```
总览（固定，默认选中）
──────────
对话（会话列表，可折叠；每条可删除）
──────────
设置
```

删除会话是必需能力，不只是整理列表：用户需要一个「没有任何对话」的状态来验证控制台空态（§5.5、R31）。

控制台是**单一主行动**的界面，不是营销页：

| 当前状态 | 主区域显示 | 主按钮 | 次按钮 |
|---|---|---|---|
| 无配置文件 | 「还没有可用的配置」 | 使用官方默认配置 | 导入文件 |
| 有配置、未连接 | 上次使用的节点 + 出口未知 | 连接 | 换节点 |
| 连接中 | 节点 + 进度 | 取消 | — |
| 已连接 | 节点名、出口 IP、已连接时长 | 断开 | 换节点 |
| 连接失败 | 错误摘要 + 「为什么会失败？」 | 重新连接 | 诊断网络 |

底部保留输入框（无 Key 时禁用），placeholder：`告诉我要去哪儿，或者让我诊断网络问题`。

控制台下方固定三个入口：`诊断网络`、`导入配置`、`默认配置（当前版本/更新时间）`。

### 5.6 R12 引导可重入

设置页提供「重新运行首次引导」，用于排查与演示；运行不会删除已有 Key 或配置。

### 5.7 R31 删除对话

**目的**：让用户可以清理历史，也让「没有任何对话」这个状态可被验证。

行为：

- 侧边栏每个会话项提供删除入口（悬停出现或右键菜单，二选一）。
- 删除前必须二次确认，文案写清「删除后无法恢复」，并显示会话标题。
- 删除的是该会话本身**和它的全部消息**，不影响其他会话、不影响配置与 Key。
- 该会话的工具调用记录必须一并删除。`tool_calls.session_id` **没有外键级联**，必须显式删除，否则参数与结果会留在库里，形成「界面删了、数据还在」的半删除。
- 若该会话有正在进行的 AI 请求：**由 UI 先取消并等到请求结束**，再发起删除；Host 在仍有进行中的请求时拒绝删除（`PRECONDITION_FAILED / active_request`）。这样能避免「取消信号还没到、删除已执行、迟到的流式分片又把消息写回来」的竞态。
- 若删除的是当前正在看的会话：自动切到下一个会话；没有别的会话时回到**总览**（控制台空态）。
- 删除失败要提示原因，列表不得出现「界面上没了、数据库里还在」的半删除状态。

**不做**：回收站、撤销删除、批量删除。删除即不可恢复，靠二次确认兜底。

**验收**：删除最后一个会话后，界面回到总览，侧边栏对话列表为空；重启应用后仍然是空的（确认不是只改了前端状态）。

### 5.8 R32 API 设置：基础 / 高级

**目的**：默认只需要一个 DeepSeek Key；愿意折腾的用户可以接任意兼容端点。

#### 基础模式（默认）

- 只有一个输入框：DeepSeek API Key。
- 保存后自动生成一个内置 provider：`openai` 兼容、`https://api.deepseek.com`、模型 `deepseek-chat`。
- 沿用现有的保存、验证、掩码、清除流程，不新增概念。
- 首次引导只走基础模式，高级模式藏在「高级设置」里。

#### 高级模式

参考 TweetPilot 的 provider 配置方式，字段与行为对齐：

| 字段 | 说明 |
|---|---|
| 名称 | 用户可读，列表展示用 |
| API 类型 | `openai` 兼容 / `anthropic` 兼容 |
| Base URL | 可空；空则用该类型的官方地址 |
| API Key | 可空，仅当端点是本机 Ollama 时允许 |
| 模型 | 必填，例如 `deepseek-chat`、`claude-sonnet-4-6` |

行为：

- Provider 列表：新增、编辑、删除、**设为当前**；同一时刻只有一个「当前」。
- 内置预设一键填充：DeepSeek、OpenAI、Anthropic、Moonshot、Ollama（本地）。
- 「测试连接」发一个最小请求，显示耗时或可读的失败原因。
- 保存后新会话立即使用新 provider；**不打断正在进行中的请求**。
- **保存只保存，不改变当前 provider**；唯一例外是当前没有任何 provider 时，保存的第一个自动成为当前。切换只能通过「设为当前」——编辑一个备用 provider 不该让对话流量悄悄换端点，这和「节点连不上不得悄悄回退默认包」是同一条原则。
- 切换「当前」provider 前必须已有可用 Key（Ollama 例外）。
- Base URL 提示随 API 类型变化：`openai` 提示 `/v1/chat/completions` 兼容；`anthropic` 提示 `/v1/messages` 兼容。

#### 约束

- Base URL 只允许 `http` / `https`；`http` **仅限** `localhost` / `127.0.0.1`，用于本地模型。
- 不允许把 Key 拼进 URL，也不允许在日志、错误信息、界面回显完整 Key。
- 多 provider 的 Key 全部进 `secrets.enc`；名称、类型、URL、模型等非敏感字段进 settings。
- 删除 provider 必须同时删除它的 Key；不允许留下孤儿密钥。
- 高级模式界面要有一句风险提示：**请求会发往你填写的端点，请确认你信任它**。
- 已有的单一 DeepSeek Key 必须无损迁移为列表里的一个 provider，基础模式仍显示它。

**验收**：详见 §11 的 H1–H5。

## 6. C. 默认配置源

### 6.1 文件形态（已实测）

`https://meshnetprotocol.github.io/bootstrap.json` 不是节点列表，而是一个**完整的 sing-box 配置包**：

```
{
  name, description, provider_id, status, visibility, tags,
  author, package_hash, updated_at, source_updated_at,
  config:    { log, dns, inbounds, outbounds, route },   // sing-box 原生结构
  routing_rules: { ... }                                  // 2 项
}
```

实测当前版本：

- `config.inbounds` = **`tun`**（Veyl 不使用 TUN）
- `config.outbounds` = 2 个 `shadowsocks` + 1 个 `selector` + 1 个 `direct`
- `updated_at` 为 `1970-01-01`（无意义），应改用 `source_updated_at` 与 `package_hash` 判断版本

> **这是内测阶段的临时方案。** 包体与节点凭据都直接放在公开仓库上，只为让早期用户装好就能用、不阻塞联调。它不满足对外发布的安全与运营要求，正式发布前必须替换（见 §6.7）。

### 6.2 R13 接入与刷新

- 内置默认源：`https://meshnetprotocol.github.io/bootstrap.json`，可在设置中查看但**不允许普通用户随意改成任意地址**（避免被引导到恶意配置）。调试可用环境变量覆盖，与现有 `VEYL_CATALOG_URL` 同一机制。
- 刷新时机：应用启动后（非阻塞）、每 6 小时、用户手动点「刷新」、连接失败诊断时建议刷新。
- 拉取失败不打扰用户：已有可用配置时静默使用缓存，并在「默认配置」入口显示 `离线 · 上次更新 X 天前`。
- 首次安装且拉取失败：主区域直接给 R18 的导入引导，不留空白。

### 6.3 R14 配置包 → 可用连接

配置包不能直接喂给我们的运行时（inbounds 是 tun），需要适配：

1. **丢弃** `config.inbounds`，替换为 Veyl 的 `mixed` 入站 + Clash API（随机本地端口 + Bearer secret）。
2. **保留** `config.outbounds`、`config.route`、`config.dns`、`config.log` 的结构与语义。
3. 选择节点 = 设置 `selector` 的 `default` 指向目标出站 tag；**不要**把包拆成互不相干的单节点配置，否则 route 规则里对 selector 的引用会失效。
4. 不认识的出站类型跳过并告警，不因一个节点失败导致整个包不可用。
5. 渲染结果必须通过 `sing-box check` 才算可用。
6. 连接前重新渲染，不在磁盘上复用旧文件（沿用 P1 不变式）。

**凭据处理**：包内出站含共享凭据。

- 不得写入 `profiles.config_json`（该表有凭据键名扫描）。
- 包体加密存放（`secrets.enc`，键如 `pkg:<provider_id>`），数据库只存元数据：`provider_id`、`package_hash`、`source_updated_at`、出站 tag 列表。
- 渲染出来的配置仍是 0600、断开即删。

### 6.4 R15 完整性与信任

- 只允许 HTTPS，且域名固定；发生跨域重定向一律拒绝。
- 校验 `package_hash`（算法待确认，见 §13）。
- 校验 JSON 结构与必填字段；`status` 不是 `active` 的包拒绝启用。
- 校验结果必须记录到日志（不含凭据）。
- 新包连续连接失败 2 次 → 提示「默认配置可能有问题」，提供回到上一版本。

### 6.5 R16 不打断在线连接

- 刷新到新版本时，**不得**替换正在使用的配置，也不得重连。
- 新版本在下一次连接时生效。
- 用户正在使用时，只在「默认配置」入口显示一个小徽标：`有新版本`。

### 6.6 R17 版本可见

在控制台与设置页都要能看到：

- 当前使用的包：`种子V21`（`provider_id` 尾段）
- 版本标识：`source_updated_at` 或 `package_hash` 前 8 位
- 本地缓存时间
- 「检查更新」按钮

### 6.7 内测期临时方案与退出条件

**当前做法**：`https://meshnetprotocol.github.io/bootstrap.json` 公开托管，包内节点凭据对所有人可见。

**为什么可以接受**：

- 内测用户少，节点是我们的种子节点，本就是免费提供。
- 目标是让「装好就能连」，不因为凭据签发流程阻塞早期验证。
- 即使凭据被滥用，损失是节点被封，不影响用户本机数据与账号安全。

**明确不接受的后果**，必须在对外发布前处理：

| 要求 | 退出条件 |
|---|---|
| 凭据不得公开 | 改为向用户签发**个人凭据**，或运行时凭据换取（短时 token），公开发布物里不含可用凭据 |
| 节点可轮换 | 有后台轮换机制；泄漏后能在 1 小时内换掉且不要求用户重装 |
| 可归因 | 能按用户/设备识别连接来源，用于滥用处置（内测期可以没有） |
| 分发可回滚 | 公开源可下线，且不导致已安装用户完全不可用（本地缓存 + 手动导入兜底） |
| **来源可认证** | 发布方提供可验证的签名或 sha256 摘要。在这之前，我们只能证明「走的是固定域名的 HTTPS」和「内容与上次不同」，**不能证明这个包是官方发的**。与「凭据不得公开」同一档，对外发布前必须解决 |

**本阶段的要求**：代码层面不把「公开凭据」写死。适配器、存储、刷新都要按「凭据是敏感数据」设计，这样将来换成签发模式时只改取数来源，不动上层。

## 7. D. 无网络下的配置分发

### 7.1 R18 导入是离线能力

- 导入 `.json`（拖入 / 文件选择）**不需要联网、不需要 AI、不需要已连接**。
- 导入后立即可连接，路径不得经过 DeepSeek。
- 导入失败必须区分并说清原因：格式错误 / 没有可用节点 / 不支持的协议 / 文件过大。

**验收**：断网状态下导入一个合法文件 → 成功；随后能连上。

### 7.2 R19 分发说明内置

没有 VPN 时用户访问不了 GitHub，这是预期内的，不是故障。应用必须自带说明：

- 首次引导第 3 步、控制台空态、设置页「导入节点文件」三处都要有一句：

  > 没有配置文件？它由 Veyl 团队分发（`.json` 文件）。从你收到它的渠道下载到本机即可，**不需要能访问 GitHub**。

- 提供「从哪里获取」的入口：默认展示内置的分发说明文本/链接，可在远程更新（联网时刷新），离线时使用内置副本。
- 不得在离线状态下自动打开任何 GitHub 链接。

### 7.3 R20 诊断话术

诊断发现「GitHub / 默认源不可达」时，结论必须写成：

> 现在无法访问默认配置源，这在未连接时是正常的。请先导入本地配置文件并连接，再检查更新。

而不是报一个红色错误。

## 8. E. AI 重定位与网络诊断

### 8.1 R21 职责边界

AI 的核心职责，按优先级：

1. 解释**为什么连不上**，并给出可执行动作。
2. 找到并应用**最新的可用配置**。
3. 在用户同意下修复本机网络设置（仅限受限工具，见 R24）。

AI **不再承担**主连接流程：连接/断开/导入/刷新都必须有纯 UI 路径。

### 8.2 R22 一键诊断

- 控制台与状态面板都有「诊断网络」按钮。
- 点击后：运行诊断 → 创建/复用一个诊断会话 → 把结果交给 AI 解释 → 输出「结论 + 证据 + 建议动作」。
- 建议动作是可点击的，例如：`重新连接`、`刷新默认配置`、`恢复网络`、`换一个节点`。
- 无 Key 时：只显示结构化结果，不调用 AI。

**验收**：人为制造三种故障（节点不可达、系统代理指向死端口、DNS 不解析），每种都能给出正确结论。

### 8.3 R23 诊断项

现有 `DiagRun` 只有 runtime / system_proxy / logs 三项，必须扩展为：

| 分组 | 检查项 | 说明 |
|---|---|---|
| 应用 | 运行时状态、sing-box 进程、版本、配置校验 | 已有 |
| 应用 | 控制面（Clash API）、数据面 | 已有 |
| 系统 | 系统代理：各网络服务分别读取，而不是只看全局 | 新增 |
| 系统 | DNS：当前解析器、能否解析 `platform.deepseek.com` | 新增 |
| 系统 | 默认路由与主接口 | 新增 |
| 网络 | 直连出口 IP 与代理出口 IP 的对比 | 已有部分 |
| 网络 | 目标可达性：默认源、GitHub、DeepSeek API | 新增 |
| 配置 | 当前 profile、默认配置版本、是否过期 | 新增 |

每一项都要有 `ok` / `detail` / `remediation` 三个字段，便于 UI 直接渲染。

### 8.4 R24 网络工具：只读 + 受限写

「默认 bypass 权限」不等于「可以执行任意 shell」。本阶段确立：

- **不提供通用 shell 工具**。
- 新增只读工具 `NetConfigGet`：读取系统代理（逐网络服务）、DNS、路由、接口、监听端口。
- 新增受限写工具 `NetRepair`，只允许三个动作：
  - `restore_direct`：撤销 Veyl 设置的系统代理，恢复备份
  - `flush_dns`：刷新 DNS 缓存
  - `set_proxy` / `clear_proxy`：仅针对 Veyl 自己的代理端口
- 任何写动作前必须已有可回滚快照；动作后必须复读校验。
- 工具描述里要写明「不要用本工具修改与 Veyl 无关的网络配置」。

### 8.5 R25 恢复网络（兜底）

- 主界面固定存在「恢复网络」入口（控制台 + 托盘菜单可选）。
- 行为：断开连接 → 撤销系统代理 → 清掉 Veyl 写入的 DNS 覆盖 → 删除渲染配置。
- **不依赖 AI、不依赖网络**，点击即执行。
- 执行后给出一句话结果：「已恢复直连，当前出口 IP x.x.x.x」或失败原因。
- 这是整个产品的最后一道防线，必须能在 AI 不可用、DeepSeek 不可达、代理指向死端口时工作。

## 9. F. 右侧状态面板

### 9.1 信息分层

面板分三层，越往下越"专业"：

| 层级 | 内容 | 默认 |
|---|---|---|
| 一级（显著） | 状态大卡、主按钮、当前节点、出口 IP、连接时长 | 始终可见 |
| 二级（次要） | 健康三项、本地端口、系统代理状态、连接数 | 可见但弱化 |
| 三级（专业） | 版本、PID、重启次数、配置哈希、最近错误、打开日志 | **默认折叠** |

### 9.2 R26 一级信息

- 状态用「图标 + 文字 + 颜色」三重要素，文字必须是完整句子，如 `已连接 · 东京 01`。
- 出口 IP 与直连 IP 都要显示（便于用户判断是否真的走代理）。
- 连接时长从连接成功时刻起算，断开归零。

### 9.3 R27 主按钮

- 未连接 → `连接`；连接中 → `取消`；已连接 → `断开`；失败 → `重新连接`。
- 按钮是面板里视觉权重最高的元素。
- 点击后按钮立即进入 loading/禁用态，防止重复提交；结果以面板状态变化体现，不弹 toast。
- **后端必须新增 UI 命令**：`runtime_start(profile_id?)`、`runtime_stop()`、`profile_list()`。当前只有 `runtime_status` / `profile_delete`，UI 无法直连。

### 9.4 R28 节点切换

- 点击当前节点名展开节点列表（来自 `profile_list`）。
- 每项显示：名称、协议、地区（若有）、是否当前。
- 选择后：若已连接，则**平滑切换**（先撤代理 → 停旧运行时 → 起新运行时 → 再设代理），切换期间按钮显示进度，不允许出现「界面说已连接、实际断网」的中间态（D-36 的教训）。
- 没有 profile 时，节点区显示「还没有节点 → 导入 / 使用默认配置」。

### 9.5 R29 折叠区

- 三级信息默认折叠，展开状态记入 `localStorage`。
- 最近错误常驻显示（若有），不需要展开。
- 提供「打开日志」入口，定位到日志文件。

### 9.6 R30 修正现有缺陷

- 面板当前把本地端口硬编码成 `127.0.0.1:2080`，而实际 mixed 端口是每次连接随机的。必须改为读取真实端口。
- 后端 `RuntimeStatus` 需要补充：`mixed_port`、`profile_name`、`connected_since`、`latency_ms`（可为 null）。

## 13. 风险与未决问题

1. **默认配置是公开明文凭据（内测期临时方案）**
   `bootstrap.json` 在公网 GitHub Pages 上，包含 2 个 shadowsocks 节点的共享凭据，任何人可下载。这是**内测阶段的临时方案**，不是产品形态：目的是让早期用户装好就能用，不因为凭据签发流程阻塞联调。它不可随对外版本发布——正式发布前必须换成个人凭据或运行时换取，并有轮换能力，退出条件见 §6.7。工程上现在就要按"凭据是敏感数据"设计（加密存储、不落库、不进日志），将来只换取数来源。

2. **`package_hash` 算法未知**
   实测字段存在但不知道是对 `config` 的哪种规范化摘要。需要与配置包的发布方确认；确认前先做结构校验 + HTTPS 域名固定，不假装做了完整性验证。

3. **配置包用 tun 入站**
   Veyl 明确不做 TUN。适配器必须丢弃 `inbounds` 并注入 mixed。若将来包内依赖 TUN 特有的行为（如 `auto_route`、`strict_route`），要单独评估。

4. **Cmd+Q 拦截的平台差异**
   macOS 可通过 `ExitRequested` 拦截；Windows 无 Cmd+Q，靠托盘与窗口关闭。本阶段只在 macOS 验收。

5. **退出对话框在窗口隐藏时的焦点**
   需要确认阻塞对话框能在应用不在前台时弹到最前；若不能，改为先显示窗口再弹框。

6. **Dock 图标切换不稳定**
   `Accessory` ↔ `Regular` 在某些 macOS 版本上会导致窗口无法聚焦，需保留降级方案。

7. **默认配置源的可用性**
   GitHub Pages 在国内可能不可达。需要镜像或对象存储备用地址；本阶段先做"失败可见 + 缓存兜底"。

8. **「恢复网络」的边界**
   如果用户开了别的 VPN 或手动改过代理，恢复网络可能覆盖用户的设置。实现必须先读当前状态，只在当前代理指向 Veyl 时才撤，否则提示"当前代理不是 Veyl 设置的，未改动"。

9. **AI 权限与安全**
   bypass 是本地工具层的默认放行，不代表允许任意命令。R24 的受限工具是硬约束；评审时要重点检查有没有偷偷放开通用 shell。
