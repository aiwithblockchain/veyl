# 能力与分类

> 日期：2026-11-03
> 用途：这是**中间区域编排层的词汇表**，同时也是后台接口契约。
> AI 只能从这里挑能力来编排，不能发明新能力；样式不属于这里，由设计规范固定。
> **本表同时是系统提示词里「可用能力清单」的来源。** 两者必须同源——提示词里多写一项，AI 就会调用不存在的能力；少写一项，AI 就不会用它。
> 先粗后细：本表会随开发逐步扩充。

---

## 1. 分类

| 组 | 名称 | 说明 |
|---|---|---|
| A | 连接控制 | 建立、断开、查看状态 |
| B | 节点管理 | 列出、切换、删除、导入 |
| C | 配置来源 | 官方默认配置的获取与版本 |
| D | 诊断 | 本地自检与 AI 解释 |
| E | 网络修复与重置 | 出问题时的自救 |
| F | AI 服务商 | 配置产品自己的智能 |
| G | 分流 | 决定哪些流量走代理、哪些直连 |
| H | 环境感知 | 提供确定性参数，供 AI 判断，而不是让 AI 去猜 |
| I | 分类目录 | 规则分类的清单与描述，供 AI 把用户意图翻译成规则 |
| J | 问题管理 | 登记、展示、转交连接问题 |
| K | 配置管理 | 列出、新建、切换、编辑、删除「一套配置」（服务于左栏） |

### H 组说明

H 组是**给 AI 提供确定性事实**的工具，不是给界面用的。

原则：**确定性参数由工具返回，AI 只负责判断与表达。** 不让 AI 去猜用户在哪个国家、当前是什么状态——这类事实可测、可缓存、可离线读取，交给工具比交给模型可靠得多。

| 参数 | 来源 | 需要联网 |
|---|---|---|
| `timezone` | 系统时区 | 否 |
| `locale` / `region` | 系统区域设置 | 否 |
| `preferred_languages` | 系统语言偏好 | 否 |
| `egress_ip` | 本机出口 IP | 是（未连接为 null） |
| `egress_country` | 出口 IP 归属 | 是（未知为 null） |
| `behind_proxy` | 当前系统代理是否已开启 | 否 |
| `other_vpn_active` | 是否有别的 VPN / 代理在运行：系统代理指向了非本机端口、存在 utun 接口、或常见 VPN 进程在跑。**只在定位那一刻采样一次，不做常驻监控** | 否 |
| `local_subnets` | 本机各网络接口所在网段（由地址 + 前缀反推，如 `192.168.1.23/24` → `192.168.1.0/24`）。用于 TUN 排除与确认页展示 | 否 |
| `runtime_version` | 本地 sing-box 版本 | 否 |

AI 拿到之后的动作只有三种：一致就确认、不一致就问、为空就问。不需要推理过程。

### J 组说明

J 组是**问题从被发现到被处理**的通道，独立于 AI。

原则：**采集与展示不依赖 AI，转交才依赖。** 网络坏了的时候 AI 大概率也不可用，用户至少要能看见问题、看见历史、并且一键回到可用状态。

| 环节 | 归属 | 依赖 AI |
|---|---|---|
| 探测发现异常、登记记录、分级、插卡 | J1 / J2 | 否 |
| 用户点「让 AI 定位」后投喂诊断包 | J3 | 是 |
| 复测通过后置为已解决 | J4 | 否 |

完整设计见 `docs/issue-management.md`。

### K 组说明

**配置和节点是两个层级**，能力也分开：

| 层级 | 组 | 例子 |
|---|---|---|
| 一套配置 | **K** | 「公司 · 接管全部」，含连接方式、分流、若干节点 |
| 单个节点 | **B** | 一台具体的服务器 |

一个节点可以被多套配置引用。K 组服务于左栏；B 组服务于中间底部的节点选择与切换。

切换配置（K3）会改变连接方式和分流；切换节点（B2）只换服务器。这两个动作在界面上长得像，结果差很远，能力上也必须分开。

## 3. E3 重置网络（新增能力）

**定义**：一旦网络不可用，撤回 Veyl 启动过的所有服务与做过的所有网络改动，把用户恢复到**安装 Veyl 之前**的网络状态。

**为什么必须有**：这是产品的最后一道防线。此时 AI 极可能也是不可用的——它要联网才能工作——所以这条路径**绝对不能依赖 AI**。

**执行顺序（不可变）**：

1. 停止 sing-box 运行时，确认进程消失。
2. 撤销系统代理——逐网络服务读取并恢复，依据连接前写入的备份（`proxy_backup`），不是简单地把开关关掉。
3. 清除 Veyl 写入的 DNS 覆盖。
4. 删除渲染出来的明文配置文件。
5. 复读校验：系统代理均为直连、无 sing-box 进程、配置目录为空。

**界面要求**：

- 二次确认，文案写清后果：会断开连接并恢复到安装前的网络设置。
- 执行中显示进度，不允许静默失败。
- 失败必须说明**卡在哪一步**，并允许重试。
- **不进中间区域的固定骨架。** 它是最后手段，常驻在主界面上既有误触风险，也违背「一屏一个主按钮」。
- 入口：问题卡（`issue_card`）、设置页、托盘菜单、右栏。

**实现缺口**：目前 `net_repair` 只有 `restore_direct` / `flush_dns` / `set_proxy` / `clear_proxy` 四个动作。E3 需要新增一个动作或独立命令，且必须复用已有的备份校验逻辑，不能写成「一律关掉」。

### 3.1 启动自检：App 挂了之后谁来收拾

用户最怕的不是「连不上」，是**「卸载了 App，网络还是坏的」**。所以恢复能力不能只放在界面里，必须有三道：

| 场景 | 谁负责 | 做什么 |
|---|---|---|
| **正常使用中出问题** | 问题卡 / 设置页 / 托盘 | 用户自己能点 E3 |
| **上次异常退出，留下了代理或 TUN** | **启动自检** | 发现「我们写的系统代理还在，但运行时没在跑」→ 启动时主动提示「检测到上次没有正常关闭，要恢复网络吗？」 |
| **App 根本起不来 / 用户直接卸载** | **卸载程序** | 卸载时必须撤销系统代理、删除 TUN 接口、卸载特权 helper、清除开机自启 |

第三行最容易漏，后果最严重：用户卸了 App，网络依然是坏的，而且他已经没有界面可以点恢复了——只能去命令行改系统设置。这会变成一条真实的差评。

**所以卸载清理和 E3 必须共用同一段代码**，不能各写一套。

## 4. 编排来源：AI + 本地规则

中间区域由 AI 编排，但**不是只有 AI 能编排**。当 AI 不可用时，本地规则要能兜底：

| 来源 | 何时生效 | 能做什麼 |
|---|---|---|
| **AI 对话** | 正常情况 | 挑选块、排序、填参数、生成内容 |
| **本地规则** | AI 不可用、或网络异常 | 从问题管理模块取出当前 P0/P1 问题，插入异常卡（如「网络异常」+ 重置网络按钮），保证用户永远有自救入口 |

本地规则只能插**极少数固定块**，不做个性化。它的存在是为了保证：AI 挂了、网断了，用户仍然能看见问题并一键恢复。

---

## 5. 三条硬规则

1. **AI 不可用时可用** 标为「是」的能力，必须在完全不调用 AI 的情况下单独工作，并且有独立的界面入口。
2. **破坏性** 为「高」的能力必须二次确认，并说明具体后果。
3. AI 只能引用本表中的能力。表里没有的，AI 不能自己造。
